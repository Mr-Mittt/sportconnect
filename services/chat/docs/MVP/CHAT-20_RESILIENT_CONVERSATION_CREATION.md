# CHAT-20 · Resilient conversation creation: no spurious 500 on first open, logged failures, and a chat box that never shows "could not create"

**Status:** `TODO` · **Type:** Bug Fix + Enhancement (chat service and client) · **Depends on:** none (CHAT-18 and CHAT-17 are done)

**Filed:** 2026-10-16, while reviewing CHAT-18 (unknown conversation id) with the user: asked what happens when a conversation fails to be created. Reading `internal/conversation` showed two weaknesses, and the user asked for a client behaviour on top.

## What

**Chat service.** `GetOrCreateGroupConversation` and `GetOrCreateDirectConversation` do a `SELECT`, then an `INSERT` if nothing was found, with no lock between them. The tables have unique indexes (`ux_conversations_external_group_id`, `ux_conversations_dm_key`), so when two requests open the same new conversation at once (two group members, a friend pair, a double-fired request such as a double click or React strict mode in dev) the loser hits the unique violation (Postgres `23505`) and answers 500, although the conversation now exists. Handle `23505` by re-selecting and returning the existing row (for DIRECT, after the failed transaction has rolled back, never inside it). Separately, `writeError`'s 500 branch logs nothing, so a failed creation leaves no trace. Log the underlying error with enough context to trace it (route, caller user id, the group id or other user id or conversation id involved; never the token or message content) at error level, for every unexpected error on every route, not only creation.

**Client.** Opening the chat is invisible to the user and must stay that way. When `POST /conversations/open/group/{id}` or `.../direct/{userId}` fails for a reason that is not "you may not use this chat" (a 5xx or a network error, today `ChatLoadFailure = 'transient'`), the chat box (`GroupChatTab`, `FriendChatPanel`) renders as normal: empty history, a usable composer, no error line, no Retry block. The open is retried (a) when the user sends their first message (open, then send; the draft is kept until both succeeded), and (b) when the chat box is revisited or the page reloaded. If the open or the send still fails, show only the existing generic "could not send, retry" error and keep the draft. The user never learns that a conversation could not be created and is never blocked by it. A 403 or 404 on open (not a member, not friends) keeps today's terminal "unavailable" behaviour; that is a real condition.

Entry point: any member opening a group chat tab or a friend chat panel; inputs and outputs are the existing open, history and send endpoints, with no contract change.

**Out of scope:** changing the 403 behaviour for non-members; retry with backoff or a background reconnection loop for the open; any change to the WebSocket path; CHAT-11's general hardening (a11y, responsive, visual regression).

**Tests:** Go, against real Postgres through the pool (not the per-test transaction wrapper): two concurrent opens of the same new group and of the same new DM both return 200 with the same conversation id; an injected insert failure still answers 500 and logs the detail (assert the log line). Client Vitest: open fails with 500, so the box renders normally and the composer is enabled; first send performs open then send and clears the draft; send fails, so the generic error shows and the draft is kept; revisit retries the open; 403 on open still shows the unavailable state. The `e2e` project: `chat-errors.spec.ts` currently expects a visible error for a failed open, so it needs updating for the new rule (only the forbidden case stays visible); `E2E_OVERVIEW.md` follows. Client strings reuse the existing send-failure copy; a new string needs en and vi in the same change.
