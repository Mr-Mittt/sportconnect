## What we worked on

Implemented ticket B6a (Pinned Posts) from the group MVP backlog. This involved a full backend feature: DB migration, entity, repository, DTOs, service methods, controller endpoints, and Spock test coverage. Extended design discussions resolved the data model, cross-domain validation strategy, permission scope, pin limit, and the `pinnedBy` type.

## Decisions made

- **Who can pin:** Both `group_owner` and `group_admin` (not members)
- **Pin limit:** Max 10 per group (up from backlog's 3); reject with `BadRequestException` when full; no auto-bump
- **Pin order:** `pinnedAt DESC` (latest on top); no explicit `pinOrder` column — timestamp is the ordering key
- **Cross-domain post validation:** Call `PostService.getPostById()` via post-api interface to verify `post.groupId == groupId` AND `post.postType == GROUP_POST` before pinning; prevents admin of group A from pinning a post belonging to group B
- **No changes to Post table:** `GroupPinnedPost` is the sole source of pin state — its existence means a post is pinned
- **`pinnedBy` type:** `UUID` (consistent with `GroupMember.userId`, `Group.createdBy`, and all other cross-domain user refs — the backlog's `UUID` label turned out to be correct, despite an initial incorrect recommendation of `Long`)
- **`pinnedPosts` in `GroupResponse`:** Populated only in `getGroup()` (top 3, latest first); null in list endpoints to avoid N+1 queries
- **`unpinPost` is idempotent:** No error if the post isn't currently pinned
- **Deleted-post resilience:** Post fetch errors during pin list building are silently filtered (pin shows nothing) rather than failing the whole request
- **group-api gains `post-api` dependency:** Needed so `PinnedPostResponse` can embed `PostResponse` and `GroupResponse` can hold `List<PostResponse> pinnedPosts`; api-to-api dependency is within architecture rules
