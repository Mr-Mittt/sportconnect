## Decisions made
- **A6 batching strategy:** rather than a 1-for-1 swap of `userRepository.findById` → `userService.getUserById` (which the ticket originally proposed), added a new batch method `UserService.getUsersByIds(List<UUID>) -> Map<UUID, UserResponse>` and used it at all 5 `GroupServiceImpl` call sites. This preserves the exact old fallback semantics (`orElse("Unknown User")`, no `isActive` filter, no exception on miss) with no exception path at all — `getUserById` throws on missing/inactive users, which would have silently changed behavior.
- Consolidated 3 of those 5 call sites from 2–3 individual lookups into 1 batched call each (`mapToGroupMemberResponse`, `mapToJoinRequestResponse`, `mapToGroupInvitationResponse`).
- Enabled the friends-only invite gate in `createInvitation()` (`userFriendService.areFriends()`), previously stubbed pending U1 (friendship system), which is now done.
- Removed `group-impl`'s improper `user-impl` Gradle dependency (swapped for `user-api`) and its now-unnecessary JTS test dependency (verified tests still compile without it first, per the ticket's own instruction not to remove speculatively).
- **N+1 in `getGroupMembers` (and 3 sibling paginated methods) is a known pre-existing issue, not introduced by A6** — logged as new backlog ticket **A7** rather than fixed inline, since fixing it touches 4 methods beyond A6's stated "no behavior change" scope.
- **Process change:** N+1 checking is now a standing rule in `CLAUDE.md` (Java code style) and an explicit Verify-phase step in both `implement.md` and `workon.md`, so future tickets check for the per-item-lookup-in-a-loop pattern before being marked done.
