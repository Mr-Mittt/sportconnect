## What we worked on

Picked up and completed ticket B5 (Group search & discovery) from the group MVP backlog. Extended `GET /api/groups/public` with keyword and sportId filters, introduced a new `GroupSearchResponse` DTO, and implemented two-tier sorting (member groups first). After the initial implementation, identified and fixed two N+1 query patterns by replacing them with a single LEFT JOIN + conditional `SUM(CASE WHEN ...)` aggregation and a batch creator name lookup — reducing queries per page from 2+2N to a flat 2.

## Decisions made

- **`keyword` matches `groupName` only** (not description) — simpler scope for MVP discovery.
- **New `GroupSearchResponse` DTO** — slim card shape; drops `currentUserRole`, `coverUrl`, `isActive`, `createdBy` UUID, `updatedAt`, `createdAt`; adds `isMember: boolean`. `GroupResponse` is unchanged and continues to be used on single-group and user-groups endpoints.
- **Sort order** — member groups first (alphabetical by name), then non-member groups (most members first); applied in-memory within the fetched page.
- **Extend `GET /api/groups/public`** — no new endpoint; same URL gains optional `keyword` and existing `sportId` params. `@AuthenticationPrincipal` added to controller for the isMember check; null-safe (unauthenticated requests route to the anonymous query).
- **Two repository methods instead of one** — `searchPublicGroupsWithCounts` (authenticated; includes `SUM(CASE WHEN gm.userId = :userId ...)`) and `searchPublicGroupsAnon` (anonymous; omits the SUM to avoid passing null into a JPQL `=` comparison). Both use explicit `countQuery` because Spring Data cannot auto-derive a count from a GROUP BY query.
- **LEFT JOIN + conditional SUM for isMember** — a naive double LEFT JOIN causes row multiplication (`gm_user` joins on `g.id`, so every expanded member row matches the user's row; COUNT returns the full member count, not 0/1). `SUM(CASE WHEN gm.userId = :userId THEN 1 ELSE 0 END)` avoids this by aggregating conditionally over the single join's expanded rows.
- **Batch creator name fetch** — replaced N × `userRepository.findById` with a single `userRepository.findAllById(creatorIds)` call, collecting results into a `Map<UUID, String>` for O(1) lookup per group.
- **Backend only** — no frontend changes this session.
