## What we worked on

Implemented B3 · Redis Like / Comment / Reply Counters from the post-impl MVP backlog. Replaced live `COUNT(*)` DB queries in `mapToResponse()` with Redis atomic counters, extended scope to also cover comment count per post and reply count per comment, and added a new `replyCount` field to `CommentResponse`. After initial implementation, identified and fixed a race condition in the write path using a Lua script.

## Decisions made

- **`StringRedisTemplate` chosen over `RedisTemplate<String, Long>`**: Spring Boot auto-configures it with no config class needed; values stored as strings and parsed with `Long.parseLong()`. No custom serializer required.
- **Extended scope confirmed**: 4 Redis keys total — `post:{id}:likes`, `post:{id}:comments`, `comment:{id}:likes`, `comment:{id}:replies`.
- **`replyCount` added to `CommentResponse`** alongside the existing `replies` list — `replyCount` is the fast Redis-backed integer for display; `replies` remains the full nested list for detail views.
- **Lua `INCR_IF_EXISTS` / `DECR_IF_EXISTS` scripts for the write path**: Initial implementation used blind `INCR`/`DECR`. This had a race condition: if the Redis key was evicted and a write (like) happened before any read re-seeded it, `INCR` would create the key at `"1"` — wrong, and invisible to the cache-miss path since it's not null. Fixed with a Lua script that checks `EXISTS` before `INCR`/`DECR`. If the key is absent the script is a no-op; the next read hits a cache miss, queries DB for the accurate count, and seeds Redis correctly. The Lua script is atomic — no TOCTOU race between `EXISTS` and `INCR`.
- **Clamp-at-zero on read**: `Math.max(0L, Long.parseLong(val))` applied on every Redis read as a defensive guard. Service-level guards (duplicate like check, "you haven't liked this" check) prevent counters legitimately going negative.
- **`getCount()` helper copied into both services** (not extracted to a shared utility): services are independent and MVP scope doesn't warrant a shared Redis utility class.
- **No Liquibase migration needed**: all changes are in-memory/service layer only.
- **DB fetch inside mutations rejected**: fetching `COUNT(*)` from DB on every like/unlike would defeat the purpose of caching — same DB cost as the original problem. The Lua script is the correct solution.
