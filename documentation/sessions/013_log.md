## What we worked on

Implemented ticket B5 — Hashtag Service — for the post module MVP backlog. This covered auto-extraction of `#word` patterns from post content, per-hashtag usage count tracking (increment on create, decrement on delete), and three public discovery endpoints (trending, autocomplete suggest, posts by hashtag). One design discussion was held around storage normalization before implementation began.

## Decisions made

- **Lowercase normalization at write time** — tags are stored as lowercase in the `hashtags` table (e.g. `#Football` → `football`). Exact lookups use `=` (fast plain btree), no `ILIKE`/`LOWER()` at query time. Consistent with Instagram/Twitter's approach.
- **`varchar_pattern_ops` index still added (V022)** — needed for the prefix LIKE query in the suggest endpoint (`WHERE tag LIKE 'foo%'`). The existing plain btree index doesn't support this efficiently on UTF-8 collation databases.
- **One `save()` per hashtag** — new hashtags are built with `usageCount(1)` directly via the builder; existing ones are incremented then saved once. Avoids redundant double-save.
- **`getPostsByHashtag` placed on `PostService`** (not `HashtagService`) — avoids a circular dependency where `HashtagService` would need `PostService`'s private `mapToResponse` logic.
- **`decrementHashtagsForPost` decrements but does not delete `PostHashtag` rows** — soft-delete pattern; keeps data integrity. Counts are decremented so the post no longer inflates trending.
- **Visibility in hashtag post search** — `USER_FEED + public` OR `GROUP_POST in caller's member groups`. Requires new `GroupService.getGroupIdsForMember()` method. Unauthenticated callers get public-only results (empty group list → sentinel `-1L` for JPQL IN safety).
- **`orphanRemoval` is safe** — `Post.hashtags` collection is never loaded in `PostServiceImpl`. Hibernate only applies orphan removal when the collection is initialized and entities are removed from it. Direct `PostHashtagRepository.save()` is safe.
