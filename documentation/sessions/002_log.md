## What we worked on

Picked up and completed ticket B2 (Group–Sport Association + UserSpace) from the group MVP backlog. This wired a required `sportId` to every group, enforced that the creator holds an active `UserSportProfile` for that sport (cross-domain check through the `sport-api` interface), added an optional `?sportId=` filter to `getPublicGroups`, and enforced a max-3 active sport profiles limit per user.

## Decisions made

- **UserSpace = UserSportProfile (reuse, not a new entity):** `UserSportProfile` already represented the "user's space per sport" concept with a unique `userId + sportId` constraint. Creating a separate `UserSpace` entity would have duplicated data unnecessarily.
- **Nullable DB column for migration safety:** `sport_id BIGINT` was added as nullable to avoid breaking pre-existing dev rows; enforcement is at the DTO layer (`@NotNull`), which is the correct boundary for incremental schema evolution.
- **`hasProfileForSport` method added to `UserSportProfileService` interface:** Preferred over catching `ResourceNotFoundException` from `getUserProfileForSport` — clean boolean signal, avoids exception-as-control-flow.
- **Max-3 sport profiles enforced in `createProfile`:** Added count check before the duplicate check in `UserSportProfileServiceImpl`.
- **Registration flow wiring is out of scope for B2:** Users create sport profiles separately via existing endpoints; wiring into registration is a separate ticket.
- **Pre-existing Spock test over-strict mock counts fixed:** Six tests used `1 *` for interactions actually invoked 2 times (role checks + `mapToGroupResponse` path); changed to `_ *` to reflect real call patterns without losing correctness guarantees.
