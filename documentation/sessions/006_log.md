## Decisions made

- **Invitation gating changed from follow → friend check:** The B1 invite guard will require a bidirectional friendship (not just a follow). Friend check is stubbed pending U1 implementation.
- **Friend check stubbed in B1:** Rather than block B1 on U1, a `// TODO: stub` comment marks the guard site in `createInvitation`. U1 will be a separate ticket.
- **Explicit friendship system (U1) lives in user-impl:** `FriendRequest` + `Friendship` entities owned by the user domain; cross-domain callers use `UserFriendService.areFriends()` via `user-api` interface only.
- **Duplicate pending invite → silent 200:** Returns existing invitation object rather than an error, to avoid spamming the inviter.
- **Already-a-member → 400 error:** Inviter should know clearly why their invite had no effect.
- **Notifications stubbed:** `// TODO: notify` comment left at `approveInvitation` call site; first entry logged in new `documentation/md/ADR.md` under "In-app notification".
- **No wildcard imports rule established:** Every Java import must name the exact class. Rule added to `CLAUDE.md` under `Architecture > Java code style` and saved to memory.
- **`GroupInvitation` stays in group-impl (not user-impl):** The invitation lifecycle is a group membership artifact, not a user inbox concept — consistent with `GroupJoinRequest` precedent.
