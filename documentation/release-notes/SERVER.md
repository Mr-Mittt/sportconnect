# server release notes

One section per released version, newest first. Write your lines under `## Unreleased` in the same PR as the change
(rules and format: [README.md](README.md)). `/release server` checks this block, turns it into the next version's section,
writes a fresh template and uses the section as the release PR description. Versions before this file existed only say so; the history is in git.

## Unreleased

### Changes
- Sessions carry `maleSlots`, `femaleSlots` (informational open slots per gender), `gameMood` (1-10, required on create) and `feeNote`, on the create and update requests and on `SessionResponse` (SESSION-46).
- A session title is required again (SESSION-49): creating a session without one, or updating it to a blank one, is `400 SESSION_TITLE_REQUIRED`; the title is trimmed. Group auto-generated sessions are titled after the group in the owner's stored language (en `<group>'s session`, vi `Trận đấu của nhóm <group>`, English when none).
- `GET /api/notifications` no longer fails for the whole page when a referenced session has no title (SESSION-49); a session without a title is just left out of the title lookup.
- `PREPARING` is a real draft (SESSION-46): a session starts `PREPARING` unless location, fee and duration are all set; every field except sport and group is editable while `PREPARING`; `PUT /api/sessions/{id}` on any other status is now 409 `SESSION_NOT_PREPARING` (before, only location and fee were locked); the automatic `PREPARING` to `SCHEDULED` flip is gone and the host leaves the draft with the new `POST /api/sessions/{id}/schedule` (400 `SESSION_NOT_READY` lists what is missing). New error codes `SESSION_GENDER_SLOTS_EXCEED_OPEN` and `SESSION_NOT_READY`.
- Game logging, backend (SESSION-50): `GET /api/sessions/{id}/records`, `POST /api/sessions/{id}/records/changes` (one change set: add, update, delete; at most 50 operations and 64 KB). Allowed while the session is `ONGOING` or `COMPLETED` and no later than 24 hours after `scheduledEndAt`; open to group members of a group session and `JOINED` participants of a standalone one. The server stores each record as sent; it checks only access, status and window, that the player ids the request names are `JOINED` (they are not stored), and the sport limits. A bad record does not fail the change set: it comes back in `results` with `status: REJECTED` and its `errorCode` (`_INVALID`, `_TOO_LARGE`, `_PLAYER_NOT_JOINED`, `_LIMIT_REACHED`) and the valid ones are stored; only a malformed request (a missing or repeated ref or id, over 50 operations) is a 400. Concurrent changes never error: the later request wins, an update of a deleted record restores it under a new id. New codes `SESSION_RECORD_NOT_ALLOWED`, `_NOT_LOGGABLE`, `_WINDOW_CLOSED`, `_INVALID`, `_PLAYER_NOT_JOINED`, `_LIMIT_REACHED`, `_TOO_LARGE`.
- People search for the session thread (SESSION-GL-64): `GET /api/sessions/{id}/thread-people?q=&size=` returns the people who can see the thread (`JOINED`, `REQUESTED` and `INVITED` participants, then, for a group session, the group's other members) as `userId`, `fullName`, `avatarUrl`; same access as the thread (404 `SESSION_NOT_FOUND`, 403 `SESSION_FORBIDDEN`). `size` defaults to 5 and is cut to 20. No new error code.
- One name search for the whole app (SESSION-GL-64): a user is found by first and last name only, from the start of a name or of a later word of it, ignoring case and accents ("tuan" finds "Tuấn", "dang" finds "Đặng"); every typed word must match. `GET /api/users/search` follows the same rule, so it **no longer matches the username and no longer matches the middle of a word**; its response shape is unchanged. A user with neither a first nor a last name is not found by name.
- Group member search for tagging (B23): `GET /api/groups/{groupId}/members/search?q=&size=` returns the group's members whose first or last name matches (the same rule as `thread-people`: word-start, ignoring case and accents, every typed word must match) as `userId`, `fullName`, `avatarUrl`. Members only, any role: 404 `GROUP_NOT_FOUND` for a missing or deleted group, 403 `GROUP_MEMBER_REQUIRED` for anyone else, public or private. `size` defaults to 5 and is cut to 20. The caller can appear; a deactivated member never does. No new error code, no migration.
- Result changes tell the session (SESSION-GL-63): a records change set that saved at least one operation writes one system comment in the session thread ("{name} has updated the result") and notifies every `JOINED`, `REQUESTED` and `INVITED` participant except the actor (new routing key `session.record.changed`; unread ones fold into one notification per session, so a busy session does not flood anyone). A change set where nothing was saved writes neither.
- System entries carry a code (SESSION-GL-63): `CommentResponse` and `PostResponse` gain `systemCode` and `systemParams` (both null for a user's comment or post and for every entry written before this release); codes `SESSION_JOINED`, `SESSION_LEFT`, `SESSION_STARTED`, `SESSION_RECORDS_UPDATED` (session thread) and `GROUP_MEMBER_JOINED`, `GROUP_MEMBER_JOINED_INVITED` (the group welcome post). `content` still carries the English text, so a client that does not read the code shows what it showed before. Old entries are not backfilled.
- Sport result schema (SESSION-50): `GET /api/sports/{id}/result-schema` (members), `GET /api/sports/all/{id}/result-schema` and `PUT /api/sports/{id}/result-schema` (admin). The schema tells the client what a recorded result is and carries `maxRecords` (default 100, at most 500). Each record is capped at 4 KB. A sport with no schema has no result logging; no schema is seeded, so an admin must `PUT` one for a sport before its sessions can record results. Invalid limits are `400 SPORT_RESULT_SCHEMA_INVALID`.
- A joined participant can leave a session only until 15 minutes before it starts (SESSION-65): `DELETE /api/sessions/{id}/leave` is `409 SESSION_LEAVE_TOO_LATE` (with `errorParams.cutoffAt`) after that, in every session status (a cancelled one included) and for group sessions, and changes nothing. Declining an invitation and cancelling a join request are unaffected.
- A notification can carry a short text (NTF-8): `NotificationResponse` gains a nullable `message` (at most 500 characters). A `session.join_request.rejected` notification carries the host's reason for declining (it used to be dropped); a blank reason is no message, and a later rejection of the same session that merges into the unread notification replaces the text, or clears it when it has none. Every other notification type has `message: null`.
- Delete the read notifications (NTF-8): `DELETE /api/notifications/read` hard-deletes every read notification of the caller in one call and returns how many it removed (`0` when there is nothing read, so a repeat call is harmless). Unread notifications and other users' notifications are never touched, the unread count does not change, and there is no soft delete: a deleted notification is gone. There is no error code of its own (it only acts on the caller's own rows).
- A host edit of a `PREPARING` session tells the discussion thread what changed (SESSION-67): `PUT /api/sessions/{id}` writes one system comment per field whose value really changed (title, location, location note, start, duration, capacity, fee, fee note, auto approval, initial slots, male and female slots, game mood, and one comment without values for the sport attributes), in the same transaction, each with a `systemCode` (`SESSION_TITLE_CHANGED`, `SESSION_LOCATION_CHANGED`, ... `SESSION_ATTRIBUTES_CHANGED`) and string params `name` (the editor), `old` and `new` (empty = no value; the fee carries `oldFeeType`, `oldFeeAmountVnd`, `newFeeType`, `newFeeAmountVnd`). A request that re-sends the stored values writes nothing. The English `content` stays as the fallback. The comments are authored by the session's creator and do not send a comment notification; the existing `session.details.updated` notification is unchanged. No new endpoint, no error code, no migration.
- Share a session with friends (SESSION-66, CLIENT-SESSION-49): `POST /api/sessions/{id}/shares` with `{ "userIds": [...] }` (1 to 50). Any user can share a standalone session, in any status and whatever their own participation: each friend gets a notification "{name} shared {session} with you" (new routing key `session.share.created`, the sharer as actor), which opens the session. It is a share, not an invitation: no participant row is written, so the friend asks to join under the normal rules (host approval unless auto-approve). The answer is `{ sent, skipped }`; anyone who is not a friend (silently: no error, never notified), the caller's own id, repeated ids, friends already `JOINED`, `REQUESTED` or `INVITED`, and deactivated friends are skipped, all in `skipped`. Refusals: `403 SESSION_SHARE_NOT_ALLOWED` (a group session, for everyone), `404 SESSION_NOT_FOUND`. No migration, nothing on the box to change.
- A host can make a standalone session private (SESSION-69): `isPublic` on `POST /api/sessions` (omitted means `true`) and on `PUT /api/sessions/{id}` (only while `PREPARING`), and `isPublic` on every session answer. A private session is seen only by its creator and anyone holding a `JOINED`, `REQUESTED` or `INVITED` row: it is never listed in Discover, anyone else gets `403 SESSION_FORBIDDEN` on `GET /api/sessions/{id}`, on its players list and on `POST .../join`, and it cannot be shared (`403 SESSION_SHARE_NOT_ALLOWED`). Switching it keeps every existing participant. `isPublic` is ignored for a group session. A change is told in the session thread (new `systemCode` `SESSION_VISIBILITY_CHANGED`, `old` and `new` are `public` or `private`). **Behaviour change:** `GET /api/sessions/{id}/participants` now checks access like the detail (a group session's players, too: `403` for a non-member, `404` for a missing session; before, anyone with the id could read them). No migration, nothing on the box to change.
- A recurrence configuration names its chosen members (CLIENT-GROUP-SESSION-5): `GroupSessionRecurrenceResponse` gains `audienceMembers` (`[{ id, name, avatarUrl }]`, the chosen members of a `SPECIFIC` audience in the order they were picked, empty otherwise; a deactivated member keeps their real name, an id that no longer resolves is left out) **in place of `audienceUserIds`**, on `GET`, `POST` and `PUT .../recurrences`. **Behaviour change:** a client that reads `audienceUserIds` from a recurrence answer no longer finds it; the request field `audienceUserIds` (`POST`/`PUT` and session creation) is unchanged. The list resolves every row's members in one batch lookup.
- A recurrence configuration carries its location (CLIENT-GROUP-SESSION-4): `GroupSessionRecurrenceResponse` gains `location` (the same `LocationResponse` a session answer embeds: id, name, address, coordinates, sport; null when the configuration has no location or it is no longer available), on `GET`, `POST` and `PUT .../recurrences`. `locationId` stays, so a client that ignores the new field is unaffected. The list resolves all the locations in one batch lookup.
- A group member creates a group session (SESSION-GROUP-1): `POST /api/sessions` with a `groupId` is open to any member of the group (it was owner/admin only; a non-member now gets `403 SESSION_GROUP_MEMBER_REQUIRED`). The sport is always the group's, `isPublic` is false, `autoApprove` defaults to `true` for a group session, and the creator is `JOINED` like a standalone creator. New request fields `audience` (`ALL_MEMBERS` default or `SPECIFIC`) and `audienceUserIds` (members only, no cap; `400 SESSION_AUDIENCE_REQUIRED` / `SESSION_AUDIENCE_NOT_MEMBER`) decide who is notified (a notification, no `INVITED` row; everyone in the group can still see and join). Edit, schedule and cancel of a group session are open to its creator while still a member as well as to the group's owner and admins. Two new notifications, `session.group.created` (the audience, minus the creator) and `session.group.cancelled` (the audience and the players, minus the actor); a standalone cancel is still silent. Two sessions of a group may now start at the same instant (the unique key `(group_id, scheduled_start)` is dropped).
- A group's sessions by bucket (SESSION-GROUP-2; **replaced by SESSION-GROUP-12 below, so the `bucket` parameter is not in the release**): `GET /api/sessions/group/{groupId}` took an optional `bucket` (`ONGOING`, `SCHEDULED`, `PREPARING`, `HISTORY`; any letter case): `SCHEDULED` holds only `SCHEDULED` sessions (a `PREPARING` draft is its own bucket), `HISTORY` holds `COMPLETED` and `CANCELLED`; each bucket is ordered by start time, soonest first (`HISTORY`: newest first), whatever sort the caller sends. A value that is not one of the four is `400`. Without `bucket` the answer is unchanged (every status, the caller's own paging and sort). Still members only.
- Share a group session (SESSION-GROUP-3): `POST /api/sessions/{id}/shares` now accepts a **group** session (it answered `403 SESSION_SHARE_NOT_ALLOWED` for every group session before). The caller must be a member of the group (a non-member gets `403 SESSION_GROUP_MEMBER_REQUIRED`; an inactive group is `404`); the recipients are the group's other members, not the caller's friends; anyone outside the group, already in the session, repeated or deactivated is skipped and counted, as before; at most 50 per call; the same `session.share.created` notification, no participant row. `SESSION_SHARE_NOT_ALLOWED` now means only a private standalone session.
- Group session settings and recurrence configurations (SESSION-GROUP-4), configuration only (no session is generated from it yet, SESSION-GROUP-5): `GET/PUT /api/sessions/group/{groupId}/settings` (`{ enabled, mode }`, `WEEKLY` or `MONTHLY`) and `GET/POST/PUT/DELETE /api/sessions/group/{groupId}/recurrences[/{id}]`. A configuration is a wall-clock slot (a weekday 1-7, or a day of the month 1-31, and a local start time), a duration, a location of the group's sport, who is notified (all members or chosen members), the fee, game mood and session attributes; with no location, duration or fixed-fee amount it is saved as a draft (`draft`, `missing` in the answer). At most 5 per group, mode and day (`409 SESSION_RECURRENCE_DAY_LIMIT`). Any member reads; the group's owner and admins write. Each change (add, replace, delete, generation on or off, mode switched) also posts a short note in the group's feed, authored as the current owner, with the new `SystemCode` values `GROUP_SESSION_RECURRENCE_ADDED`, `_UPDATED`, `_DELETED`, `GROUP_SESSION_GENERATION_ON`, `_OFF` and `GROUP_SESSION_MODE_CHANGED`. New codes `SESSION_RECURRENCE_DAY_INVALID`, `SESSION_RECURRENCE_START_REQUIRED`, `SESSION_RECURRENCE_DAY_LIMIT`, `SESSION_RECURRENCE_NOT_FOUND`. The old single weekly rule (`GET/PUT /api/groups/{id}/recurrence`) still works and is still what generates sessions until SESSION-GROUP-5; GROUP-1 then removes it.
- Regular group sessions are generated (SESSION-GROUP-5): with generation on, the group's complete recurrence configurations of its current mode produce real sessions, read as wall-clock slots in the location's timezone (a monthly day a month lacks is skipped). A queue holds the slots still to generate and is drained in order; a failed slot is retried (1, 5, 15, 60 minutes, then `FAILED`). It is fed by the server start (down-time recovery: each group's nearest day), by the last regular session of a day completing or being cancelled (the next nearest day, never while generation is off, never by a custom session), and by an owner or admin switching generation on, switching the mode, or adding or editing a configuration (today's slots that have not ended are generated at once, as `SCHEDULED` or `ONGOING`). A generated session is the owner's, auto-approve on, not public, carries the configuration's location, duration, fee, mood, attributes and audience (the audience is notified with `session.group.created`, the owner excluded) and has `recurrence_id` and `occurrence_date`. **The old single weekly rule no longer generates anything**: updating `PUT /api/groups/{id}/recurrence` or the group's auto-generate flag stops creating sessions (the endpoints still answer until GROUP-1 removes them), and `SessionService.generateNextOccurrenceForGroup` is gone. SESSION-41 (no retry for a failed generation) is closed by this.
- The old single weekly recurrence rule is removed (GROUP-1): `GET` and `PUT /api/groups/{id}/recurrence` are gone, `GroupSettingsResponse` and `UpdateGroupSettingsRequest` no longer carry `autoGenerateSessions` (a client that still sends it is not refused, the field is ignored), `GroupService` loses `getGroupRecurrence`, `updateGroupRecurrence`, `getGroupsWithAutoGenerateSessionsEnabled` and `getGroupRecurrenceConfigsByGroupIds`, and group-impl no longer depends on the session or location modules. Groups that had a rule lose it (nothing generated from it since SESSION-GROUP-5); the owner sets up configurations in the group's session settings. `GROUP_RECURRENCE_LOCATION_SPORT_MISMATCH` stays (now returned by the new configuration endpoints).
- Cancelling the scheduled regular sessions when the rules change (SESSION-GROUP-6): `GET /api/sessions/group/{groupId}/regular-sessions/count?scope=ALL|RECURRENCE&recurrenceId=` (owner or admin) returns how many `SCHEDULED` or `PREPARING` regular sessions the group has (or one configuration generated); `PUT /api/sessions/group/{groupId}/settings` accepts `cancelScheduled` and, when it turns generation off or switches the mode, also cancels all of the group's scheduled regular sessions (`cancelledSessions` in the answer); `DELETE /api/sessions/group/{groupId}/recurrences/{id}?cancelScheduled=true` cancels the ones that configuration generated first (the answer's `count` is how many; the delete used to answer with no body data). A rule-change cancel tells the session's audience and its players (`session.group.cancelled`, the person who did it excluded), never touches an `ONGOING` or a custom session, and never queues a replacement. Without `cancelScheduled` the sessions are left there, as before.
- Review corrections of the group-session chain (SESSION-GROUP-10): the chosen members of a `SPECIFIC` audience are stored on the session and on the recurrence (`group_audience_user_ids`, `audience_user_ids`, one text column of comma-separated ids; no member tables) and the API is unchanged; a regular-session slot that is skipped is `IGNORED` with a reason, and one whose date no longer falls on its recurrence's day (an edit moved the weekday) is ignored instead of generating a session on the old day; two planners or two runners (two server instances, or two threads of one) no longer collide on the generation queue (a lost race is logged at INFO as `queue race absorbed`); regular sessions are now generated by one background worker thread per instance, so saving a configuration or cancelling a session answers at once and the session appears moments later (a 60-second tick also retries failed slots on their backoff and picks up slots an instance left behind).

- Group sessions by status (SESSION-GROUP-12): `GET /api/sessions/group/{groupId}/today`, `/later`, `/history/dates` and `/history` (members only, `403 SESSION_GROUP_MEMBER_REQUIRED` otherwise), each with a required `viewerZoneId` (the zone "today" and the dates are read in) and a repeatable `status`. `/today`: sessions whose playing time overlaps today (a session that started yesterday and ends today or tomorrow counts), ONGOING, SCHEDULED, PREPARING, COMPLETED, CANCELLED then start. `/later`: from tomorrow on (PREPARING, SCHEDULED, CANCELLED). `/history/dates`: the end dates (the end, or the start when a session has no end) of finished sessions in a 30-day window (`days`, at most 90) ending the day before `before`, with counts, `hasMore` and `nextBefore`; `/history?date=`: one date's sessions, newest end first. The `bucket` parameter of `GET /api/sessions/group/{groupId}` is removed (the plain list is unchanged).
- A cancelled session always has an end time (SESSION-GROUP-12): cancelling (by the host, by the automatic cancel of an unprepared draft, or by a regular-session rule change) sets the end to the start when the session had no end; existing cancelled sessions are backfilled.
- A group left, a group session gone from your lists (SESSION-GROUP-12): `GET /api/sessions/upcoming`, `/requested` and `/history` (and its date counts) show a group session only while you are a member of that active group; before, a session you had joined stayed listed after you left the group (and opened as "no access"). Rejoining brings them back.
- Admin import of finished group sessions (SESSION-70): `POST /api/sessions/import/preview` and `POST /api/sessions/import` (role `ADMIN`, granted in Keycloak; a plain user gets `403`). The request names a group, a location, an optional host and a list of sessions (title, local date, start and end time, games as winners and losers by first name). The preview matches the names against the group's active members, lists the ones it cannot settle and returns the group's active members (`members`, to settle them with); the apply refuses (`409 SESSION_IMPORT_UNRESOLVED_NAMES`) until an alias settles each, then creates every session `COMPLETED` with its players and one record per game, one transaction per session, and skips a session already there (same group, start and title). It sends no notification and writes no system comment. New error codes `SESSION_IMPORT_INVALID`, `SESSION_IMPORT_UNRESOLVED_NAMES`, `SESSION_IMPORT_HOST_NOT_MEMBER`, `SESSION_IMPORT_ALIAS_NOT_MEMBER`, `SESSION_IMPORT_NOT_FINISHED` (the client copy is CLIENT-ADMIN-IMPORT-1).
- A venue carries its country and region (LOC-5): `LocationResponse` (and so every embedded location in session and group answers) gains the nullable `countryId` and `regionId`, derived offline from the coordinates when a location is created (`POST /api/locations`) and, for existing venues, once at start-up. A venue with no coordinates, in open water, or in a country that is not seeded (only Vietnam is; regions exist only for Vietnam) keeps both null; a lookup failure never fails the save. No endpoint changes; a client that ignores the two fields is unaffected.
- Ranking games (SESSION-72): a participant who joined a session proposes one of its games as a ranking game, and the players named in it confirm it. `POST /api/sessions/{id}/records/{recordId}/ranking-request` and `POST .../verify` (both return the record), and every record in `GET /api/sessions/{id}/records` and in the change-set answer gains `ranking` (`status` `NORMAL`, `PROPOSED` or `VERIFIED`, `requestedBy`, `confirmedBy`). Games can now be logged in a `SCHEDULED` session as well as an `ONGOING` or `COMPLETED` one (until 24 hours after it ends), with no score yet, so the players can set them up before the start; `SESSION_RECORD_NOT_LOGGABLE` now means not scheduled, ongoing or completed. Editing a game changes its revision: confirmations of the old content stop counting and the other players are asked again. New error codes: `SESSION_RECORD_NOT_FOUND`, `SESSION_RECORD_RANKING_PROPOSER_NOT_JOINED`, `SESSION_RECORD_RANKING_NOT_AVAILABLE`, `SESSION_RECORD_RANKING_NOT_RANKABLE` (with `errorParams.reason`), `SESSION_RECORD_VERIFY_NOT_A_PLAYER`, `SESSION_RECORD_NOT_PROPOSED`. New notification routing key `session.record.verification_requested` (a player asked to confirm a game); a client that does not know it shows the generic text. Nothing is counted into statistics yet (SESSION-53).
- Statistics engine (SESSION-53; it is read through the SESSION-73 endpoints below, the boards are SESSION-54): a background job counts every completed session of a sport that has **statistics switched on** once 24 hours have passed since it ended (its start when it has no end), checking every 5 minutes, one session at a time, on its own thread. **A sport has a new switch, `statisticsEnabled` (off by default; an admin sets it with `PUT /api/sports/{sportId}`, and `SportResponse`, `CreateSportRequest` and `UpdateSportRequest` carry the optional field), and the job counts only the stats the sport's `record.scoreboard.columns` list, the same list the client's scoreboard reads (`games`, `wins`, `losses`, `winRate`, `winDiff`, `scoreFor`, `scoreAgainst`, `scoreDiff`); a sport that lists none collects nothing, there are no defaults.** The job reads the session's games through the sport's result schema, ignores the invalid ones, the ones with no score and any naming a player who is no longer `JOINED`, and updates the per-player and per-group-member statistics (the listed stats only, a history of the last 500 games, and, when the sport's `record.scoreboard.groupBy` is `PARTNER` or `TEAM`, counters for each partner or team). For a group session of a `PARTNER` sport it also keeps the group's head-to-head of its pairs (a new `group_stats` document per group and sport, the latest 5,000 matchups). It writes **no leaderboard rows**: it only marks the boards it touched dirty, and SESSION-54's nightly job will build and rank them. A ranking game (proposed and confirmed by every player, SESSION-72) also counts at the venue's region and country (LOC-5) for every player, wherever they live; a normal game counts for the players and the group only. A sport's result schema may carry `record.scoreboard.groupBy`, `record.ranking` (sort keys, at most three, no default order, and minimum games) and `record.data.allowDraws`; the first build's `record.statistics` block is not read, and a schema the server cannot use never stops a session being counted. **Ranking games can now be proposed and confirmed only for a sport that has the switch on** (otherwise `409 SESSION_RECORD_RANKING_NOT_AVAILABLE`, an existing code). A session whose counting fails is retried after 15 minutes, four attempts in all, then once every 6 hours. After a sport is switched on, its completed sessions older than 24 hours are counted in the usual bounded passes.
- Leaderboards, the engine side (SESSION-54, slice A; nothing reads a board yet): after a ranking game is counted, a nightly job (00:05 `Asia/Ho_Chi_Minh`, `app.stats.ranking.cron`, and a 30-minute retry tick for failed boards) builds the **region, country and group boards** of every sport that has statistics on (a group only while its own switch is on): one board per kind, `SINGLE` (a player) and `PARTNER` (a pair), each a ranked tree in `leaderboard_entry` with the rank derived, the previous rank kept and ties sharing a place. **How a board is ordered is a server-only rule an admin sets** (`PUT /api/admin/sessions/ranking/rules/{sportId}`, role `ADMIN`; `GET` lists them, `DELETE` removes one): a list of up to four keys, each with its own direction, a key being a stat of the sport (`wins`, `winRate`, ...) or a weighted sum of stats, plus the preconditions a player or pair must all meet to be listed (a list such as `games >= 5` and `wins >= 2`); one rule per sport, or per country (it then covers that country's regions and its country board). **A sport with no rule has no board.** The country's pair board is the merge of its region boards, a pair at its best region only, at most 1,000 entries for each region board merged (`app.stats.ranking.country-slots-per-region`). `POST /api/admin/sessions/ranking/{sportId}/rebuild` rebuilds every board of a sport from the players' statistics and `POST /api/admin/sessions/ranking/run` runs the pass now. The read endpoints and the group refresh are the next slice (SESSION-54 part B), so there is no client change yet.
- Leaderboards, the reads, the group's own sort list and the manual refresh (SESSION-54, slice B): `GET /api/sessions/group/{groupId}/leaderboard` (members), `GET /api/leaderboards/regions/{regionId}` and `/countries/{countryId}` (any signed-in user, `sportId` required), each with `kind` SINGLE or PARTNER, a cursor and the caller's own place; a deactivated player (and, on a group board, a member who left) is not shown; a sport with statistics off answers 404 like an unknown sport. A group owner or admin sets the group's own sort list (`PUT /api/sessions/group/{groupId}/leaderboard/rules`; the group board follows it, the sport's rule otherwise) and may rebuild the group's board by hand (`POST /api/sessions/group/{groupId}/leaderboard/refresh`, at most once an hour: 429 `SESSION_RANKING_COOLDOWN`). New optional properties: `app.stats.ranking.refresh-cooldown-minutes` (60) and `app.stats.ranking.read-cache-boards` (8 boards kept in memory per instance). The development-only `ADMIN` group scope of the test trigger is not part of this release.

### Applied automatically
- Statistics read API (SESSION-73), four new endpoints for a signed-in active account: `GET /api/stats/me?sportId=` (my statistics in a sport: the columns of the sport's `record.scoreboard.columns`, totals for all, ranking and normal games, my pairs or partners one page at a time with `page` and `size`, and my ranking games per region and country), `GET /api/stats/me/games?sportId=` (my counted games, newest first, paged by a cursor), `GET /api/sessions/group/{groupId}/stats` (one totals row per active member, members only; the sport is the group's, no `sportId` is sent) and `GET /api/sessions/group/{groupId}/stats/members/{userId}` (one member's totals and pairs or partners; any member of the group may open it, and a member who left is still shown). While a sport's statistics switch is off these show no columns and no values. Response shapes: section 9 of `documentation/md/STATISTICS_JSONB_REFERENCE.md`.
- A group's switch for its statistics and leaderboard (SESSION-78): the group's owner or an admin turns the group's member statistics, head-to-head and leaderboard on or off with the group's session settings (`GET/PUT /api/sessions/group/{groupId}/settings` gain an optional `statisticsEnabled`, any member reads it, only an owner or admin writes it; a change writes a group post, `GROUP_STATISTICS_ON` or `GROUP_STATISTICS_OFF`, and sends no push notification). **It is off for every group, so after the deploy no group's member statistics are counted until its owner or an admin switches it on.** The players' own statistics are not affected. - Game outcomes follow the score (SESSION-80): in the statistics and in ranking games the team with the higher score wins whichever team is named first (it used to be the first team, and a game the first team did not win was ignored). **A game with no score now counts, as a win for the first team** (it used to be ignored as `NO_SCORE`), with no score numbers. ## 0.2.0 — 2026-11-09

### Changes
- Roles come from the Keycloak access token (`realm_access.roles`, only `USER` and `ADMIN`) instead of our `user_roles` table (A37). The sign-in, refresh and `GET /api/users/me` responses still return `roles`, now taken from the token. A user the token gives no `USER` gets 403 on authenticated endpoints; deactivation is unchanged (still refused within 60 s by the database gate, even with a valid `ADMIN` token).
- Provisioning no longer attaches a role to a new user (A37).
- The `roles` and `user_roles` tables, the `Role` entity and `UserService.getUserRoles` are removed (U27, migration `V084`). Nothing read the tables after A37; this release ships both together.

### Applied automatically
- `V084__drop_roles_and_user_roles.sql` drops `user_roles` and `roles` when the server starts (U27). It cannot be undone by Liquibase and a restore of a dump taken after it does not bring the tables back.
- The Redis entry `user:access-state:{id}` shrinks from `1|USER,ADMIN` to `1` or `0`; entries cached by the previous release are still read for their 60 s TTL, so nothing needs flushing (A37).

### Manual actions on the box
- Before this release is deployed: box `0.2.0` or later is installed (`sportconnect-setup`), `apply-realm-production.sh apply` and `check` have run (all lines `ok`; they read the secret files, so run `eval "$(bash ~/sportconnect/infra/oracle/scripts/fetch-secrets.sh)"` first and `bash ~/sportconnect/infra/oracle/scripts/fetch-secrets.sh --clean` after), and `ADMIN` is granted in the Keycloak console to every current admin (INFRA-25). Without that, every user gets 403 until their next token refresh and nobody can reach `/admin`.
- Before the deploy, on the box, with the old server still running (U27): export who holds ADMIN today and dump the two tables, because the migration drops them and the dump is the only way back:
  `docker exec sportconnect-dev-postgres-1 psql -U postgres -d sportconnect_dev -c "select u.id, u.email from users u join user_roles ur on ur.user_id = u.id join roles r on r.id = ur.role_id where r.name = 'ADMIN'"` (keep the output; grant ADMIN in Keycloak to each of those people), then
  `docker exec sportconnect-dev-postgres-1 pg_dump -U postgres -d sportconnect_dev -t roles -t user_roles > roles-before-u27.sql` and keep the file off the box.
- After the deploy: sign in, open `/admin` as an admin (a refresh may be needed), and confirm a plain user is redirected.

### Rollback
- Going back is not a plain redeploy any more (U27). The previous server release (0.1.2) loads `user_roles` for every user, so against this release's database it fails on the first authenticated request. To go back: redeploy 0.1.2, then restore the two tables from `roles-before-u27.sql` (`docker exec -i sportconnect-dev-postgres-1 psql -U postgres -d sportconnect_dev < roles-before-u27.sql`, which recreates `roles` and `user_roles` with their rows; the dump has no data in any other table). A full database restore from the box backup also works and brings the tables back.
- The Keycloak roles are additive and need no undo.

### Depends on
- box >= 0.2.0
