# A37 · Roles come from the Keycloak token (`realm_access.roles`)

**Status:** `DONE` (2026-11-10, implemented and verified locally; the production rollout order is INFRA-25 then the server release, in the release notes)
**Type:** Enhancement (Architecture)
**Depends on:** INFRA-24 (release notes), INFRA-25 (the production realm has the roles first)
**Filed:** 2026-11-09, `/feature` session "Move roles to Keycloak": roles lived in our `roles` and `user_roles` tables and `ADMIN` could only be granted by a manual insert; Keycloak should own them.

`JwtAuthenticationFilter` builds `ROLE_<name>` authorities from the verified token's `realm_access.roles` (only `USER` and `ADMIN` are kept). The per-request gate still asks `UserService.getAccessState` whether the user exists and is active, so deactivation is unchanged; `UserAccessState` becomes `UserAccessState(isActive)` and the Redis value `1`/`0` (the decoder still reads the old `1|USER,ADMIN` for its 60 s TTL). The callback and refresh responses and `GET /api/users/me` return `roles` from the token. Provisioning stops attaching `USER`. Realm roles `USER` and `ADMIN` plus `USER` as the default role are created by `infra/scripts/realm-roles.mjs` (api and file modes, mirrored into `sportconnect-realm.json`) with `apply-realm-roles.sh` and `verify-realm-roles.mjs`. A token without `USER` gets 403 until its next refresh (up to 5 minutes); a revoked role works until the access token expires (accepted).


**Local dev realm (added 2026-11-10, at INFRA-25's close):** the local Compose Keycloak (`sportconnect-dev-keycloak-1`) has no `USER` or `ADMIN` role today (checked read-only 2026-11-10), and INFRA-25 deliberately changes only the production box. So `apply-realm-roles.sh` must also leave every **existing local user** with `USER`: besides creating the roles and putting `USER` in the realm default role, it gives `USER` directly to any real user whose effective roles still lack it (an account without the default role), prints a `users: N checked, A already had USER, B fixed, C failed` line and exits 1 on a failure. Reuse the logic of `infra/oracle/scripts/set-realm-roles.sh` (INFRA-25) rather than writing a second version; a fresh local realm imported from the realm file already has the roles, and a long-lived volume gets them from this script. `verify-realm-roles.mjs` checks the roles, the default-role entry and that no real local user lacks `USER`. `ADMIN` is created empty: to try `/admin` locally, grant it to your own user in the console (`http://localhost:8081`, admin/admin) and refresh.

**Census:** `UserAccessState` and its specs, `getUserRoles`, `UserResponse.roles`, the Redis key row in `REDIS_KEYS.md`, `BaseIT`/`TestKeycloak` and 13 ITs. The client keeps receiving `roles: string[]` (compatible as-is). Chat reads no roles.

**Tests:** the local backfill (a user without the default role is fixed, a second run changes nothing); claim to authorities, no claim, unknown names ignored, a deactivated user with a valid ADMIN token refused, a DB-only role grants nothing, USER 200 / ADMIN-endpoint 403, callback roles equal token roles, realm script idempotence.

**Out of scope:** client roles, VENDOR and GROUP_OWNER, a role-management UI, faster revocation, a DB fallback, dropping the tables (U27).

## Implementation summary (2026-11-10)

**Built** (branch `feature/a37-roles-from-keycloak-token`). `TokenRoles.of(jwt)` (auth-impl) reads `realm_access.roles` and keeps only `USER` and `ADMIN` (sorted, deduplicated; a missing or odd claim is "no roles", never an error). `JwtAuthenticationFilter` still refuses an unprovisioned or deactivated user first (the database gate), then builds `ROLE_<name>` from `TokenRoles`. `AuthServiceImpl.sessionOf` (callback, reactivate, refresh) returns `user.roles` from the verified access token; `UserController` `GET /me` and `PUT /{id}/profile` set `roles` from the request's authorities; `JwtTokenServiceImpl.getAuthoritiesFromToken` returns the same roles (it was hard-coded empty). `UserAccessState` is now `(isActive)`; `getAccessState` stops loading roles; the Redis entry is `1`/`0` and the decoder still reads the old `1|USER,ADMIN` for its 60 s TTL; provisioning attaches no role; `toUserResponse` leaves `roles` empty. The tables, `Role`, `User.roles` and `getUserRoles` stay (documented as legacy) until U27. Realm: `infra/scripts/realm-roles.mjs` (`api` and `file`), `apply-realm-roles.sh`, `verify-realm-roles.mjs`; `sportconnect-realm.json` now has the roles and the default-role entry. Docs: `auth-impl` and `user-impl` `CLAUDE.md`, `REDIS_KEYS.md`, root `CLAUDE.md` (realm-change list, an A37 lifecycle update), `PORTS.md` (8095), `SERVER.md` release notes.

**Key decisions and findings.** (1) The gate keeps the database for `isActive` only: Keycloak knows nothing of our deactivation, so a deactivated user is still refused even with a valid ADMIN token (tested). (2) Keycloak 26.4 **ignores `defaultRole.composites` on import**. The realm file needs the default role as a `roles.realm` entry with its members (and the two built-in roles listed there too, or the import stops with "Unable to find composite realm role: uma_authorization") **plus** a `defaultRole` pointer; with only the entry Keycloak builds a second default role (`default-roles-sportconnect-1`) and new users never get USER. `file` mode writes exactly that and a fresh Keycloak was proven to import it. (3) The real `sportconnect-web` client's token is checked through Keycloak's "evaluate" endpoint (`verify-realm-roles.mjs`), since direct grants are off for that client. (4) The tests no longer write roles to the database: `BaseIT.createUserWithRoles` records them and `bearer(id)` puts them in the token; `bearerFor(id, roles...)` is for users a test builds by hand (six ITs). A dedicated test proves a role held only in the database grants nothing.

**Divergences from the approved plan:** none in behaviour. The test for the dev tooling is its own file, `infra/scripts/test-realm-roles-dev.sh` (throwaway Keycloak on :8095).

**Tests** (my own runs, development computer): `./gradlew :server:test :modules:auth:auth-impl:test :modules:user:user-impl:test :modules:notification:notification-impl:test` all green (697 server tests). New or changed: `JwtAuthenticationFilterSpec` (claim to authorities, bad shapes, unknown names, deactivated with ADMIN), `AuthServiceImplSpec` (session and refresh roles from the token, not the entity), `UserAccessStateSpec` (cache formats incl. the old one), `UserProvisioningSpec` (no role attached), `JwtTokenServiceImplSpec`, `KeycloakResourceServerIntegrationTest` (20: USER 200 and admin endpoint 403, ADMIN allowed, no roles 403, VENDOR and built-ins grant nothing, a database-only ADMIN grants nothing, deactivated with ADMIN refused, `/me` shows the token roles), `KeycloakCallbackIntegrationTest` (the session shows the token roles). `test-realm-roles-dev.sh`: 31 passed (api on a pre-A37 realm, the local backfill, idempotence, file mode, the committed realm file, a fresh import, the web client token). **Mutation check:** with `TokenRoles.of` forced to return `USER`, 11 unit cases and 5 integration cases fail; restored byte for byte.

**Not run:** a browser sign-in against the local Keycloak (the local realm has not been updated yet: run `infra/scripts/apply-realm-roles.sh`, then grant ADMIN to your user in the console to try `/admin`), and everything in production. Release order and the ADMIN grant are in `documentation/release-notes/SERVER.md`.
