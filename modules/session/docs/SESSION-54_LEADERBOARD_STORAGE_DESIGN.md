# SESSION-54 · Leaderboard storage and ranking: the design discussion and the locked decisions

**Date:** 2026-11-26 · **Ticket:** `modules/session/docs/MVP/SESSION-54_GROUP_LEADERBOARDS_AND_RANKING_ORDER.md` · **Status:** design locked by the owner in the `/workon` Phase 1 to 3 discussion; **nothing of it is built yet.**
All sizes below are **estimates** from the owner's example (60 regions, 1,000 players per region, 5 partners per player), not measurements.

## 1. Where we started

The ticket (as rewritten after the SESSION-53 rework) said: the engine no longer writes `leaderboard_entry`; a nightly job builds the boards from the statistics blobs, one row per ranked subject per board with three sort values `k1..k3`, and ranks each board with one `rank() OVER` statement. Open questions: how to find every player at a place (GIN index on `scopes` or an index table), how to build the pair board for a `PARTNER` sport, how to keep a board's rows up to date.

## 2. The discussion, step by step (owner concern, my suggestion, outcome)

| # | Owner's concern or idea | My suggestion or answer | Outcome |
|---|---|---|---|
| 1 | A table of (sport, region, country) boards that the night job walks, with a comma list of ranked record ids resolved in the last 24 h, frozen while the job runs | `stat_board_runs` already is that table. A comma list on a row is a hot row (every counted session locks it) and rewrites the whole text per append; the frozen second list is a hand-made outbox | An **append-only change table with a cutoff id** (the cutoff replaces the frozen list); it stores **who changed**, not record ids (an entry is rebuilt from the blobs, never from the records) |
| 2 | We care about pair and team boards more than personal; if we have pairs we know the singles | The change row must name the ranked **subject** (a user, or the sorted member ids of a pair). | 3 | "Pair A,B won 5 today, the blob says 3, after the job 8?" | No arithmetic: the blob already holds the running total, the job **copies** it. Adding deltas would double count on a retry | Copy, idempotent |
| 4 | Boards should be configurable per sport (`PARTNER`, `TEAM`, `SINGLE`, `GROUP`); a group board scored by points per day | `ranking[]` with the board kinds; `TEAM` refused at save until a team has an identity; `GROUP` is a different input (a daily ledger of **counts**, the rule applied at ranking time so a rule edit is retroactive) | `GROUP` points board is **its own ticket** (not yet filed; the group's region and the window are to be discussed there) |

## 3. The locked design

- **Rules (server-only, session module):** one **sort list with a direction per key**; a key is a catalog stat or a weighted sum (points). A rules row per `(sportId, countryId, kind)` covers every region board and the country board of that country; a group's own list is a row per `(sportId, groupId, kind)` (group owner or admin), falling back to the sport's default. The sport rows are changed by an ADMIN endpoint; a change makes the boards of that sport and kind rebuild; `prev_rank` is kept across a change.
- **Boards:** `SINGLE` (every player), `PARTNER` (each player's **best pair** by the sort list; a pair is listed once if it is the best pair of at least one member), `TEAM` refused until it has an identity, `GROUP` points board in its own ticket.
- **Country board** is built from the region boards: each pair counts at its **best region only**, then each player's best pair.
- **Storage:** `leaderboard_entry`, one row per board: a **tree keyed by the sort values** in the sort list's order (the tree states its own sort list), leaves `subject~prevRank`, node counts give the rank. No cap on entries; a configured maximum per board is a guard (over it the board is marked failed and logged). A board's page, a player's rank (best rank among the listed pairs that contain them) and a pair's rank are read from the tree held in the application, with a subject index built when the tree is loaded and cached per version. Rank, prev rank and the columns shown come from the tree, so a page can only show stats that are in the sort list.
- **Updates:** the engine inserts **append-only change rows** (board key, user, generated id) in the same transaction as the count. The nightly job (dedicated worker, claim by compare-and-set on `stat_board_runs`) takes the highest id as the cutoff, rebuilds only the changed players' best pairs from their blobs, sorts in memory, writes the new tree with `prevRank` baked in, then deletes the change rows up to the cutoff. A group's manual refresh (one-hour cooldown) uses the same code for one board and copies `prevRank` unchanged.

## 4. Consequences and points still to settle in the design phase

1. **Defaults I assumed that the owner did not answer explicitly:** a player's **single** entry at country level is the aggregated COUNTRY entry (best-region-only is for pairs); a **group** board lists every pair (best pair per player is for region and country).
2. **A sort-list change needs a full rebuild from the players' blobs**, because the leaves carry no counters. That brings back the first question (find every player at a place: a GIN index on `user_sport_stats.scopes` or a scan), now needed only for a full rebuild; the minimum-games change needs it too.
3. **Incremental best-pair upkeep:** a changed player's old best pair is the best-ranked entry in the tree that contains them; it is removed unless a partner's best is the same pair. To be written down and mutation-checked.
4. **A board beyond about a million entries** would be split into one row per first-level key (not built now).
5. **Engine change in SESSION-53's code:** it also inserts the change rows. The COUNTRY scope entries of pairs are no longer needed; singles still use them.
6. **Still to file:** the `GROUP` points board ticket (and `TEAM` when a team has an id). The client side (CLIENT-SESSION-42 and a rank display) is to be checked at the consumer census.
7. **Not provable on H2 or one JVM:** two instances ranking one board, PostgreSQL's TOAST cost of a large tree, the real nightly time and memory of a country board. Measure on a synthetic board at review gate 2.

## 5. As built, slice A (2026-11-26)

Built as designed, with these differences: a tree node is an array of `[key, child]` pairs and not an object (jsonb reorders object keys, so the order would be lost); the owner replaced the single `minGames` by a list of **preconditions** (`require`: `games >= 5`, `wins >= 2`, any catalog stat including a formula, at most six) that decide who is listed and never the order; the group board is always rebuilt whole from the members' rows. Point 1 of section 4 (singles at country level and every pair on a group board) was built as assumed. Point 2 is built: a rule change (or a missing tree) rebuilds a board whole from one pass over the sport's players per country; no GIN index was added. Review gate 2 (measure a synthetic country board) and slice B (reads, a group's own sort list, the refresh) are next. The ticket has the test and mutation report.
