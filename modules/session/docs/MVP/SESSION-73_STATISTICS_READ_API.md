# SESSION-73 · Statistics read API: personal, history and group member statistics

**Status:** `DONE` (2026-11-24; reworked 2026-11-25 on the reworked SESSION-53, see "Rework" below, which wins wherever the text under it differs)
**Type:** Feature · **Depends on:** SESSION-53 (and review gate 1)
**Filed:** 2026-11-23, `/feature` session "statistic and ranking" (owner specification `modules/session/docs/GROUP_AND_REGION_STATISTIC_RANKING.md`; design `modules/session/docs/STATISTIC_RANKING_DESIGN.md`; BA hand-over `modules/session/docs/STATISTIC_RANKING_DELTA.md`).

Reads over the counters and the history. Design section 7 (reads) and 8.

- `GET /api/stats/me?sportId=` the caller's `user_sport_stats` row (personal counters for all games and ranking games, normal derived as the difference, the per-partner and per-team groupings, the scope entries) in one read, the sport's derived columns evaluated from its schema, and `asOf` (the last counted session).
- `GET /api/stats/me/games?sportId=&cursor=` a page of the caller's history: the blob's pointers (newest first, at most 500) sliced by cursor, each resolved by id from `session_records` and the session (teams, scores, ranking badge, date); one batch query per page, never one per game.
- `GET /api/sessions/group/{groupId}/stats?sportId=` the group's member statistics from `group_member_stats` (singles, and the per-partner and per-team groupings, unranked here; ranks come with SESSION-54); members only (404 before 403); a user who left the group or is deactivated is not listed.
- All the sport's columns come from its schema; names through the display lookups (a deactivated player's name still shows in history).
- **Account lifecycle:** behind the per-request active gate; deactivated users are filtered at read time with `getActiveUserIds` (a new interaction), never in the history.
- Measure the read against real data (target under 2 seconds on a phone connection, BA ST-7) and say which index it uses.

**Out of scope:** another player's personal statistics (SESSION-74), head-to-head (SESSION-76), ranks (SESSION-54).

**Scope changes (owner, 2026-11-24, at the pickup scope gate):**

- **The group list is totals only, and a fourth endpoint reads one member's detail.** `GET /api/sessions/group/{groupId}/stats?sportId=` returns, for each listed member, only the totals and the sport's derived columns (no pair or partner breakdowns: a 50-member group would send over a thousand entries). **New:** `GET /api/sessions/group/{groupId}/stats/members/{userId}?sportId=` returns one member's statistics in that group, **including that member's pair statistics** (the breakdowns stored in `group_member_stats.stats.groupings`). Fixed with the owner at the same gate: the detail carries the member's totals, the sport's derived columns and **the member's pairs** (**amended later the same day, see the last decision below: the sport's one grouping, so pairs for a `TEAM` sport and partners for a `PARTNER` sport**); **any member of the group may open it** (the caller must be an active member, one 403 `SESSION_GROUP_MEMBER_REQUIRED` otherwise); the member asked about may have **left the group or been deactivated and is still shown** (this is a display of group history, the root `CLAUDE.md` rule: a lookup to show a user includes deactivated accounts; the list still hides them), so there is **no new error code** here. SESSION-74 (a player's privacy setting for personal and pair statistics) must gate this endpoint too: noted in its hand-over.
- **Decided at the same gate:** the scope entries of the personal read carry ids only (`countryId`, `regionId`; the client resolves names from `/api/reference`); `asOf` is the row's own `updated_at` (the player's `user_sport_stats` row; for the group list the newest `group_member_stats` row of the members shown), null when there is no row; the group endpoints answer **one 403 `SESSION_GROUP_MEMBER_REQUIRED`** for a non-member and for a missing or inactive group alike (as the group session lists do), not 404 then 403.
- **One grouping, so one of `pairs` and `partners` (owner, 2026-11-24, during the build):** a sport's `record.statistics.groupBy` names ONE dimension (`PARTNER` for badminton, `TEAM` for football; SESSION-53 now keeps only the first usable entry), so a response holds either `partners` or `pairs`, never both. **The member detail follows the same rule**: it returns `partners` (with `partnersTotal`) for a `PARTNER` sport such as badminton and `pairs` (with `pairsTotal`) for a `TEAM` sport, so the detail is never empty for want of the right grouping.
- **A cap of 100 on `pairs` and `partners` (decided by the PostgreSQL measurement below, as the plan said):** a player's row grows by one entry per new teammate and is not capped (a row with 300 partners is 106 KB of jsonb; with both groupings, as first designed, 300 partners and 300 pairs was 192 KB). The personal read lists the 100 most-played of each and returns `pairsTotal` and `partnersTotal`; the member detail lists at most 100 pairs with `pairsTotal`. Names are looked up for the listed entries only.
- **Client:** the member detail screen is added to **CLIENT-SESSION-42** (its group member statistics screen, which already shares the table component); no new client ticket.

**Tests:** Spock and an integration test for the visibility (own stats only, member vs non-member, left member), paging, the derived normal numbers.

**What SESSION-53 built that this ticket reads (2026-11-23, hand-over):** `user_sport_stats` and `group_member_stats` are read through `PlayerStatsDoc.read(row)` and `GroupStatsDoc.read(row)` (public, in `com.sportconnect.session.stats`): `personal().all()` and `.ranked()` are `StatsCounters` (`core("games")`, `metric("scoreFor")`, ...), `group("PARTNER", partnerUserId)` the counters with one teammate and `group("TEAM", comboKey)` the pair counters (key = the sorted member ids joined by commas; `AllRanked` for a player, `StatsCounters` in a scope or a group member), `scope(...)` the venue region and country entries (each with its own `group(by, key)`). **The jsonb shapes are documented in `documentation/md/STATISTICS_JSONB_REFERENCE.md` (read it before writing the response DTOs; the client will build on it), and the sport's `record.statistics.counters` says which core counters to show (default `games`, `wins`).** The sport's derived columns come from `StatisticsSchema.of(schema).valueOf(key, counters)` (null when there is no value, for example a division by zero); never recompute them in a new place. "Normal games" are all minus ranking for the core counters and SUM metrics only: a MAX or MIN metric is shown for all games and for ranking games, not as a difference. The history pointer is `{recordId, sessionId, ranking}`, newest first, at most 500; `asOf` is the `finished_at` of the latest `DONE` row of `session_stats_jobs`. A history page resolves its games by id from `session_records` and the sessions in one query each.

## Rework (2026-11-25, owner: S53 was reworked, so the reads follow it)

SESSION-53 was reworked and merged (PR #475): one shared config `record.scoreboard.columns` from a catalog, one grouping in `record.scoreboard.groupBy`, a per-sport switch `sports.statistics_enabled`, no `record.statistics`, no custom metrics, no fixed counters. This ticket's code was rebuilt on it (branch rebased on the merged master); the stash of the first build was applied and the conflicting S53 files kept as the rework made them.

**What changed in the API (the first-build text below is superseded where it differs):**

- **Columns:** `columns` is a plain list of catalog keys, the sport's `record.scoreboard.columns` (unknown and repeated keys dropped). The column objects (`type` CORE/METRIC/DERIVED, `aggregate`) and `StatsColumnDto` / `StatsColumnType` are gone: there are no custom metrics, the catalog is the list the client already has. No new client enum to mirror.
- **Normal games:** still all minus ranked (`StatsCounters.minus`: every stored stat subtracts, never below zero; the MAX/MIN case is gone with the custom metrics), formulas computed on the difference.
- **Pairs and partners are paged** (S53 decision 9: "paged from the blob"), the cap of 100 is gone: `page` (from 0) and `size` (1 to 50, default 20; else 400) on `GET /api/stats/me` and on the member detail; the totals stay; names are looked up for the page only.
- **The group endpoints take no `sportId`** (owner, 2026-11-25: a group has one sport): `GET /api/sessions/group/{groupId}/stats` and `.../stats/members/{userId}` read `Group.sportId` through `GroupService.getGroup` after the member gate; a group with no sport is 400 `SESSION_SPORT_REQUIRED` (an existing code). The personal endpoints keep `sportId`. The missing-sport 404 on the group endpoints is gone (the group's sport is the sport).
- **The sport's switch** (decision of this rework, not in the first ticket): while `statistics_enabled` is off, `me`, the group list and the member detail show no columns, no values and no pairs or partners (an empty schema; the rows are kept, switching it on shows them again). The same call is the 404 for a missing or deactivated sport. **`GET /api/stats/me/games` is not gated** (it reads game records, not statistics; say if it should be).
- **A player or member with no counted game has `null` values**, not zeros: the engine writes a collected stat from the first counted game on, so "none yet" is `null` and the client shows a dash.
- The group list's order uses `wins` only when the sport collects it (else 0), so it never fails for a sport whose columns omit wins.
- **Docs:** section 9 of `documentation/md/STATISTICS_JSONB_REFERENCE.md` (rewritten, the old 9 is now 10), rule 23 of `session-impl/CLAUDE.md`, the server release notes, CLIENT-SESSION-41 and 42 contract notes, the SESSION-54 and 74 hand-overs.

**Census:** `/api/stats` and the group `/stats` paths had no consumer anywhere (backend, `client/src`, the MSW mocks); the group endpoints dropped a parameter before any release, so nothing is broken; `GroupService.getGroup` is read as it is (a member passes its private-group gate); no `-api` method or existing DTO changed except this module's own response records. **Client-visible enum:** none new (the first build's CORE/METRIC/DERIVED are gone). **Account lifecycle:** unchanged (per-request active gate; the group list excludes deactivated and departed members, the detail and every name use the display lookup).

**Tests run (2026-11-25):** `SessionStatisticsServiceSpec` 43 (rewritten for the new API: columns, switch off, normal, paging of partners and pairs, a page past the end, bad page or size, group with no sport, plus the first build's cases), `StatsReadHelpersSpec` 8 (rewritten), `StatisticsReadIntegrationTest` 21, all green. **Mutation check, 13 mutants of this rework, 13 caught:** `minus` without the floor and ignoring ranked, a page that always starts at 0, the negative-page check removed, the page size limit raised, the switch bypassed, the wins sort ignored, `valuesOf` returning nulls, the member detail's partners always page 0, the pairs total counting only the page, normal not subtracted, the group's sport hardcoded (caught by the IT), the no-sport check removed.

## Implementation summary (2026-11-24, first build; superseded where "Rework" above differs)

**Built (session-api, session-impl package `stats`, controller `StatisticsController`; no migration, no entity, no new table, no new error code, no setting).**

- **Four read endpoints**, all `ROLE_USER` behind the per-request active gate, `sportId` required (a missing one is 400, a missing or deactivated sport is 404 `SPORT_NOT_FOUND` from `SportService.getResultSchema`):
  - `GET /api/stats/me`: `columns` (the sport's `counters`, metrics and derived columns, each with its type), `totals` as three maps `all`, `ranked` and `normal` (all minus ranked), `pairs` or `partners` with the players named and the same three maps each, `scopes` (the venues' region and country, ids only), `asOf` (the row's `updated_at`). A player with no counted game gets zeros and `asOf: null`.
  - `GET /api/stats/me/games`: a page of the latest 500 history pointers, newest first, `size` 1 to 50 (400 otherwise), a **record-id cursor** (not an offset); records, sessions and names are one batch each; a gone record is skipped.
  - `GET /api/sessions/group/{groupId}/stats`: members only, one **totals** row per current, active member with a counted game (no pair or partner data), most games, then wins, then id; paged (size 1 to 50); `asOf` is the newest among all listed members.
  - `GET /api/sessions/group/{groupId}/stats/members/{userId}`: any member of the group; the member's totals and their pairs or partners (the sport's one grouping); the member asked about is not checked, so one who left the group or was deactivated is still shown.
- **Gate:** `isGroupMember` is false for a non-member and for a missing group alike, one 403 `SESSION_GROUP_MEMBER_REQUIRED`, checked before the sport (so a non-member learns nothing from a 404).
- **Engine-side helpers:** `StatsCounters.minus` ("normal"), `StatisticsSchema.columns()` and `valuesOf`, read-only views `PlayerStatsDoc.groupings()/scopes()/pointers()` and `GroupStatsDoc.groupings()`, `GroupMemberStatsRepository.findByGroupIdAndSportId`.
- **Docs:** section 9 of `documentation/md/STATISTICS_JSONB_REFERENCE.md` (the response shapes, which the client builds on), `session-impl/CLAUDE.md` (the four endpoints and rule 23), the server release notes, the CLIENT-SESSION-41 and 42 contract notes, hand-overs in SESSION-54, SESSION-74 and SESSION-76.

**Where it differs from the plan approved at Phase 3 (said plainly, not silently updated):**

1. **One grouping only, so one of `pairs` and `partners`** (owner, during the build): the plan returned both lists. A sport now declares ONE of `PARTNER` (badminton) or `TEAM` (football); SESSION-53's `StatisticsSchema` keeps only the first usable `groupBy` entry. For a two-player team the two lists were the same numbers twice.
2. **The member detail follows the sport's grouping** (partners for `PARTNER`, pairs for `TEAM`) instead of "pairs only" (a consequence of 1: for badminton the detail would otherwise have been empty). Found after the first build of the detail.
3. **The 100-entry cap** (the plan's contingency, triggered by the measurement): `pairs` and `partners` list the 100 most played and `pairsTotal` / `partnersTotal` say how many exist; the member detail the same; names are looked up for the listed entries only.
4. **What is shown follows the sport's CURRENT grouping, not what is stored** (owner, after the build: grouping is the sport's, and a missing `groupBy` means no grouping at all): a sport with no `groupBy` or no statistics block shows no `pairs` and no `partners`, even when rows hold some from before a schema edit; groups stored under another dimension stay in the row and are not shown. The engine was already sport-specific (it reads each session's own sport schema); this closes the read side.
5. **`asOf` of the group list** is the newest update among all listed members (not only the page); the plan said the row's `updated_at` for a player.

**PostgreSQL measurement** (a throwaway PostgreSQL 16 container, removed; synthetic rows through `V104`; plans from `EXPLAIN (ANALYZE, BUFFERS)`):

| Read | Rows and size | Plan and time |
|---|---|---|
| personal read | one row, 106 KB of jsonb (300 partners, 20 places, 500 pointers; 192 KB with both groupings before the one-grouping rule) | primary-key index scan on `user_sport_stats_pkey`, 0.03 ms (60,001 rows in the table) |
| group list | 200 members x 100 partners = 2.7 MB (14 KB a row); 30 members x 29 partners = 122 KB (the first measurement with both groupings was 6.2 MB and 150 to 200 ms) | index scan on `group_member_stats_pkey` (group prefix), 0.04 ms for the 200 rows and 0.02 ms for the 30, with 60,000 other rows in the table; reading and serialising the 200-row case took 40 to 51 ms, the 30-row case about 1 ms |
| member detail | one row | primary-key index scan, 0.09 ms |
| games page | 50 records, up to 50 sessions | primary-key lookups by id (`findAllById`); **not measured** here (those tables were not created in the scratch database) |

Under the 2-second target for every case measured. The group list reads every row of the group and sport and pages in Java; at 200 members and 100 partners that is 2.7 MB per request, acceptable but the reason the fallback (a `games` column on `group_member_stats` and paging in SQL) is written in rule 23. **Not measured:** Java-side parsing of that jsonb, the full request time on a running server, and the games page.
