# SESSION-72 · Ranking games: propose a record and verify it (server)

**Status:** `DONE` (2026-11-23)
**Type:** Feature · **Depends on:** SESSION-50 (done) · **First of the statistic and ranking chain** (server first: LOC-5, SESSION-72, SESSION-53, SESSION-73, SESSION-54; then the client: CLIENT-SESSION-54, 41, 42).
**Filed:** 2026-11-23, `/feature` session "statistic and ranking" (owner specification `modules/session/docs/GROUP_AND_REGION_STATISTIC_RANKING.md`; design `modules/session/docs/STATISTIC_RANKING_DESIGN.md`; BA hand-over `modules/session/docs/STATISTIC_RANKING_DELTA.md`).

> **Read the "Scope changes" and "Implementation summary" at the end first: they replace parts of the text below** (who proposes, where the confirmations live, the region snapshot, the notification routing key, the status rule).

A record becomes a **ranking game** when someone who may log proposes it and every player named in it confirms it. Design: `modules/session/docs/STATISTIC_RANKING_DESIGN.md` section 5.

- **Data:** `session_records.ranking_requested_by`, `ranking_requested_at` (a flag); new table `session_record_verifications (record_id, user_id, verified_at, country_id, region_id)`, primary key (record_id, user_id); the country and region are the player's values at the moment of confirming (the snapshot, owner 2026-11-23). Liquibase and the H2 `schema.sql` mirror.
- **`POST /api/sessions/{id}/records/{recordId}/ranking-request`:** anyone the records access rule lets log; session ongoing or completed and not past `scheduledEndAt + 24h`; the record must be **rankable** by the reader of its type (for `COMPETITIVE`: a complete score with a strictly higher first team; the reader is shared with SESSION-53, so this ticket builds the `RecordTypeReader` interface and the `COMPETITIVE` reader first) and the sport must allow ranking games (409 `SESSION_RECORD_RANKING_NOT_RANKABLE` with the reason as a parameter, `SESSION_RECORD_RANKING_NOT_AVAILABLE`). Sets the flag and sends `session.record.verification.requested` to every other player of the record who is active (`UserService.getActiveUserIds`, a new interaction), one per player per proposal. The proposer is not a confirmer unless they are a player.
- **`POST /api/sessions/{id}/records/{recordId}/verify`:** only a player named in the record (403 `SESSION_RECORD_VERIFY_NOT_A_PLAYER`), only while proposed, same window; the player must have a region (409 `SESSION_RECORD_VERIFY_REGION_REQUIRED`). `INSERT ... ON CONFLICT DO NOTHING`, so a second tap does nothing.
- **State, derived:** NORMAL, PROPOSED, VERIFIED (flag and a confirmation from every player). The record DTO gains `ranking: { status, requestedBy, confirmedBy[] }` (additive).
- **Edit resets:** an update that changes a record's `data` or players clears the flag and deletes its confirmations inside the row lock the update already takes; verify takes the same lock and re-reads the record. A delete removes the confirmations. A change set that does not change the content (UNCHANGED) clears nothing.
- **Notification:** new outbox event and routing key `session.record.verification.requested`; `notification-impl` fans it out; client case in CLIENT-SESSION-54 (CLIENT-NOTIF-4 rule). Log it as NOTIF-16 in `documentation/md/NOTIFICATION_USE_CASES.md`.
- **Account lifecycle:** both endpoints are behind the per-request active gate; a deactivated player cannot propose or confirm and is not notified.
- **Census at pickup:** `SessionRecordResponse` and the client's mirrored type, the change-set update path, `SessionImportWriter` (must leave the flag empty), MSW handlers, ERROR_CODES, `NotificationType`.

**Out of scope:** counting the game (SESSION-53); a refusal state (not designed); guests (SESSION-52 will block proposing a record with a guest).

**Tests:** Spock for the state rules, the edit reset and the notification fan-out; `server/src/test/.../integration` for propose and verify through the real endpoints (non-player 403, no region 409, outside the window, edit after confirm resets, deactivated not notified, concurrent confirms, verify racing an edit); mutation check per rule.

## Scope changes (2026-11-23, owner, at the pickup scope gate)

1. **Only a `JOINED` participant of the session can propose** a game as a ranking game. This replaces "anyone the records access rule lets log" (which also lets a group member who never joined a group session log): logging keeps its own rule, proposing is narrower. A non-`JOINED` caller gets 403 `SESSION_RECORD_RANKING_PROPOSER_NOT_JOINED`.
2. **Storage (revised the same day, owner): confirmations go back to a separate table, not a JSON column on the record** (a read-modify-write of jsonb on every confirm and edit is more work than one row per player). The proposal itself stays two plain common fields on each record, `ranking_requested_by` and `ranking_requested_at` (no jsonb). Proposed shape (needs owner confirmation, see the table design in the pickup discussion): `session_records` also gains `revision INTEGER NOT NULL DEFAULT 1`, bumped by every content-changing update; `session_record_verifications (record_id, user_id, revision, verified_at, country_id, region_id)`, primary key (record_id, user_id), the confirmation counts only while its `revision` equals the record's current one (so an edit invalidates confirmations without writing to the table).
3. **Notification target stays "the other players of the game"** (the players named in the record, active ones, not the proposer); the owner's "others game participants" is read that way. Confirm if every other `JOINED` participant of the session should be notified instead.
4. **Records can be logged and proposed from `SCHEDULED` on (owner, 2026-11-23)**, so participants can set up the ranking games before the session starts: in a `SCHEDULED` or `ONGOING` session a game can be added and proposed **without a score**; in a `COMPLETED` session (until `scheduledEndAt + 24h`) a game is added or proposed with its score. When statistics are calculated (SESSION-53) a game that has no complete score, or is proposed but not confirmed by every player for its current content, is not counted as a ranking game; a game with no valid score is ignored altogether. **This relaxes SESSION-50's logging rule** (today only `ONGOING` and `COMPLETED`): the status rule of the records endpoints, the client's Result section and the 24h window description change; a client follow-up ticket is filed once the design is confirmed.
5. **Board rule changed (owner, 2026-11-23): a ranking game counts for the board of the venue's region and country, for every player in it, wherever that player lives.** A player X from region A who plays a ranking game at a venue in region B is counted for X on region B's board (and B's country's). The player's own region is no longer compared with anything, so: **the region and country snapshot is dropped** (`session_record_verifications` is `(record_id, user_id, revision, verified_at)`, no `country_id` / `region_id`); **verifying no longer needs a region on the profile** (`SESSION_RECORD_VERIFY_REGION_REQUIRED` and the "add region" dialog are gone; a player with no region proposes and confirms like anyone); a combo (pair) counts at the venue's region and country as a whole. The only geography that matters is the venue's `region_id` / `country_id` (LOC-5), read when SESSION-53 counts the session; a game at a venue with no region (no coordinates, unseeded country) is a ranking game for no regional board. This replaces the 2026-11-23 "snapshot at verification" decision. `STATISTIC_RANKING_DESIGN.md` (decisions, sections 3 to 7), `STATISTIC_RANKING_DELTA.md` (rows on region snapshot, region and country boards, decision 3), SESSION-53, 73, 54, CLIENT-SESSION-54, 41, 42, `GROUP_AND_REGION_STATISTIC_RANKING.md` notes and NOTIF-16 are updated in this change.

## Implementation summary (2026-11-23)

**Approved design, as built; the approved plan is the "Scope changes" above plus the design discussion at pickup.** One deviation from the ticket text: the routing key is `session.record.verification_requested` (three words), because the notification queue is bound `session.*.*` and the four-word key written in the ticket would never have reached the consumer.

**What was built**
- **V103**: `session_records.ranking_requested_by`, `ranking_requested_at` (nullable) and `revision INTEGER NOT NULL DEFAULT 1`; new table `session_record_verifications (record_id FK ON DELETE CASCADE, user_id, revision, verified_at, PK (record_id, user_id))`, at most one row per player per record (4 for badminton doubles). Mirrored in the H2 `schema.sql`.
- **Reader** (shared with SESSION-53): `RecordTypeReader`, `RecordFacts`, `CompetitiveRecordReader`, `RecordReaders`. Valid = two teams, players per side within the schema's range, UUIDs, nobody twice, scores consistent as the record schema contract says (rule, required slots, both teams fill a slot or neither). Rankable = valid, a complete score, the first team strictly ahead in the ranking slot. A game with no score is a **planned game** (valid, `NO_SCORE`). A sport with no score slot, or a type with no reader, has no ranking games.
- **`SessionRecordServiceImpl`**: `requestRanking` and `verify` (new endpoints on `SessionRecordController`); `requireLoggable` now accepts `SCHEDULED`; an update compares `data` and raises `revision` only when it changed; a changed proposed game asks its other players again; `toDtos` adds `ranking` for the whole session with one confirmations query (`RecordRankingSupport`).
- **Notification**: `SessionRecordVerificationRequestedEvent`, a case in `SessionEventsConsumer` (single recipient), one event per other active named player (`getActiveUserIds`).
- **Docs**: `ERROR_CODES.md` (six new codes, the NOT_LOGGABLE text), the design (decisions 7, 8, section 5), the delta, NOTIF-16, CLIENT-SESSION-54, SESSION-53 notes, the owner's spec note, `session-impl/CLAUDE.md` rule 21, release notes, deployment-guide row, `PROGRESS.md`.

**Design review answers.** Table or column: two flag fields plus a revision on the record, a table for confirmations (a row per player, written at different times by different people, read by record id). Statuses: NORMAL, PROPOSED, VERIFIED are derived and never stored. Async work: the notification goes through the existing outbox, in the same transaction. Two at once: propose, confirm and update all take the record's row lock, so a confirm and an edit of one record serialize and two confirms of one record serialize; confirming twice, or two players at once, never conflicts; a confirmation of an older revision never counts even without the lock. Time: the window is the existing `scheduledEndAt + 24h`. Failure visibility: coded 403 and 409 answers with `errorParams.reason` for a not-rankable game, an INFO line per proposal and confirmation. Account lifecycle: both endpoints sit behind the per-request active gate; a deactivated player is never notified.

**Consumer census (final).** `SessionRecordDto` (additive `ranking`): `SessionRecordsIntegrationTest`, `SessionRecordServiceImplSpec`, `SessionImportWriter` and its spec (writes records at the column defaults), `RecordChangeSetResponse`: compatible as-is. Client `SessionRecord` type, MSW `handlers/sessions.ts` and the Result tests: compatible as-is (extra field ignored), the badge is CLIENT-SESSION-54. The status rule (`SCHEDULED` now loggable): updated here (`SessionRecordServiceImplSpec`, `SessionRecordsIntegrationTest`, `ERROR_CODES.md`); the client side (`resultAccess.ts`, CLIENT-GL-38) is CLIENT-SESSION-57, filed. `session.record.changed` is unaffected. No JPQL names the new columns.

**Update 2026-11-25 (SESSION-53 rework, owner):** proposing and confirming a ranking game now also needs the sport's statistics switch on (`sports.statistics_enabled`, off by default): `requestRanking` and `verify` refuse a sport that has it off with the existing `409 SESSION_RECORD_RANKING_NOT_AVAILABLE`, checked after the result schema (`SESSION_RECORD_NOT_LOGGABLE`) and before the record lock.
