# SESSION-54 · Ranking jobs and the boards: group, region and country

**Filed:** 2026-11-12 as "Group leaderboards and the admin-set ranking order (BA LB-1 to LB-9)"; **rewritten 2026-11-23** by the `/feature` session "statistic and ranking" (`modules/session/docs/STATISTIC_RANKING_DESIGN.md`). ## Scope change (2026-11-25, owner, from the SESSION-53 rework): this ticket now builds the boards, not only ranks them

The counting engine **no longer writes `leaderboard_entry`** (the table stays exactly as `V104` made it) and only marks the boards it touched dirty in `stat_board_runs`. Anything below that says the engine upserts the entries, or hands this job ready sort values, is superseded by this block.

- **For each dirty board this job builds the rows from the blobs**, then ranks them with the statement below. GROUP board: the `group_member_stats` rows of the group (`stats.counters`, and `stats.groupings` for pairs or teams). REGION and COUNTRY boards: the `user_sport_stats.scopes` entries of that place. **How to find every player with an entry at a place is this ticket's design question**: a jsonb array has no index (options: a GIN index on `scopes`, or a small index table kept by the engine, which would be a SESSION-53 change); measure it at review gate 2 together with the ranking statement.
- **The sort values** are computed here: `k1..k3` from `record.ranking.sort` with `StatisticsSchema.valueOf(key, counters)` (a key the sport does not collect has no value, sort it last). A sport that names **no `ranking.sort` has no ranking order, so no board rows**: there is no default sort (the schema contract says so). `minGames` per kind as before (`StatisticsSchema.minGamesSingle()` / `minGamesCombo()`).
- **The pair board for a `PARTNER` sport (badminton) is built here**, from the `groupings.PARTNER` entries (the engine writes no `COMBO` rows, owner 2026-11-25): a pair's counters are in both partners' blobs (the accepted duplication), so take them once, for example from the smaller user id's row. A `TEAM`-grouped sport's pair or team board is built the same way from `groupings.TEAM`. This settles the open question left by SESSION-73's hand-over (the `TEAM` size 2 alternative is not needed).
- **The sport's switch:** the nightly job and the manual refresh skip a sport whose `statistics_enabled` is off (`SportService.getStatisticsEnabledSportIds()`), and the board reads answer as for an unknown sport.
- `StatisticsSchema` API to use: `collected()`, `columns()`, `sort()`, `valueOf(key, counters)`, `groupBy()`, `minGamesSingle()`, `minGamesCombo()`; `StatsCounters.value(key)` and `games()`; the docs are `PlayerStatsDoc`, `GroupStatsDoc`; the shapes `documentation/md/STATISTICS_JSONB_REFERENCE.md`.

Design section 7.

- **The projection and the ranking statement (owner, 2026-11-23):** ranks live in `leaderboard_entry (scope_type, scope_id, sport_id, kind, subject_key, k1, k2, k3, games, rank, ranked_at)`, one row per player or combo per board (GROUP, REGION, COUNTRY; SINGLE or COMBO), upserted by the statistics job (SESSION-53) with `k1..k3` from `record.ranking.sort` (a core counter, a metric or a derived formula; at most three keys, validated when the schema is saved). Ranking a board is one set-based statement: `UPDATE ... SET rank = r.rk, ranked_at = now() FROM (SELECT subject_key, rank() OVER (ORDER BY k1, k2, k3 with the sport's directions) rk ... WHERE <board> AND games >= :minGames) r ... WHERE e.rank IS DISTINCT FROM r.rk`, then `rank = NULL` below `minGames` (`single`, `combo`); equal entries share a rank; index `(scope_type, scope_id, sport_id, kind, k1 DESC, k2 DESC, k3 DESC)`. Measure it on a large synthetic country board at review gate 2 and decide then whether a Redis sorted set per board is needed (rebuilt from Postgres, `REDIS_KEYS.md` row).
- **Nightly job:** cron `app.stats.ranking.cron` (default `0 5 0 * * *`, `Asia/Ho_Chi_Minh`), walks the dirty boards one per transaction, bounded per pass; a board is claimed by compare-and-set on `stat_board_runs` (stale claim 15 minutes); the dirty flag is cleared only by the run that read it.
- **Manual refresh:** `POST /api/sessions/group/{groupId}/leaderboard/refresh?sportId=`, group owner or admin; one atomic update claims the board only when `computed_at <= now - 1 hour` (configurable); otherwise 429 `STATS_RANKING_COOLDOWN` with `retryAfterSeconds`; region and country boards are never refreshed by hand.
- **Reads:** the group board (members only) gains ranks; `GET /api/leaderboards/regions/{regionId}` and `/countries/{countryId}` (`sportId`, `kind` SINGLE or COMBO, paged) for every signed-in user, by display name, with the caller's own row; every answer carries `rankedAt`. Deactivated users and members who left are dropped at read time.
- **Account lifecycle:** the job counts nothing new; reads drop deactivated users; the refresh is behind the active gate and the owner/admin check.
- **Redis/ports:** none. The cron expression and cooldown are properties; add them to the production deployment guide's configuration list in the same change.

**Out of scope:** a group's own ranking order (later), seasons (SESSION-55), adjustments (SESSION-56), head-to-head.

**Tests:** Spock for the ranking maths (sort keys, ties, minimum games) and the cooldown; `server/src/test/.../integration` for the refresh permissions, the 429, the board visibility (member vs non-member, any signed-in user for region and country), dropped users; real-Postgres concurrency (nightly vs manual refresh on one board, two refreshes at once) or listed as not run; mutation check per rule.

**What SESSION-53 built that this ticket ranks (2026-11-23, hand-over):** the projection is `leaderboard_entry (scope_type GROUP|REGION|COUNTRY, scope_id, sport_id, kind SINGLE|COMBO, subject_key, k1, k2, k3, games, rank, ranked_at)`; the entity field is `boardRank` (the column is `rank`). `k1..k3` are the values of the sport's sort keys (`StatisticsSchema.sort()`, at most three, in order, `descending()` says the direction) computed when a session is counted; a key with no value is **null** (sort it last: `NULLS LAST`, matching the index `idx_leaderboard_entry_board`). `subject_key` is a user id for SINGLE and the sorted ids joined by commas for COMBO. `minGames` per kind is `StatisticsSchema.minGamesSingle()` / `minGamesCombo()`; the engine does not apply it, this ticket does (an entry below it gets `rank = NULL`). `stat_board_runs (sport_id, scope_type, scope_id, dirty, dirty_at, status, claimed_at, computed_at)`: the engine sets `dirty = true, dirty_at = now` by one atomic update; clear `dirty` only by comparing `dirty_at` with the value you read, so a session counted mid-run keeps the board dirty. Rows of boards that exist are created by the engine; the first ranking of a board that nobody touched has no row. The nightly job is a new `@Scheduled` method: it **must not run the ranking on the shared scheduler thread** (see `documentation/md/BACKGROUND_JOBS.md`: nudge a dedicated worker like `SessionStatsWorker`), and it adds its own row and "when it fails" row there in the same change. Statistics are counted for deactivated players too; the board hides them at read time.
