# SESSION-66 · Any user shares a standalone session with friends (notification, no invitation row)

**Status:** `DONE` (2026-11-18)
**Type:** New Feature
**Depends on:** none (client side: CLIENT-SESSION-49)
**Filed:** 2026-11-17, owner decision (the standalone-session list: finish the standalone session first, then group and group sessions), checked against the existing backlogs and filed in the same planning pass.

Today friends can be invited only at creation (`CreateSessionRequest.inviteeIds`, creator only, written as `INVITED` rows). New: `POST /api/sessions/{sessionId}/shares` with `{ "userIds": [...] }` (at most 50). It is a **share, not an invitation** (owner, 2026-11-17): no participant row is written; each recipient gets a notification, opens the session from it and decides for themself to send a join request (the normal join rules apply, including host approval unless the session is auto-approve).

**Rules (corrected 2026-11-18 by CLIENT-SESSION-49, owner).** The session is **standalone**; **any identified caller may share it, in any status and whatever their own participation** (joined, requested, invited, left or not in it at all). It was first filed as "the caller is a `JOINED` participant" and "the session is `PREPARING` or `SCHEDULED` (refused once `ONGOING`, `COMPLETED` or `CANCELLED`, 409 `SESSION_NOT_SHAREABLE`)"; both rules are gone, and the code with them. Every recipient is a **friend of the caller** (checked through `UserFriendService` in `user-api`, already a dependency of `session-impl`; a non-friend is **silently ignored**, never notified, so the notification cannot be used to reach strangers; **scope change 2026-11-18, owner: this was first filed as a coded refusal of the whole call, `SESSION_SHARE_NOT_FRIENDS`**); a recipient who is already `JOINED`, `REQUESTED` or `INVITED` is skipped without error. Group sessions are not covered here (group and group sessions come after the standalone chain): 403 `SESSION_SHARE_NOT_ALLOWED`, for everyone. The response is `{ sent, skipped }`.

**Notification (corrected 2026-11-18 by CLIENT-SESSION-49, owner).** One **`session.share.created`** outbox event per recipient (`SessionShareCreatedEvent`: actor = caller, recipient = friend), consumed by `SessionEventsConsumer` as a single-recipient notification that opens the session, text "{name} shared {session} with you" (client case in CLIENT-SESSION-49, the CLIENT-NOTIF-4 rule). The unread aggregation key `(recipient, type, session)` collapses repeats. It first reused `session.invitation.created` ("{actor} invited you to join"); that read as an invitation although no invitation exists, so the owner reversed it ("no invite term in this feature"). The key has three words because the notification queue is bound with `session.*.*`. The use case is logged as NOTIF-13 in `documentation/md/NOTIFICATION_USE_CASES.md`.

**Account lifecycle.** A deactivated caller is refused by the per-request gate (`JwtAuthenticationFilter`, A25); the service still resolves access through the session gate (available, then visible to this caller) rather than assuming it. Coded errors (C12) with en/vi copy in `errors:codes` ship with CLIENT-SESSION-49, or the client ticket is filed in the same change.

**Out of scope:** Group sessions, a participant row, any host approval of the share itself, rate limiting beyond the 50-per-request cap (file separately if abuse shows up).

**Tests:** Spock for the rules and counts; an IT in `server/src/test/java/com/sportconnect/integration/` through the real pipeline: any caller allowed (joined, requested, invited, left, not in the session), non-friend skipped, every status allowed, group session refused, skipped recipients counted, and the outbox events written in the same transaction.

## Implementation summary (2026-11-18)

**Design as approved** ("go ahead", 2026-11-18). Built as designed with one divergence, below.

**Rule and index added during the build (owner, 2026-11-18).** A lookup to *show* a user includes deactivated accounts (so "{userA} invited you ..." always has the real name), a lookup for a *new interaction* excludes them (refuse or skip silently, per use case); recorded in root `CLAUDE.md` § Account lifecycle, `user-impl/CLAUDE.md` and the `UserService` Javadoc. The owner also asked for an index for the active-user condition in this ticket: `V093__users_active_partial_index.sql`, a partial index `users (id) WHERE is_active = true` (a plain index on the two-valued `is_active` would be useless; keyed by id it serves `getActiveUserIds`, the per-id active checks and the chat-sync keyset scan `findByIdGreaterThanAndIsActiveTrueOrderByIdAsc`). **Verified** by applying the file to the dev Postgres inside a rolled-back transaction: it applies, `pg_indexes` shows it partial, `EXPLAIN` uses it for an `id IN (...) AND is_active` lookup (with sequential scans disabled; at 212 users the planner prefers a sequential scan on its own, so the gain shows as the table grows) and for the chat-sync keyset scan, and after the rollback it is gone. **Not verified:** the file running through Liquibase itself (the test schema is a hand-kept H2 mirror, so no test executes it) and a build on a large table. Consumer census for the DB change: an added index changes no column, constraint or result; every query naming `users.is_active` (`UserRepository` derived and JPQL methods, the A25 access-state read, `InternalUserSyncService`) is **compatible as-is**; `schema.sql` needs no change.

**Decisions at pickup (owner, 2026-11-18).** The share reuses `session.invitation.created` and its existing text ("invited you to join"), so no new notification type and no client change in the notification list (**reversed the same day, see the Correction at the end**). A friend who `LEFT` the session (a rejected request is `LEFT` too, there is no `REJECTED` status) is notified again; only `JOINED`, `REQUESTED` and `INVITED` are skipped. **Scope change during the build (owner, 2026-11-18):** a recipient who is not a friend is silently ignored too (skipped and counted, no error), where the ticket first said a coded refusal of the whole call (`SESSION_SHARE_NOT_FRIENDS`, now removed); a stranger is still never notified, and the answer does not tell a stranger from any other skipped id.

**Built.**
- **`POST /api/sessions/{sessionId}/shares`** (`SessionController`): `{ "userIds": [...] }` (`ShareSessionRequest`: not empty, at most 50, no null entry, bean validation), answers `{ sent, skipped }` (`SessionShareResponse`). `SessionService.shareSession(sessionId, callerId, request)` in `session-api`.
- **`SessionShareGate`** (new `ResourceGate<Session>`, `access/`): available like the other gates (the session exists and its group is active), visible only to a `JOINED` participant of a **standalone** session (**corrected: any caller**); a group session is visible to nobody, so it is a 403 for everyone (group sessions come after the standalone chain).
- **`SessionServiceImpl.shareSession`**, one `@Transactional` method, every refusal before any write: gate (404 `SESSION_NOT_FOUND`, 403 `SESSION_SHARE_NOT_ALLOWED`), status must be `PREPARING` or `SCHEDULED` (409 `SESSION_NOT_SHAREABLE` with `status`; **corrected: removed**), then the recipients are filtered to the caller's friend list; anyone else is silently ignored (see the scope change above). Then, in batches: one `getAcceptedFriendIds`, one derived query for the friends already `JOINED`/`REQUESTED`/`INVITED` (`findBySessionIdAndStatusInAndUserIdIn`, new), one `getActiveUserIds` (new, ids only: `WHERE id IN (...) AND is_active = true`) to drop deactivated accounts, and one `saveAll` of one `session.invitation.created` outbox row per recipient (actor is the caller; **corrected: `session.share.created`**). No participant row, no system comment. `skipped` is the distinct ids asked for minus `sent`.
- **Notification path (first build; corrected, see the end):** `SessionEventsConsumer` already turns `session.invitation.created` into a single-recipient notification that opens the session; the event Javadoc now says a share also uses it and that no `INVITED` row exists then.
- **Error codes** `SESSION_SHARE_NOT_ALLOWED` and `SESSION_NOT_SHAREABLE` registered in `documentation/md/ERROR_CODES.md` § session (**corrected: `SESSION_NOT_SHAREABLE` is deleted**).

**Divergence from the design, found by the integration test.** The plan said a deactivated friend would be skipped through `UserService.getUserSummariesByIds`, because its `-api` Javadoc said inactive ids are "simply absent". The first integration run showed a deactivated friend being notified: **neither `getUsersByIds` nor `getUserSummariesByIds` filters deactivated accounts** (the implementation never did; `user-impl/CLAUDE.md` already said "no-active-filter contract"). The first fix read `isActive` from `getUsersByIds`. **Then, on the owner's suggestion, the filtering moved into SQL:** a new additive `UserService.getActiveUserIds(Collection<UUID>)` (`UserRepository.findActiveIdsByIdIn`, `SELECT u.id ... WHERE u.id IN :ids AND u.isActive = true`) returns only the active ids, so no user row is loaded or mapped just to read one flag. The two stale sentences in `UserService`'s Javadoc are corrected too (the batch lookups include deactivated accounts). No behaviour of any existing caller changed. There is no index on `users.is_active` (checked in the changelog); the lookup is by primary key for at most 50 ids, so none is needed.

**Consumer census.** `SessionService` (one implementor, `SessionServiceImpl`): a method added, **compatible as-is**. `SessionParticipantRepository`: one derived query added, **compatible as-is**. `SessionInvitationCreatedEvent` and the `session.invitation.created` consumer (`SessionEventsConsumer`, `notificationText.ts`, en/vi `sessionInvitationCreated`): unchanged shape, **compatible as-is**. `UserService`: `getActiveUserIds` added (additive, one implementor `UserServiceImpl`, **compatible as-is** for every caller) and two Javadoc sentences corrected. No DB change (no migration, no `schema.sql` change). New constructor dependencies in `SessionServiceImpl` (`UserFriendService`, `SessionShareGate`): `user-api` is already a dependency of `session-impl` and has no dependency back, so no `@Lazy`; real context start is proven by the integration tests. **Client:** the two new error codes need their `errors:codes` en/vi copy and the dialog is CLIENT-SESSION-49 (already filed; its ticket now names the codes and the response contract). **Account lifecycle:** a deactivated caller is refused by the real JWT filter (A25, 401, asserted in the IT); the gate still runs before any write; a deactivated recipient is skipped.

## Correction (CLIENT-SESSION-49, 2026-11-18, owner)

Found while building the client dialog: the owner decided the feature says **share** everywhere and relaxed two rules. The server was rewritten in the same branch as CLIENT-SESSION-49 (its first, separate commit).

- **Status rule removed.** `shareSession` no longer refuses by status: `ONGOING`, `COMPLETED` and `CANCELLED` sessions share too; the 409 `SESSION_NOT_SHAREABLE` and its code are deleted (`ERROR_CODES.md`).
- **Participant rule removed.** `SessionShareGate.isVisibleTo` is now "an identified viewer of a standalone session"; a group session is still refused for everyone (403 `SESSION_SHARE_NOT_ALLOWED`, now meaning exactly that). The gate no longer reads the participant repository (constructor is `GroupService` only).
- **Its own event.** `session.share.created` (`SessionShareCreatedEvent`) replaces the reuse of `session.invitation.created`; `SessionEventsConsumer` has a case for it (single recipient), `SessionInvitationCreatedEvent`'s Javadoc no longer mentions shares. **The key has three words on purpose:** the queue is bound with `session.*.*`, so the two-word `session.shared` first considered would have been silently dropped (`SessionEventsConsumerIntegrationTest` proves the real route). Nothing was released, so no stored `session.invitation.created` notification needed converting.
- **Consumer census.** `SessionShareGate` (one caller, `SessionServiceImpl`), `shareSession` (one caller, the controller): updated here. `SessionEventsConsumer` and its two tests: updated here. Client: `NotificationType`, `notificationText`, en/vi `enums.json`, MSW: **updated in CLIENT-SESSION-49** (CLIENT-NOTIF-4). Docs: `ERROR_CODES.md`, `session-impl/CLAUDE.md` (endpoint, rule 13), `NOTIFICATION_USE_CASES.md` NOTIF-13, `SERVER.md` Unreleased, `PROGRESS.md`, the session backlog row, Swagger text on the controller and `ShareSessionRequest`.
- **Consequence, recorded not decided here:** any user can notify up to 50 of their friends per call about any standalone session; there is no rate limit (out of scope above).
- **Tests.** Spock: `SessionShareGateSpec` rewritten (17 cases: any viewer, every status, a group session in every status, `require` 404 and 403), `SessionServiceImplSpec` share cases (the 409 cases replaced by "any status": 249 tests in the class, all pass), `SessionEventsConsumerSpec` (16, a new case for the key). Integration: `SessionShareIntegrationTest` (13: any caller incl. requested, invited, left and not in the session; every status; group session 403; no `session.invitation.created` is written) and `SessionEventsConsumerIntegrationTest` (12, a new real-RabbitMQ case for `session.share.created`) all pass. **Mutation check, 5 of 5 killed** against a passing baseline (status rule back as a 409; group refusal dropped; creator-only rule; the invitation routing key written again; the consumer case removed). Not run: the full `:server:test`, a live server.
- **SESSION-69 (2026-11-18):** a **private** standalone session is not shareable either (`SessionShareGate` also needs `isPublic`; 403 `SESSION_SHARE_NOT_ALLOWED` now means "a group or a private session"), and `SessionShareGateSpec` / `SessionPrivateSessionIntegrationTest` cover it.
