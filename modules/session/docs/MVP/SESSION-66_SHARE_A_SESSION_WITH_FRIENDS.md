# SESSION-66 · A joined participant shares the session with friends (notification, no invitation row)

**Status:** `DONE` (2026-11-18)
**Type:** New Feature
**Depends on:** none (client side: CLIENT-SESSION-49)
**Filed:** 2026-11-17, owner decision (the standalone-session list: finish the standalone session first, then group and group sessions), checked against the existing backlogs and filed in the same planning pass.

Today friends can be invited only at creation (`CreateSessionRequest.inviteeIds`, creator only, written as `INVITED` rows). New: `POST /api/sessions/{sessionId}/shares` with `{ "userIds": [...] }` (at most 50). It is a **share, not an invitation** (owner, 2026-11-17): no participant row is written; each recipient gets a notification, opens the session from it and decides for themself to send a join request (the normal join rules apply, including host approval unless the session is auto-approve).

**Rules.** The caller is a `JOINED` participant of a standalone session (the host of a standalone session is one); the session is `PREPARING` or `SCHEDULED` (refused once `ONGOING`, `COMPLETED` or `CANCELLED`); every recipient is a **friend of the caller** (checked through `UserFriendService` in `user-api`, already a dependency of `session-impl`; a non-friend is **silently ignored**, never notified, so the notification cannot be used to reach strangers; **scope change 2026-11-18, owner: this was first filed as a coded refusal of the whole call, `SESSION_SHARE_NOT_FRIENDS`**); a recipient who is already `JOINED`, `REQUESTED` or `INVITED` is skipped without error. Group sessions are not covered here (group and group sessions come after the standalone chain). The response is `{ sent, skipped }`.

**Notification.** One `session.invitation.created` outbox event per recipient (actor = caller, recipient = friend), so the client's notification text and click-to-open-session already work, and the unread aggregation key `(recipient, type, session)` already collapses repeats. Open at pickup: whether the text "{actor} invited you to {session}" still reads right when no invitation row exists, or whether a `session.shared` type is cleaner (it would then need its client case in the same change, CLIENT-NOTIF-4 rule). The use case is logged as NOTIF-13 in `documentation/md/NOTIFICATION_USE_CASES.md`.

**Account lifecycle.** A deactivated caller is refused by the per-request gate (`JwtAuthenticationFilter`, A25); the service still resolves access through the session gate (available, then visible to this caller) rather than assuming it. Coded errors (C12) with en/vi copy in `errors:codes` ship with CLIENT-SESSION-49, or the client ticket is filed in the same change.

**Out of scope:** Group sessions, a participant row, any host approval of the share itself, rate limiting beyond the 50-per-request cap (file separately if abuse shows up).

**Tests:** Spock for the rules and counts; an IT in `server/src/test/java/com/sportconnect/integration/` through the real pipeline: joined caller allowed, non-joined caller refused, `REQUESTED` or `INVITED` caller refused, non-friend skipped, wrong status refused, group session refused, skipped recipients counted, and the outbox events written in the same transaction.

## Implementation summary (2026-11-18)

**Design as approved** ("go ahead", 2026-11-18). Built as designed with one divergence, below.

**Decisions at pickup (owner, 2026-11-18).** The share reuses `session.invitation.created` and its existing text ("invited you to join"), so no new notification type and no client change in the notification list. A friend who `LEFT` the session (a rejected request is `LEFT` too, there is no `REJECTED` status) is notified again; only `JOINED`, `REQUESTED` and `INVITED` are skipped. **Scope change during the build (owner, 2026-11-18):** a recipient who is not a friend is silently ignored too (skipped and counted, no error), where the ticket first said a coded refusal of the whole call (`SESSION_SHARE_NOT_FRIENDS`, now removed); a stranger is still never notified, and the answer does not tell a stranger from any other skipped id.

**Built.**
- **`POST /api/sessions/{sessionId}/shares`** (`SessionController`): `{ "userIds": [...] }` (`ShareSessionRequest`: not empty, at most 50, no null entry, bean validation), answers `{ sent, skipped }` (`SessionShareResponse`). `SessionService.shareSession(sessionId, callerId, request)` in `session-api`.
- **`SessionShareGate`** (new `ResourceGate<Session>`, `access/`): available like the other gates (the session exists and its group is active), visible only to a `JOINED` participant of a **standalone** session; a group session is visible to nobody, so it is a 403 for everyone (group sessions come after the standalone chain).
- **`SessionServiceImpl.shareSession`**, one `@Transactional` method, every refusal before any write: gate (404 `SESSION_NOT_FOUND`, 403 `SESSION_SHARE_NOT_ALLOWED`), status must be `PREPARING` or `SCHEDULED` (409 `SESSION_NOT_SHAREABLE` with `status`), then the recipients are filtered to the caller's friend list; anyone else is silently ignored (see the scope change above). Then, in batches: one `getAcceptedFriendIds`, one derived query for the friends already `JOINED`/`REQUESTED`/`INVITED` (`findBySessionIdAndStatusInAndUserIdIn`, new), one `getActiveUserIds` (new, ids only: `WHERE id IN (...) AND is_active = true`) to drop deactivated accounts, and one `saveAll` of one `session.invitation.created` outbox row per recipient (actor is the caller). No participant row, no system comment. `skipped` is the distinct ids asked for minus `sent`.
- **Notification path unchanged:** `SessionEventsConsumer` already turns `session.invitation.created` into a single-recipient notification that opens the session; the event Javadoc now says a share also uses it and that no `INVITED` row exists then.
- **Error codes** `SESSION_SHARE_NOT_ALLOWED` and `SESSION_NOT_SHAREABLE` registered in `documentation/md/ERROR_CODES.md` § session.

**Divergence from the design, found by the integration test.** The plan said a deactivated friend would be skipped through `UserService.getUserSummariesByIds`, because its `-api` Javadoc said inactive ids are "simply absent". The first integration run showed a deactivated friend being notified: **neither `getUsersByIds` nor `getUserSummariesByIds` filters deactivated accounts** (the implementation never did; `user-impl/CLAUDE.md` already said "no-active-filter contract"). The first fix read `isActive` from `getUsersByIds`. **Then, on the owner's suggestion, the filtering moved into SQL:** a new additive `UserService.getActiveUserIds(Collection<UUID>)` (`UserRepository.findActiveIdsByIdIn`, `SELECT u.id ... WHERE u.id IN :ids AND u.isActive = true`) returns only the active ids, so no user row is loaded or mapped just to read one flag. The two stale sentences in `UserService`'s Javadoc are corrected too (the batch lookups include deactivated accounts). No behaviour of any existing caller changed. There is no index on `users.is_active` (checked in the changelog); the lookup is by primary key for at most 50 ids, so none is needed.

**Consumer census.** `SessionService` (one implementor, `SessionServiceImpl`): a method added, **compatible as-is**. `SessionParticipantRepository`: one derived query added, **compatible as-is**. `SessionInvitationCreatedEvent` and the `session.invitation.created` consumer (`SessionEventsConsumer`, `notificationText.ts`, en/vi `sessionInvitationCreated`): unchanged shape, **compatible as-is**. `UserService`: `getActiveUserIds` added (additive, one implementor `UserServiceImpl`, **compatible as-is** for every caller) and two Javadoc sentences corrected. No DB change (no migration, no `schema.sql` change). New constructor dependencies in `SessionServiceImpl` (`UserFriendService`, `SessionShareGate`): `user-api` is already a dependency of `session-impl` and has no dependency back, so no `@Lazy`; real context start is proven by the integration tests. **Client:** the two new error codes need their `errors:codes` en/vi copy and the dialog is CLIENT-SESSION-49 (already filed; its ticket now names the codes and the response contract). **Account lifecycle:** a deactivated caller is refused by the real JWT filter (A25, 401, asserted in the IT); the gate still runs before any write; a deactivated recipient is skipped.
