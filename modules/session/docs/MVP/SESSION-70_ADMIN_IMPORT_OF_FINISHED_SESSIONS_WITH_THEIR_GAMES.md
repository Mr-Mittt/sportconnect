# SESSION-70 · Admin import of finished sessions with their games (preview and apply)

**Status:** `DONE` (2026-11-22)
**Type:** New Feature · **Depends on:** none (script pair: SESSION-71; admin page: CLIENT-ADMIN-IMPORT-1)
**Filed:** 2026-11-22, owner request: the group keeps a year of past sessions and their game results in a Google Sheet ("Cầu lông bé khỏe bé gáy", one sheet per month) and wants them in the app, locally first and then in production.

Two admin-only endpoints, `POST /api/sessions/import/preview` and `POST /api/sessions/import`, take a batch of finished sessions and create them through the normal session and result services (validation and the companion post still run; the session is created `COMPLETED`, never through the "start must be in the future" path).

**Request (both calls).** `groupId` (optional: a group session of that group when present, a standalone one otherwise), `locationId`, `hostUserId` (default: the group's owner), `sportId` (default: the group's sport), and a list of sessions: `title`, `localDate`, `startTime`, `endTime` (read in the location's timezone, stored as UTC plus timezone like any session) and `games`, in order, each with a `winners` pair and a `losers` pair of **names as the sheet writes them** (first names, no ids). Plus, for `apply`, `aliases`: a map from a sheet name to a user id, chosen by the admin.

**Name matching is the server's job.** A name is matched, accent-insensitively, by first name against the members of `groupId` (or the host's friends for a standalone import: decide at pickup); an alias wins over matching. `preview` returns, per session, each game with the matched user (id, display name) and the list of **unresolved names** (no match, or several, with the candidates). `apply` refuses with a coded error while any name is unresolved: nothing is created partially. The players of a session are the people in its games; each becomes a participant (`JOINED`), the host included.

**Result.** `apply` returns, per session, created or skipped. A session with the same group, title and start already present is **skipped, not duplicated** (so a re-run is safe).

**Checks.** Account lifecycle: admin only (`ADMIN` role from the token), the per-request gate refuses a deactivated caller; a deactivated player is an unresolved name, never a participant. Notifications: an import sends **none** (decide and log in `NOTIFICATION_USE_CASES.md` at pickup if the owner wants a digest). Client-visible: new `errorCode`s for an unresolved name, an unknown location or group, a host outside the group; their en/vi copy belongs to CLIENT-ADMIN-IMPORT-1. Consumer census at pickup: the session creation and record paths this reuses, `SecurityConfig`, the IT schema mirror.

**Out of scope:** scores (the sheet has none), guests, a UI (CLIENT-ADMIN-IMPORT-1), reading a spreadsheet (SESSION-71).

**Tests:** Spock for the matching and the skip rule; `server/src/test/.../integration` for admin vs non-admin vs deactivated, a real create of a past `COMPLETED` session with its games, an unresolved name creating nothing, and a repeated apply; a mutation check per requirement.

## Implementation summary (DONE 2026-11-22)

**Scope decisions at pickup (owner, 2026-11-22).** Group sessions only: `groupId` is required (the standalone variant, matching against the host's friends, is not built; a small follow-up if ever wanted). The host must be an active member of the group and defaults to the group's owner; it is a participant only if it appears in a game or is the host (the host is always `JOINED`). The group, location and host are chosen per call, so production can use its own group.

**Design as approved.** Two ADMIN-only endpoints, `POST /api/sessions/import/preview` and `POST /api/sessions/import`, one request shape (`groupId`, `locationId`, `hostUserId?`, `aliases?`, `sessions[]` with title, local date, start and end time, games as winner and loser names). Both build one plan: the group (404 `GROUP_NOT_FOUND`), its sport, the location (same sport, a timezone), the host, the active members (`getActiveUserIds`, one `getUsersByIds`), the aliases, the sport's `maxRecords` and `playersPerSide.max` from its result schema, then each session (times read in the location's timezone and stored as UTC, the end must be past, games 1..max, sides 1..max, no member twice in a game). Names match **first name against the active members, ignoring case and accents** (`ImportNames`); no match or several = unresolved, listed once with the candidates; an alias settles it. Preview reports; apply refuses the whole call with 409 `SESSION_IMPORT_UNRESOLVED_NAMES` before any write while any name is unresolved, otherwise writes each session in its own `REQUIRES_NEW` transaction (`SessionImportWriter`: companion post by the host, the `Session` `COMPLETED`/private/group audience all members/free/mood 5, host and players `JOINED`, one `session_records` row per game `{teams:[{scores:[null],players:[..]},{..}]}` winners first, deterministic `clientRequestId`). A session already there (same group, start and title) is `SKIPPED`; an unexpected failure is `FAILED` for that session only. No outbox row, no system comment, no notification. No migration, no entity change, no new table or column.

**Built.** In `session-api`: `ImportSessionsRequest`, `ImportPreviewResponse`, `ImportApplyResponse`, `SessionImportService`. In `session-impl` (package `importer`): `SessionImportServiceImpl`, `SessionImportWriter`, `ImportNames`, `controller/SessionImportController`, and `SessionRepository.findByGroupIdAndScheduledStartIn` (one query for the whole batch, never one per session; a repeat inside one batch is skipped too). Five new error codes in `ERROR_CODES.md`; rule 20 and two endpoint rows in the session-impl `CLAUDE.md`; a `SERVER.md` release-notes bullet (the endpoints need the ADMIN role, granted in Keycloak; nothing to run on the box).

**Divergences from the plan.** (1) The first build asked the repository once per session whether it existed; replaced before the checks by one batched query (the no-N+1 rule), with a test that fails if it goes back. (2) The preview also returns `exists` per session, so the page can show what an apply would skip. (3) The spec's `owner` field name shadowed a Groovy closure property (the mock matcher compared a wrong value); renamed in the spec only.

**Checks.** Account lifecycle: ADMIN role from the token, the per-request gate refuses a deactivated admin (IT), a deactivated member is never matched or made a participant (spec and IT). Client-visible enum or event type: none (the new error codes' en/vi copy is in CLIENT-ADMIN-IMPORT-1, whose ticket now carries the contract and the code list). Notification use case: none sent, by design. Consumer census: new endpoints, no existing consumer; the only consumer is CLIENT-ADMIN-IMPORT-1 (filed).

**Verification.** Spock: 46 import tests (`ImportNamesSpec`, `SessionImportServiceImplSpec`, `SessionImportWriterSpec`); `session-impl` 737 tests, 0 failures. `:server:test` 941 tests, 0 failures on the second full run; the first full run had 14 failures (13 in `SessionEventsConsumerIntegrationTest`, the known RabbitMQ-container flake under load, and 1 in `SessionGroupCustomSessionIntegrationTest`), and both classes pass in isolation. Mutation: 21 of 21 mutants killed (accents not stripped, the d-stroke not folded, aliases ignored, deactivated members as candidates, unresolved names not blocking apply, existing sessions not skipped, the timezone ignored, an unfinished session accepted, the host need not be a member, a player twice in a game, the session not COMPLETED, winners and losers swapped, the host not a participant, a failing session stopping the batch, the game count and the side size uncapped, an alias naming a non-member, the location sport unchecked, one query per session, apply open to a plain user, preview open to a plain user); the host-participant mutant first survived (the host also played in a game in the test) and the spec was fixed. **Not run:** concurrent applies of the same batch (there is no unique key for group + start + title, V094 dropped it on purpose, so two admins applying the same batch at the same instant could both create it; accepted, the import page disables Apply while a call is pending), real PostgreSQL (H2 only), a live admin call against the dev server and a real import of sheet `102026` (that is SESSION-71 plus the page).

**IT changes.** Added `server/src/test/java/com/sportconnect/integration/SessionImportIntegrationTest.java` (12 tests, real MockMvc and database): a plain user cannot preview or apply, a deactivated admin is refused, nothing written either way; preview matches names by first name and writes nothing; an ambiguous and an unknown name are listed with their candidates; apply creates a `COMPLETED` session in the right group, sport, location and host with start and end converted from Vietnam time, its post, the players `JOINED`, one record per game, no outbox row and no comment; the imported games are readable through the normal records endpoint although the session is far past the 24-hour window; an alias settles an ambiguous name; an unresolved name blocks the whole apply before any write; a deactivated member is never matched; a repeated apply skips; a session that has not ended is refused; a missing group is 404 and a host outside the group is refused. No existing IT changed; `schema.sql` needed no change.
