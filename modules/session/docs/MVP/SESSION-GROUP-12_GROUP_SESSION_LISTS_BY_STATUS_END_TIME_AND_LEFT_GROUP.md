# SESSION-GROUP-12 · Group session lists: hide a left group's sessions, group endpoints by status (today, later, history), and an end time for cancelled sessions

**Status:** `DONE` (2026-11-20)
**Type:** Bug Fix + Enhancement · **Depends on:** SESSION-GROUP-1 (group sessions and their access rule), SESSION-GROUP-2 (the bucket endpoint this replaces), `GroupService` (`group-api`) for the caller's group ids
**Filed:** 2026-11-20. Part A: found in use by the owner while testing CLIENT-GROUP-SESSION-1 (after leaving a group, its session still shows on the Upcoming rail and opens as "You don't have access to this."). **Scope change, same day (owner, at the pickup of CLIENT-GROUP-SESSION-2):** parts B and C added to this ticket (one ticket, three parts, each testable on its own): the group Sessions tab needs three status-filtered sections and a history by end date, which the bucket endpoint cannot serve.

## Part A. The session lists hide the group sessions of a group the caller has left

**Root cause.** `GET /sessions/upcoming`, `GET /sessions/requested` and the history lists find a session **only through the caller's own `SessionParticipant` row** (`SessionRepository.findUpcomingSessions`, `findUpcomingSessionsByDate`, `findHistorySessionsByDate`, the native `findHistoryDateCounts`; `getRequestedSessions` reuses `findUpcomingSessions` with `REQUESTED`). Leaving a group removes the `GroupMember` row and leaves every participant row as it was, so the session is still "theirs" to the list queries, while the single-session gate (`SessionDetailGate`: a group session needs a group member) refuses it. The list and the gate disagree.

**Expected.** A group session (`sessions.group_id` not null) appears in the caller's Upcoming, Requested and History lists (and the history date counts) **only while the caller is a member of that group and the group is active** (the gate's rule). A standalone session is unchanged. Rejoining makes the sessions listed again (the participant rows were never touched).

**How (decide at pickup).** Add `AND (s.groupId IS NULL OR s.groupId IN :groupIds)` to the four queries, with `groupIds` the caller's active group ids from `group-api` (one batch call per request, never per row; an empty list needs a sentinel such as `-1`, JPQL `IN ()` is not portable). `GroupService.getGroupIdsForMember(UUID)` exists but may include inactive groups, while the gate also requires an active group: filter it, or add an active-only batch method to `group-api` so the list and the gate use one rule. Page totals stay right because the filter is in the query. Rejected: flipping the participant rows to `LEFT` when someone leaves (a data change, a cross-module hook, and it misses a removed or kicked member and a group deleted later).

## Part B. A cancelled session always has an end time

**Today.** `scheduled_end_at` is set only with a duration, so a `PREPARING` session has none, and **all three cancel paths** set `cancelled_at` only: `SessionServiceImpl.cancelSession`, `SessionGenerationService.cancelUnpreparedSessions` (the automatic cancel of a draft whose start passed), `RegularSessionCanceller`. A cancelled draft therefore has no end, and a list ordered or grouped by end time cannot place it. (`closePastSessions` already reads a missing end as the start: `COALESCE(scheduledEndAt, scheduledStart)`.)

**Expected (owner's decision).** On cancel, when the session has no end, `scheduled_end_at = scheduled_start` (in all three paths; a session that has an end keeps it). A Liquibase migration backfills the existing `CANCELLED` rows with no end the same way. A `COMPLETED` session with no duration needs no backfill: the history queries order and group by `COALESCE(scheduled_end_at, scheduled_start)`.

**Check at pickup.** What else reads `scheduled_end_at`: the record edit window (`SessionRecordServiceImpl`, only `ONGOING`/`COMPLETED`), `findSessionsToStart` (only `SCHEDULED`), the `SessionResponse` end the client shows (a cancelled draft would read as "19:00 to 19:00": the client ticket CLIENT-GROUP-SESSION-2 checks how the card and the detail render an end equal to the start).

## Part C. Group session endpoints by status: `/today`, `/later`, `/history/dates`, `/history`

The group Sessions tab (CLIENT-GROUP-SESSION-2) and the Posts-tab shortcut (CLIENT-GROUP-SESSION-1) need these; `GET /sessions/group/{groupId}?bucket=` (SESSION-GROUP-2) returns one status per call, has no overlap rule, no date grouping and no window, so **its `bucket` parameter is replaced** (owner's decision; the plain `GET /sessions/group/{groupId}` without it is unchanged).

All four: member of the group only (403 `SESSION_GROUP_MEMBER_REQUIRED` for a non-member and for a missing or inactive group alike, the gate `getGroupSessions` already uses: `isGroupMember` is false for all of them, by design, so group existence does not leak), a required `viewerZoneId` (validated as on the history endpoints), a **repeatable `status`** filter (the statuses a section allows; any other value is a 400, an empty list is a 400), and a Page of `SessionResponse` where a list is returned. "Today", the end date and the windows are all read in **`viewerZoneId`** (owner's decision, like the Matches history; a session's own location zone is not used because a SQL range over per-session zones would cross the module boundary).

| Endpoint | Which sessions | Allowed `status` | Order |
|---|---|---|---|
| `GET /sessions/group/{groupId}/today?status=` | playing time overlaps today: start before the end of today and `COALESCE(end, start)` from the start of today | all five | ONGOING, SCHEDULED, PREPARING, COMPLETED, CANCELLED, then start |
| `GET /sessions/group/{groupId}/later?status=&page=&size=` | start from the start of tomorrow on | PREPARING, SCHEDULED, CANCELLED | start |
| `GET /sessions/group/{groupId}/history/dates?status=&before=&days=30` | the distinct **end dates** (`COALESCE(end, start)`) with counts, in a window of 30 calendar days ending the day before `before` (the first call sends today: yesterday back 30 days); `hasMore` when a matching session ends before the window; same shape idea as `GET /sessions/history?dateCount=` | COMPLETED, CANCELLED | date newest first |
| `GET /sessions/group/{groupId}/history?date=&status=&page=&size=` | one end date's sessions | COMPLETED, CANCELLED | end time (newest first) |

A session that overlaps today is in `/today` whatever its status (a COMPLETED one that ended this morning included); history starts at "ended yesterday or earlier". `days` defaults to 30 and is capped.

**How (decide at pickup).** Same pattern as the Matches history: a JPQL range on instants computed in Java from the zone for the list queries; a native `TO_CHAR(... AT TIME ZONE :zone, 'YYYY-MM-DD')` with `GROUP BY 1` for the date counts (the H2/Postgres notes in `session-impl/CLAUDE.md` apply); an index decision on `(group_id, scheduled_end_at)`. Group id and status filter are the narrowing columns, so no new table. **Design questions for `/workon` Phase 3:** the order of the five statuses in `/today` as a `CASE`, the window's `before` cursor and its exclusive/inclusive edge, a page size cap for `/today`.

## Implementation summary (DONE 2026-11-20)

**Design as approved (2026-11-20), restated.** No new table, entity, status or error code. Part B: one `Session.endAtStartIfMissing()` called by the three cancel paths, plus migration V101 (one `UPDATE`). Part A: `GroupService.getActiveGroupIdsForMember` (new, active groups only, one ids-only query; the feed's `getGroupIdsForMember` is untouched) feeds `AND (groupId IS NULL OR groupId IN :groupIds)` in the four caller-scoped queries, once per request, `-1` standing for "no group". Part C: four member-only endpoints replacing the `bucket` parameter, a required `viewerZoneId`, a repeatable required `status`, "today" read in the viewer's zone as two `atStartOfDay` instants. Owner's answers kept: `bucket` removed now (server and client are released together, see the release notes), empty 30-day windows are the client's to skip (`hasMore`, `nextBefore`), `/today` pages 50 (max 100).
