# SESSION-GROUP-5 · Regular group sessions: the generation queue, its triggers and retry

**Status:** `DONE` (2026-11-19)
**Type:** New Feature (replaces SESSION-38's generation) · **Depends on:** SESSION-GROUP-1, SESSION-GROUP-4
**Filed:** 2026-11-19, from the owner's specification ("Generation"). Closes **SESSION-41** (the retry/backstop gap) and supersedes the single-rule path of SESSION-38.

**Data** (one changelog):
- `sessions` gains `recurrence_id` (null = custom session) and `occurrence_date` (the local date of the slot). A partial unique index `(recurrence_id, occurrence_date) WHERE recurrence_id IS NOT NULL` is the duplicate guard that replaces the dropped `unique_group_session_start`.
- `group_session_generation_queue`: `id`, `recurrence_id`, `target_start` (instant, orders the queue), `status` PENDING|DONE|FAILED, `attempts`, `next_attempt_at`, `last_error`, timestamps; unique `(recurrence_id, target_start)`.

**Time model (owner, 2026-11-19).** A config is a wall-clock slot read in the **location's timezone**. The session is saved as a UTC instant plus the location's timezone (as a standalone session); "today", "nearest day" and "already ended" are judged on that wall clock; UTC is only the stored form and the queue order. A monthly config on a day the month lacks (29 to 31) **skips that month**.

**Resolver.** An event listener drains the queue ordered by `target_start`; each item runs `REQUIRES_NEW` so one failure cannot poison another. It reuses `SessionGenerationService`'s title, companion post (`createSessionPost`) and author (the group's current owner) code, and fills the session from the config (fee, location, duration, game mood, attributes, `autoApprove = true`, `isPublic = false`, the audience snapshot). Status by the clock: `SCHEDULED` when the start is ahead, `ONGOING` when now is inside the slot, **skipped** when the slot has already ended. Retry: up to 5 attempts, backoff 1, 5, 15, 60 minutes, then `FAILED` (kept for inspection; the startup job and the next trigger re-queue a group's nearest day, so a `FAILED` item never strands a group). The audience is notified with `session.group.created` at generation (all members or the config's specific ones, active members only; a member who left is filtered out at that moment).

**Producers** (only for a group that is ON, using non-draft configs of the active mode):
1. **Startup** (`ApplicationReadyEvent`, down-time recovery): for each such group, push the configs of the nearest day (including today's not-yet-ended slots); if anything was pushed, fire the resolver.
2. **The last regular session of a day** reaching `COMPLETED` or `CANCELLED` (`closePastSessions` and `cancelSession`): "last" = no other regular session of that group with the same `occurrence_date` is `PREPARING`, `SCHEDULED` or `ONGOING`; push the next nearest day. **Custom sessions never trigger.** A cancel while the group is **OFF** (or the config deleted or inactive) triggers nothing, so "cancel everything" cannot regenerate.
3. **Owner/admin actions** ON, add a config, edit a config, switch mode: generate today's slots not yet ended now; then for the nearest configured day, if a regular `SCHEDULED`/`ONGOING` session exists between now and that day let it trigger generation, otherwise enqueue.

**Concurrency (the spec's "2check").** Producers 1 and 2 can race for the same slot; both go through the queue's unique key and the sessions' `(recurrence_id, occurrence_date)` key, so the loser is a no-op. Prove it with a two-thread IT.

**Replaces.** `GroupServiceImpl.triggerSessionGenerationIfEligible` and its two calls, the single-rule branch of `SessionGenerationService`, `SessionGenerationJob`'s generation part (the 15-minute status jobs stay). The old columns remain until GROUP-1, but nothing reads them after this ticket. Existing generated sessions stay as custom sessions (no `recurrence_id`).

**Open at pickup:** a deactivated owner (the author): proposal, skip and log, because the generator acts as the owner (new-interaction rule). **Account lifecycle:** no endpoint added; the producers run in the owner/admin request or as jobs.

**Consumer census:** `SessionGenerationService`, `SessionGenerationJob`, `GroupServiceImpl` trigger calls, `GroupSessionGenerationIntegrationTest` and the failure-isolation IT (rewritten), `closePastSessions`, `cancelSession`, SESSION-38/41 tickets, `session-impl/CLAUDE.md` (stale hourly-job text), `NOTIFICATION_USE_CASES.md`.

**Tests:** Spock for the occurrence maths (weekly, monthly, skipped months, timezone edges, today's ongoing and ended slots), the "last of the day" rule, retry/backoff; ITs: startup recovery, completion and cancel triggers, OFF/inactive cancel does not regenerate, the admin actions, the duplicate race, a failure isolated and retried, notification to ALL and SPECIFIC audiences. Mutation check each requirement.

## Implementation summary (2026-11-19)

**Built as filed**, with the points below.
- **Data (V096):** `sessions.recurrence_id` and `occurrence_date` (nullable) with a **plain unique index** on the pair (a null `recurrence_id` never collides in Postgres or H2, so the filed `WHERE recurrence_id IS NOT NULL` was not needed and H2 has no partial indexes); `group_session_generation_queue` (`recurrence_id` with FK and cascade to its recurrence, `occurrence_date`, `target_start`, `status`, `attempts`, `next_attempt_at`, `last_error`). The queue key is `(recurrence, occurrence_date)` rather than `(recurrence, target_start)` as filed: the session is rebuilt from the recurrence when it is generated, so `target_start` only orders the queue.
- **Pure maths (`GroupSessionOccurrences`):** `next` = the first slot that has not ended at `now` ("today" is the date in the location's timezone; a slot that ends exactly now is over); `at` = date + local start time in the zone, as a UTC instant; weekly `nextOrSame`; monthly skips a month without the day (29-31).
- **Planner (`REQUIRES_NEW`, four batch queries, never per recurrence):** only groups with generation on, only complete (non-draft) recurrences of the active mode with a location and a duration. `enqueueForAllEnabledGroups` (startup), `enqueueAfterDaysEnded` (a day is over only when `findOpenRegularDays` no longer lists it), `enqueueAfterConfigurationChange` (today's not-yet-ended slots; the nearest later day only when there are none and no `SCHEDULED`/`ONGOING` regular session starts before it). Queuing is idempotent: a queued or generated slot is left alone, a `FAILED` one is revived.
- **Generator (`REQUIRES_NEW` per slot):** as filed, plus the skip list that marks the row `DONE` without creating anything (recurrence gone or draft, off, other mode, group inactive, slot ended, session exists). The session is the current owner's (`getGroupOwnerId`), `autoApprove = true`, `isPublic = false`, status by the clock (`SCHEDULED`, or `ONGOING` when under way), companion post first, audience snapshotted, `session.group.created` to the audience minus the owner. Failure: 4 retries at 1, 5, 15, 60 minutes, the fifth attempt ends `FAILED` (`GroupSessionOccurrenceGenerator.recordFailure`).
- **Runner:** drains due `PENDING` rows in `target_start` order (batches of 50), one transaction per slot; a slot that fails is recorded and not retried in the same run.
- **Producers:** `GroupSessionGenerationListener`: `ApplicationReadyEvent` (startup, down-time recovery) and two after-commit events (`RegularSessionsEnded`, published by `closePastSessions` and `cancelSession`; `ConfigChanged`, published by the config service when generation is switched ON, the mode is switched while ON, or a configuration is added or replaced). Handlers are caught and logged, so a generation failure never undoes or fails the change (the old design needed `REQUIRES_NEW` for that, found by a real IT; the after-commit events make it structural).
- **Removed:** `SessionGenerationService.generateForConfigs` and its helpers, `SessionService.generateNextOccurrenceForGroup`, `GroupServiceImpl.triggerSessionGenerationIfEligible` and its two calls, group-impl's `@Lazy SessionService` and its `session-api` Gradle dependency, and the two old generation ITs (`GroupSessionGenerationIntegrationTest` rewritten, `GroupSessionGenerationFailureIsolationIntegrationTest` deleted: its subject no longer exists). The old `groups.recurrence_*` columns, endpoints and flag remain until GROUP-1 but nothing generates from them.
- **Extracted:** `GroupSessionRecipients` (from `SessionServiceImpl`, now shared by create, cancel and the generator); `SessionServiceImpl`'s constructor loses `SessionGenerationService` and gains the recipients component and the event publisher.

**Deviations and notes.**
- The ticket's "SCHEDULED/ONGOING regular session **between now and that day**" is implemented as one existence query on regular sessions starting before the nearest day (`existsByGroupIdAndRecurrenceIdIsNotNullAndStatusInAndScheduledStartLessThan`).
- A generated session's creator is not made a participant (the owner is its author, not necessarily a player), unlike a custom session's creator.
- The deactivated-owner question is **not special-cased** (open item 6 of the plan): the generator uses `getGroupOwnerId`, which returns the owner whatever the account state, as the old generator did; revisit when SESSION-68, B24, CHAT-23 and U28 (the deactivated-account tickets) are picked up.
- The spec's "2check" (startup job vs the last-session trigger) is answered by idempotent queuing through the two `(recurrence, date)` keys; `GroupSessionGenerationIntegrationTest.theStartupRecovery...` runs the recovery twice and the config-change tests re-trigger over existing sessions.

## Known concurrency gaps (review, 2026-11-19; found by reading the code, none reproduced, no test runs two instances or two racing threads)

The queue is correct when only one thing runs at a time. "At the same time" means **two database transactions**, and that is true for two server instances and also for **one instance with several threads**: every transaction takes its own connection from the pool (20, 50 in production; a connection is bound to one thread's transaction and is never shared), so the database sees two threads of one pod exactly like two pods. The threads that can overlap in one pod are the request threads (the after-commit handlers below run on the thread that committed, so on a Tomcat request thread), the single `@Scheduled` thread (the 15-minute jobs; `closePastSessions` publishes `RegularSessionsEnded` from it) and, once, the startup thread.

| # | What races | What happens today | What a user sees |
|---|---|---|---|
| Q1 | Two instances start together (`enqueueForAllEnabledGroups`) | Both insert the same queue keys; the loser fails on the unique `(recurrence_id, occurrence_date)` and its **whole** transaction (every enabled group) rolls back, logged as `Group session generation at startup failed` (ERROR) | Nothing; a slot only the loser would have queued is queued at the next trigger |
| Q2 | Two changes to the same group's configuration at once (an owner and an admin, a double click, an add followed by a switch ON), on any thread or instance | Two `ConfigChanged` handlers plan the same slot; the loser fails on the same key, caught and logged as `Group session generation after a configuration change failed` (WARN) | The HTTP response is not affected (the change is committed, the handler catches everything); the other handler queued the same slot |
| Q3 | A regular session ends or is cancelled (a user's request thread, or the scheduler thread) while another planner runs for the same group | Same as Q2 (`... after regular sessions ended failed`, WARN) | Nothing |
| Q4 | A configuration change while a startup or an ended-day planner runs, on another thread or instance | Same as Q2 | Nothing |
| S1 | Two runners drain the same due item (two instances, or one instance with a request thread and the scheduler thread both calling `processDue()`) | Both build the session; the loser waits on the unique `sessions (recurrence_id, occurrence_date)` index and fails after the winner commits, and its whole transaction (companion post, session, outbox rows) rolls back; `recordFailure` sees `DONE` and returns **silently, nothing is logged** | Nothing: no duplicate session, no duplicate notification, a few milliseconds of waiting |
| S2 | Two planners revive the same `FAILED` row, or two instances record the same real failure | A read-modify-write on the row: lost updates, and `attempts` can be counted twice, so the item reaches `FAILED` sooner than the 1, 5, 15, 60 minute schedule | A group's session can arrive late, until the next trigger or restart revives it |
| E1 | A configuration is edited so that its day changes (Tuesday to Monday) while its old slot is still `PENDING` | `GroupSessionOccurrences.at` applies the **current** start time to the queued **old** date and never checks the date still falls on the rule, so both items generate | Two sessions for one recurrence, one on a day the rule no longer includes |

**Q2 (and its family Q1, Q3, Q4) is recorded here as a known gap to find out whether it ever occurs.** To see it in production, search the server log for the three messages in the table (`Group session generation at startup failed`, `... after a configuration change failed for group`, `... after regular sessions ended failed for`); S1 leaves no trace today. The queue hardening that follows this note (one commit each: the `IGNORED` status with the rule guard, race-free queueing, `FOR UPDATE SKIP LOCKED`) absorbs Q1 to Q4 and S1 and S2 by construction, and logs each absorbed race at INFO with a fixed marker (`queue race absorbed`) so the count of real occurrences stays visible; E1 is closed by the rule guard. This section is updated with the commits when they land.

**Landed 2026-11-19 (commit 1 of 4: `IGNORED` status and the day-rule guard, V100):** E1 is closed. It was reproduced first: a `PENDING` row queued for a date two days after the recurrence's weekday made the generator create a session on the wrong day (`aQueuedDate_thatNoLongerFallsOnTheRecurrencesDay_isIgnoredAsSuperseded...`, failing before the guard, green after). A skipped slot is now `IGNORED` with a reason, not `DONE`, and the planner revives it, so a slot skipped while generation was off is generated when it is switched back on. `last_attempt_at` was added. An existing IT (`aFailingSlot_isRetriedWithABackoff...`) queued a date that was not on its recurrence's day and had only passed because nothing checked; its fixture now uses a date on the rule. Still open: Q1 to Q4, S1, S2 (race-free queueing, `SKIP LOCKED`), R1, R2 (asynchronous worker and the 60-second safety net).

| # | What | What happens today | What a user sees |
|---|---|---|---|
| R1 | A failed slot's retry backoff (1, 5, 15, 60 minutes) has no clock | Nothing drains the queue on a timer: `processDue()` runs only from the three after-commit/startup handlers, so a retry waits for the next trigger anywhere in the app (or a restart) and can sit for hours in a quiet system; the "retry" is a minimum wait, not a schedule | A group's slot arrives late |
| R2 | Draining runs on the request or scheduler thread that triggered it, with no limit on how many run at once | A backlog (after downtime, a bulk change) lands on one owner's request thread; many concurrent runners would hold 2 connections each of a pool of 20 (50 in production) | A slow or timed-out save |

**Owner decision (2026-11-19):** the runner becomes **asynchronous**. The handlers keep planning inline (a few idempotent queries) and then nudge **one worker per instance** (a single thread, queue of one, discard policy: a nudge while one run is running and one is queued is dropped, which is safe because the queued run starts after that nudge's commit); a 60-second scheduled call to the same worker is the safety net and gives the backoff its clock (R1); the instances share the queue through the row lock. The save answers at once ("saved, sessions will appear shortly", noted in CLIENT-GROUP-SESSION-4 and 5). Scaling the worker with the backlog, up to a configured limit of parallel runners, is **SESSION-GROUP-9**.
