# SESSION-GL-64 · Search the people who can see a session's thread (for tagging)

**Status:** `IN PROGRESS`
**Type:** New Feature
**Depends on:** none (the thread and its gate exist: SESSION-10, SESSION-21)
**Filed:** 2026-11-15, owner request after CLIENT-GL-39: the `@` picker should also work in normal comments, like tagging people, and it should offer everyone who can see the thread. The participants endpoint lists only `JOINED` people to an ordinary caller, so the client cannot build that list alone.

A new read endpoint, `GET /api/sessions/{sessionId}/thread-people?q=&size=`, returns the people who can see the session's discussion thread, narrowed by a name search as the user types and capped in size (default 5, ceiling 20: the default is what a call gets without `size`, the ceiling is the most a caller may ask for, anything above is cut to it; scope change 2026-11-16). Who counts: the `JOINED`, `REQUESTED` and `INVITED` participants, plus, for a group session, the group's members (the same people `SessionGate` lets read the thread). Each item is `userId`, `fullName`, `avatarUrl` and nothing else (no email, no status). Used by CLIENT-GL-50 (the tag picker in the comment box); entry point is an authenticated call from the session detail modal.

Rules: the caller has to pass the same gate as the thread (`SessionGate`: available, then visible; 404 `SESSION_NOT_FOUND`, 403 `SESSION_FORBIDDEN`); a deactivated caller is refused by the JWT filter as on every authenticated path (no extra check, per CLAUDE.md); an empty `q` returns the first page ordered by name, a `q` matches the start of any word of the full name, case and accent insensitive; deactivated people are not returned; a person who is in the list twice (a participant and a group member) appears once; the caller may appear. Batch the user lookups (`getUserSummariesByIds`), never one call per row. A group's member list can be large, so the search runs in the database or in a batch of ids, never by loading the whole group into memory (decide at pickup; check the `group-api` and `user-api` for a name search).

Cross-domain: only `-api` interfaces (`group-api` for members, `user-api` for names); ids only. Error codes: none new (reuses the gate's). Client-visible enum: none.

**Scope change 2026-11-16 (owner, at pickup): one name-search standard for the whole app.** Every user search by name matches on `firstName` and `lastName` only (no `username`, no email, no phone), **word-start only** (no "contains"), **accent-insensitive** (Vietnamese first: `tuan` finds "Tuấn", `dang` finds "Đặng"), case-insensitive. A multi-word query splits into words and each word must start some word of `firstName + ' ' + lastName`, in any order (`anh tu` finds "Tuấn Anh"). A user with no first and no last name (a phone-only or username-only account) is not found by name. The rule is built once in the user domain, as a new `user-api` method that takes a **scope** (a list of user ids), the query and a size, and returns `UserSummaryResponse` (`id`, `fullName`, `avatarUrl`) for active users only; every caller adds its own scope: this ticket (thread people: participants plus, for a group session, the group's members), a group-member search, the friend search. In this ticket:
- build that `user-api` method and its database-side matching (folding, word-start; decide at pickup between Postgres `unaccent`, a stored pre-folded column, or folding in Java for a small scope, and verify `unaccent` exists on dev, the Testcontainers database and production);
- move the existing `UserService.searchUsers` (`GET /api/users/search`, today `LIKE '%keyword%'` on `firstName`, `lastName` and `username`, case-insensitive only) onto the same rule: **an existing contract changes** (it stops matching `username` and the middle of a word), so the consumer census (backend callers, `client/src`, MSW mocks, tests) is done first and each consumer is listed as compatible, updated or deferred with a filed ticket;
- the group side needs a scope source from `group-api` (a member-ids method or a member search; decide at pickup, additive);
- result order, because the cap is small: people already in the session first (JOINED, then REQUESTED, INVITED), then group members, then a match on the first word before a later word, then name; an empty `q` gives the first page in that order.
The client friend-invite filter (`CreateSessionModal`, a browser-side `includes` over the friends list) moves to the same rule through a shared client matcher, in CLIENT-GL-50 (not here).

**Out of scope:** validating the tags inside a comment (the server keeps storing the text as it is); notifying a tagged person (NOTIF-12); paging beyond the cap.

**Tests:** Spock for the merge, the de-duplication, the name matching and the cap; an integration test in `server/src/test/java/com/sportconnect/integration/` through the real endpoint: a standalone session (joined, requested and invited appear), a group session (members appear), a stranger gets 403, a missing session 404, a deactivated user is not listed.
