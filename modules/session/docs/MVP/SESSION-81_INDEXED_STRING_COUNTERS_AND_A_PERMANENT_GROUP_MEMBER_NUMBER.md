## Part A · counters as indexed strings

- **(As built: the ids are global, one table for every record type, `StatsCatalog.ids()`: `games` 1, `wins` 2, `losses` 3, `scoreFor` 4, `scoreAgainst` 5, `winRate` 6, `winDiff` 7, `scoreDiff` 8; a blob does not know its record type, so a global id needs no schema to decode. The client's file carries them as `COMPETITIVE.scoreboard.statIds`.)** A fixed, explicit, append-only id for every stat, in `StatsCatalog` and in the client's `record-ui-v1.json` (a new `id` on each `COMPETITIVE.scoreboard` stat; `StatsCatalogSpec` fails when the two differ, as it does for the keys). The id is **not** the display order (the client may reorder columns); it is never reused or renumbered. Suggested for `COMPETITIVE`: `games` 1, `wins` 2, `losses` 3, `scoreFor` 4, `scoreAgainst` 5, then the formulas `winRate` 6, `winDiff` 7, `scoreDiff` 8 (stored stats first, so trailing empty slots are cut).
- **A counters object is stored as one string, the values by id**: `"7,4,3"` is 7 games, 4 wins and 3 losses; a stat the sport does not collect is an empty slot (`"7,4,,52,40"`), trailing empty slots are cut, a sum keeps its decimal part (`.`) and its sign. `,` is the separator (a `-` would clash with a negative sum). An empty counters object is `""`.
- **Where:** every counters object of `user_sport_stats` (`personal.all`, `personal.ranked`, each partner or team entry, each scope entry) and of `group_member_stats` (totals and groupings). A partner or team entry holds its `all` and its `ranked` in one string, `"all/ranked"`, the `ranked` part left out when nothing was counted (`"7,4,3"` or `"7,4,3/2,1,1"`). **Only counters become strings**: the fields that identify a place (`scope`, `countryId`, `regionId`) and the structure stay plain jsonb, so SESSION-54 can still index or query them (the open question of finding every player at a region).
- **Measured** (`pg_column_size`, 300 partners): 48 KB now, 30 KB as arrays, **18 KB as one string per partner** (21 KB with half of them carrying a ranked part).
- The jsonb reference documents the id table and the format; `StatsCounters.fromMap`/`toMap` (or a small codec class) is the one place that knows it. The SESSION-73 reads are unchanged (they decode to stat names; the API still answers with keys). Not done: aligned `values` arrays in the SESSION-73 responses (a contract change, to decide with CLIENT-SESSION-41 and 42).

## Part B · a permanent member number per group, in `group-impl`

- **The group module owns it (as built: allocated the first time it is asked for, not at join):** each member gets a number that is unique **inside the group** and **kept for good**: a member who leaves and rejoins gets the same number back, and a number is never reused. `group_members` rows are deleted on leave (`deleteByGroupIdAndUserId`), so the number lives in its own small table, `group_member_numbers (group_id, user_id, member_no)` (primary key `(group_id, user_id)`, unique `(group_id, member_no)`), with an atomic per-group counter (for example `groups.last_member_no`, bumped by one `UPDATE ... RETURNING`). A migration backfills the existing members in joined order. No foreign key across modules, per the repo rule.
- **`group-api`:** `getMemberNumbers(groupId, userIds)` (batch, allocating the missing ones) and `getUserIdsByMemberNumbers(groupId, numbers)` (batch). The session module never joins group tables.
- **The session module uses it:** `group_member_stats.stats.groupings.PARTNER` is keyed by the partner's member number (not a UUID), and `group_stats.h2h` takes its pair numbers from the group, so **its own `members` dictionary and `lastMember` go away** (the number is allocated at join time, so counting no longer allocates and the head-to-head row is locked only when a head-to-head is written, as before). The SESSION-73 group reads translate numbers back to user ids with one batch call per request (the group's members are few hundreds at most). A team key in a group (`TEAM`) becomes the member numbers, sorted, joined by commas.
- **Personal rows are not changed:** a player's partners come from many groups, so `user_sport_stats` keeps UUID keys (a global user number would be a cross-domain change nobody wants).
- **Measured** (300 partners in a group member's row): 48 KB now, **8 KB** with small-integer keys and indexed strings; a normal group row (20 partners) is a few hundred bytes either way, so this matters for large groups.

## Design review (to answer at pickup)

- **Table or column:** the number is its own table because it must survive the `group_members` delete; written once per member at join, read in batch by the engine and the reads, never joined across modules.
- **Two at once:** two people joining one group at the same time take their numbers from one atomic counter update (the loser waits for the row lock, never gets the same number); the unique key `(group_id, member_no)` is the backstop. A rejoin finds its existing row. A counting run reads the numbers with no lock.
- **Failure and visibility:** a user with no number yet (a member from before the migration whose backfill failed) is allocated lazily by `getMemberNumbers`; the allocation is logged.
- **What the tests can prove:** the allocation, the rejoin and the codec on H2; two real instances allocating and PostgreSQL's `UPDATE ... RETURNING` are not run.
- **Account lifecycle:** a deactivated member keeps their number; the group list still hides them (SESSION-73), the detail still shows them.
- **Census:** consumers of the stored shapes are `PlayerStatsDoc`, `GroupStatsDoc`, `GroupH2hDoc`, `StatsCounters`, `SessionStatisticsServiceImpl`, their specs and ITs and the jsonb reference; `/api/stats` and the group statistics paths keep their contract. Consumers of `group_members` (join, leave, remove, delete group) must allocate and not delete the number.

**Out of scope:** the SESSION-73 wire format, positional counters keyed by id in an object, a global user number, pruning job rows (SESSION-75), the rebuild (SESSION-77, which must use the same codec and numbers), a ticket for the notification of the change.

**Tests:** Spock for the codec (round trip, empty slots, decimals, negatives, trailing cut, a stat added later), the catalog ids and the client contract test, the number allocation (join, leave and rejoin, two joins, backfill order), the head-to-head with group numbers; integration tests for the join and rejoin through the real group API, the engine writing and the reads translating, and the statistics tables written in the new shape; mutation check per rule; update `STATISTICS_JSONB_REFERENCE.md`, rule 22 of `session-impl/CLAUDE.md`, `group-impl/CLAUDE.md` and the release notes (a migration; the development database must clear the statistics tables once more).
