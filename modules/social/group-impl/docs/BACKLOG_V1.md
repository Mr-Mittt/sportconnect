## Tickets

### A1 · Migrate Group/GroupMember ids to Snowflake IDs
**Status:** `TODO` · **Type:** Enhancement (Architecture) · **Filed:** 2026-07-13, during client ticket FEED-0
**Companion ticket:** `modules/social/post-impl/docs/BACKLOG_V1.md` · C11 (Post/Comment/Hashtag — same generator, separate module). **Depends on C11 shipping first** — this ticket reuses C11's shared generator rather than building a second one.

#### Motivation

Same rationale as the companion post-impl ticket (C11) — see that ticket for the full writeup.
Summary: `Group`, `GroupMember` (and, for full-module consistency, `GroupInvitation`,
`GroupJoinRequest`, `GroupPinnedPost`, `GroupRole`, `GroupSettings`) currently use
`@GeneratedValue(strategy = GenerationType.IDENTITY)` / `BIGSERIAL`. Sequential ids are enumerable
(caller can infer group count/growth by incrementing — access itself stays permission-gated by
existing membership/ownership/privacy checks) and can't be safely generated by two independent
services without coordination, relevant to this repo's stated monolith-first,
microservice-ready direction (root `CLAUDE.md`).

#### Design

**Do not build a second generator.** C11 (post-impl) builds `com.sportconnect.common.id.
SnowflakeIdGenerator` in `modules/common` specifically so both modules share one implementation —
this ticket is purely "apply the existing generator here," not a new design.

- Swap `@GeneratedValue(strategy = GenerationType.IDENTITY)` → `SnowflakeIdGenerator` on: `Group`,
  `GroupMember` (client-facing, required — both appear in `GroupResponse`/`GroupMemberResponse`).
  Optionally also `GroupInvitation`, `GroupJoinRequest`, `GroupPinnedPost`, `GroupRole`,
  `GroupSettings` for full module consistency — none of these are serialized to the client today, so
  this part doesn't block anything and can be scoped down if time-boxed.
- Same `IDENTITY`-relies-on-DB vs. app-assigns-before-insert change as C11 — not just an annotation
  swap.
- **JSON safety:** add `@JsonSerialize(using = ToStringSerializer.class)` to `GroupResponse.id`,
  `GroupMemberResponse.id`/`groupId`, and anywhere else these ids appear in a response DTO (check
  `GroupSearchResponse`, `GroupInvitationResponse`, `JoinRequestResponse`, `PinnedPostResponse` too —
  C11 only covers post-module DTOs, this ticket owns every group-module DTO exposing one of these
  ids). Same reasoning as C11: a raw large Snowflake integer in JSON silently loses precision for a
  JS/TS client past `Number.MAX_SAFE_INTEGER`. **Must ship in the same PR as the generator swap.**
- No production data exists yet — no backfill needed.

#### Client-side impact — do not skip this note

Same situation as C11: the client's FEED-0 ticket types `Group.id`, `GroupMember.id`/`groupId` as
**`number`** — a deliberate, explicit decision to match the *current* `BIGSERIAL` backend, made
aware this ticket would eventually force a revisit. **When this ticket ships, the same follow-up
client ticket that C11 triggers must also cover these fields** (don't file a second, separate
client ticket — one follow-up covering Post/Comment/Hashtag/Group/GroupMember together, since by
then they'll all need the same `number` → `string` change in the same client PR). Affects
`client/src/features/feed/types.ts`, `queryKeys.ts` (`groupFeed(groupId)`, `userGroups` results),
and whichever of FEED-1/2/3/4/6/7/8/9 have shipped by then.

#### Out of scope

- Building a second Snowflake generator — reuse C11's.
- Config-driven multi-worker-id support — same as C11, hardcoded worker id is correct for the
  current single-instance deployment.
- The client-side type change itself — folded into C11's follow-up client ticket, not built here.
- Backfilling existing rows — no production data exists to backfill.

#### Tests

- Confirm `Group`/`GroupMember` entities get ids from the shared generator (reuse C11's generator
  unit test — no need to re-test the generator itself here).
- Update `GroupServiceImplSpec` wherever a literal id value (e.g. `1L`) is currently asserted.
- Confirm `GroupResponse`/`GroupMemberResponse`/`GroupSearchResponse`/`GroupInvitationResponse`/
  `JoinRequestResponse`/`PinnedPostResponse` all serialize their id fields as JSON strings
  (integration test against the real controller, checking the raw JSON body).

### B10 · Group type change flow (upgrade/downgrade)
**Status:** `TODO` · **Type:** New Feature · **Moved from MVP backlog:** 2026-07-21
**Origin:** filed directly out of B7 — every group is silently created as `DEFAULT` (50 members) with
no way to move to `STANDARD` (100) or `PREMIUM` (500). `GroupType` entity/repository and the
`group_types` table already exist (B7); this ticket is the actual change-type flow.

**Design questions to resolve at pickup (flagging now, not assumed):**
- Who can change a group's type — owner only (matches `updateGroupSettings`'s existing owner-only
  precedent), or does this need an approval/payment gate (tiers read like a monetization surface —
  confirm with the user before assuming it's free/self-serve)?
- Downgrade path: what happens if `currentMemberCount > newType.maxMembers`? Reject the downgrade,
  or allow it and let the group sit "over cap" (no further joins until it's back under, per B7's
  `enforceMemberCapacity`)?
- New endpoint shape: extend `PUT /api/groups/{groupId}/settings` with a `groupTypeId` field, or a
  dedicated `PUT /api/groups/{groupId}/type` endpoint?
