# CLIENT-GROUP-SESSION-5 · The recurrence configuration form

**Status:** `DONE` (2026-11-20)
**Type:** New Feature · **Depends on:** SESSION-GROUP-4, CLIENT-GROUP-SESSION-1 (member picker), CLIENT-GROUP-SESSION-4
**Filed:** 2026-11-19, from the owner's group-session specification ("Add button ... Recurrence session creation form, same design as standalone with sections"). Closes GRP-12's scope (game mood).

A modal built on `SessionFormSection` and the shared section components, in this order:
- **Overview:** sport hidden (the group's).
- **When:** a day dropdown (weekday names for Weekly, 1st to 31st for Monthly; the options follow the group's mode), start time, duration, end time (`useSessionTimeFields` linking them); **no date picker**, so `WhenFields` gets a date-less variant.
- **Where:** as standalone, scoped to the group's sport.
- **Who:** All members / Specific with the member picker (no notification at config time).
- **Fee:** free by default. **Attributes:** as standalone, plus the **game mood**.
- **Save:** day and start time are required. If location or duration is missing, a warning "Your recurrence session is missing information" with Keep editing / Save as draft; saving a draft is allowed. On success a dialog with **two texts, by the generation switch (owner, 2026-11-20, set while scoping CLIENT-GROUP-SESSION-4)**, each ending "Do you want to schedule another regular session?" with **No** (closes the form) / **Create more** (clears the form for the next one): *switch ON:* "Your scheduled regular session is saved. Its next regular session will be created soon."; *switch OFF:* "Your scheduled regular session is saved. Regular session generation is OFF, no session is auto generated until you turn it on." (the owner's wording, typos corrected; en and vi; the dialog reads the switch from the settings query). This replaces the earlier "was saved" text and the Add another / Close buttons. Editing an existing slot opens the same form filled.
- **Scope changes (owner, 2026-11-20, Phase 1):**
  1. **Server part, own commit (as in CGS-4):** a recurrence response with a `SPECIFIC` audience carries the audience members resolved (`audienceMembers: [{id, name, avatarUrl}]`, which **replaces** the response's `audienceUserIds` (owner, 2026-11-20: the ids would appear twice; the request keeps `audienceUserIds`), one batch display lookup, deactivated accounts included because it is a display lookup), so Edit can fill the member picker without client lookups. Spock + IT cover it; `GROUP_SESSION_DESIGN.md` and `SERVER.md` updated.
  2. Changing the day of an existing slot is a plain full replace (PUT); the server enforces the 5-per-day limit on the new day.
  3. Game mood: the standalone session form's control, default 5, under Attributes.
  4. No time zone hint in the form (same as standalone).
  5. "Create more" resets everything, as if the form had just been opened (the day too).
- Errors (5 per day, location sport mismatch, permissions) inline with en/vi codes; all strings en and vi; stories (empty, filled, draft warning, saved); tests; MSW handlers; Playwright flow.

**Consumer census:** `WhenFields`/`useSessionTimeFields`, `WhereFields` and the location picker, `useSessionWhoFields` (not reused: this form has its own state), the shared member picker, `GRP-12` ticket (mark superseded), `errors.json`, I18N-4 rows.


**Server contract (SESSION-GROUP-4, built 2026-11-19).** `POST /api/sessions/group/{groupId}/recurrences` (create, takes the group's current mode) and `PUT .../recurrences/{id}` (full replace) with `{ dayKey, startTime, durationMinutes?, locationId?, locationNote?, audience?, audienceUserIds?, feeType?, feeAmountVnd?, feeNote?, gameMood?, attributes? }`. `dayKey` and `startTime` are the only required fields: a missing location, duration or fixed-fee amount is saved as a draft (the response says `draft: true` and `missing`), so the "missing information" warning is the client's (Keep editing / Save as draft) and the save itself never fails for it. Fee defaults to free, game mood to 5. A `SPECIFIC` audience needs at least one member id (no cap). Errors: see CLIENT-GROUP-SESSION-4's contract note.

**Generation is asynchronous (owner decision, 2026-11-19, SESSION-GROUP-5 hardening).** The save answers as soon as the change is committed; the slot a change causes (today's, or the nearest day) is queued at once and generated by a background worker moments later (a second or so, longer if the queue is crowded), so the response never contains the new session and a refetch right after the save may not show it yet. The client says the change is saved and the sessions will appear shortly, in en and vi, and refetches the group's sessions after a short delay (or on the next visit to the Sessions tab). No new field or error code: the worker's failures are retried and never reach the caller.

## Phase 2 findings (2026-11-20)

- **No date-less time fields existed.** `useSessionTimeFields`, `SessionStartTimePicker` and `WhenFields` all work on `yyyy-MM-ddTHH:mm`, so the "date-less variant" is a new hook (`useRecurrenceTimeFields`, `HH:mm`) and component (`RecurrenceWhenFields`), not a flag on `WhenFields`. An end earlier than the start is the next day's (owner, 2026-11-20); an end equal to the start, or a duration of a day or more, is refused.
- **The Overview section would have been empty** (a configuration has no title and no sport field; the server names the sessions it generates), so it is dropped; a one-line intro "A regular session of {group}, created automatically on this day and time." sits on top instead (owner, 2026-11-20).
- **`CreateSessionModal` is 920 lines with two modes already**, so the form is its own `RecurrenceConfigModal` built from the shared section fields (`WhereFields`, `CostFields`, `GroupAudienceField`, `GameMoodSlider`, `SportAttributesFields`, `SessionFormSection`); its data wiring is a new `useRecurrenceFormData` composing the same lower-level hooks. `useCreateSessionModalData` and the standalone and group-session forms are untouched.
- **Consumer census of the response change** (`audienceUserIds` replaced by `audienceMembers`): server `GroupSessionConfigServiceImpl`, its Spock spec (7 assertions) and `GroupSessionConfigIntegrationTest` line 353, `session-impl/CLAUDE.md`, `GROUP_SESSION_DESIGN.md`: updated here; client `sessionConfig/types.ts`, `fixtures.ts`, `e2e/mocks/fixtures.ts`: updated here; the request field `audienceUserIds` (session create and recurrence save) is unchanged; no other consumer.

## Implementation summary (DONE 2026-11-20)

**Server (own commit).** `GroupSessionRecurrenceResponse.audienceMembers: [{ id, name, avatarUrl }]` (new `GroupSessionAudienceMember`, since `session-api` does not see `user-api`) **replaces** the response's `audienceUserIds`. The list collects the distinct audience ids of every row and does **one** `UserService.getUserSummariesByIds` (a display lookup: a deactivated member keeps their real name, an id that no longer resolves is left out, no call at all when nobody has a chosen audience); `POST` and `PUT` name only their own audience. Spock 84 (2 added, 5 changed), `GroupSessionConfigIntegrationTest` 18 (1 added, 1 changed). No table, no migration.

**Client.** New in `features/groups/sessionConfig/`: `useRecurrenceTimeFields.ts` (start, duration and end linked on a wall-clock `HH:mm`, wrap past midnight), `recurrenceForm.ts` (the form's values, the request builder, the Edit prefill, what a configuration is missing), `useRecurrenceFormData.ts` (open state of Add and Edit, the location picker, favourites, the sport's session-attribute schema, the member search, the save mutation; `isSaved` and Create more), `components/RecurrenceWhenFields.tsx`, `components/RecurrenceConfigModal.tsx` (When, Where, Who with the game mood, Cost and Session detail sections; the missing-information warning with Keep editing / Save as draft; the saved dialog with its two texts by the generation switch and No / Create more; a leave confirmation for unsaved entries), and `useSaveGroupSessionRecurrence` in `hooks.ts` (POST or PUT, the answer into the list cache, the group feed and the group's sessions refreshed now and once more 3 seconds later, because generation is asynchronous). `GroupSessionsConfigSection`'s Add and Edit are enabled and open the form (`GroupSessionsConfigData.recurrenceForm`; `useGroupSessionsConfigData` takes the group's sport; `GroupSettingsTab` passes the group name). Required to save: a day and a start, always set (a new form opens on Monday 18:00, free, for everyone, mood 5). Without a location, a duration or a fixed fee's amount the warning offers Keep editing or Save as draft; a specific audience with nobody picked is refused (`SESSION_AUDIENCE_REQUIRED` is never sent). en/vi for everything (`groups.json` `settings.sessions.form.*`); the four `SESSION_RECURRENCE_*` codes and `GROUP_RECURRENCE_LOCATION_SPORT_MISMATCH` show inline. MSW: `POST` and `PUT .../recurrences` (draft, 5 per day, audience members named). Stories: empty, monthly, filled, warning, save failed, saved (ON and OFF).

**Owner correction, same day (2026-11-20):** a draft never generates, so (1) the missing-information warning reads "This configuration is missing the information below. It will be saved as a DRAFT and cannot be used to generate your group sessions until you complete it." with what is missing listed below (Location, Duration, Fee amount; `ChoiceDialog` gained an optional `items` list), and (2) a draft's saved dialog has its own text, "Your regular session configuration is saved as a DRAFT. It cannot be used to generate your group sessions until you complete it. Do you want to schedule another regular session?", whatever the switch says (`isSavedDraft`, from the server's `draft`). The ON and OFF texts apply to a complete configuration only.

**Owner addition, 2026-11-21 (folded into this ticket, own commit): every single-line control is 32px.** `Button` default and `icon` go from 36px to 32px (`sm` already was), `Input` and `Select` from about 42px (`h-auto`, `py-2.5`) to `h-8` with no vertical padding, so a field and a button in one row line up (the recurrence form's Where and When rows showed the mismatch). `Textarea` and the mention composer are untouched. Hand-rolled controls that do not use these primitives (the top bar's notification bell, a comment's delete button, both `size-9`) are unchanged. `client/CLAUDE.md` records the rule; `shared/ui/controlHeight.test.tsx` pins it. Affects every form and dialog in the app, so every baseline that shows a field or a button is expected to change (`BASELINE-UPDATE-1`).
