# CLIENT-GROUP-SESSION-4 · Group settings: the Sessions configuration section

**Status:** `DONE` (2026-11-20)
**Type:** New Feature · **Depends on:** SESSION-GROUP-4; pair of CLIENT-GROUP-SESSION-5 (the form)
**Filed:** 2026-11-19, from the owner's group-session specification ("Configuration"). Replaces the unbuilt UI of GRP-12 (game mood now belongs to the config).

A new collapsible section in `GroupSettingsTab` for group-session configuration; owner/admin edit, members view-only (same hint pattern). It has its **own save semantics** (each action saves at once; it does not join `useSettingsUnsavedGuard`).
- **ON/OFF** control for regular-session generation; when OFF everything below is hidden. (Switch or the tab's existing On/Off pill: pick the existing pill for consistency, decide at pickup.)
- **Recurrence** dropdown (native `Select`): Weekly or Monthly. Switching when configurations of the current mode exist shows the confirm "By switching the recurrence mode, your current configurations are not usable until you switch back." (Stay / Got it); "Got it" switches the mode, which only changes which configurations are active.
- **Add** button next to the dropdown opens the recurrence form (CLIENT-GROUP-SESSION-5).
- **List**, grouped by day (weekday or month-day) in collapsibles (`SessionFormSection`), collapsed by default: title `{Day} (x)`; collapsed it shows each slot's start to end time and location, a missing field as a warning and a "Draft" status, ordered by start ascending; expanded, one row per slot with Edit and Delete (Delete confirms, hard delete). Only configurations of the active mode are listed.
- All strings en and vi (weekday and ordinal names localised), I18N-4 rows for the new error codes, stories, tests, MSW handlers, Playwright flow. Extends `group-settings.spec.ts`.

**Consumer census:** `GroupSettingsTab`, `useGroupSettings`, `feedKeys`, `useSettingsUnsavedGuard` (unchanged), `groups.json`, e2e mocks, `BASELINE-UPDATE-1`. The 5-per-day limit and the other SESSION-GROUP-4 errors are shown inline.

**Out of scope:** the cancel confirmations on OFF, delete and mode switch (CLIENT-GROUP-SESSION-6).


**Server contract (SESSION-GROUP-4, built 2026-11-19).** `GET/PUT /api/sessions/group/{groupId}/settings` (`{ enabled, mode }`, partial update, `WEEKLY` | `MONTHLY`; a switch changes no configuration) and `GET/POST/PUT/DELETE /api/sessions/group/{groupId}/recurrences[/{id}]`. The list returns every configuration of both modes (filter by `mode` to the group's current one; configurations of the other mode are the ones the switch confirm is about), each with `draft`, `missing` (`locationId`, `durationMinutes`, `feeAmountVnd`), `audience`, `audienceUserIds` and `startTime` (`HH:mm:ss`). Errors to give en/vi copy and an I18N-4 row: `SESSION_RECURRENCE_DAY_LIMIT` (409, `{limit}`), `SESSION_RECURRENCE_DAY_INVALID`, `SESSION_RECURRENCE_START_REQUIRED`, `SESSION_RECURRENCE_NOT_FOUND`, `SESSION_AUDIENCE_REQUIRED`, `SESSION_AUDIENCE_NOT_MEMBER`, `GROUP_RECURRENCE_LOCATION_SPORT_MISMATCH` (already has copy). Each change also writes a group feed post: add the en/vi text for the six `systemCode` values `GROUP_SESSION_RECURRENCE_ADDED`, `_UPDATED`, `_DELETED`, `GROUP_SESSION_GENERATION_ON`, `_OFF`, `GROUP_SESSION_MODE_CHANGED` (params `name`, `mode` = `WEEKLY`|`MONTHLY`, and for the three recurrence ones `day` = the weekday 1-7 or the day of the month, `time` = `HH:mm`) in `enums`/the post renderer (CLIENT-I18N-5 rule); until then the stored English text shows. The group's sport and a location of that sport are the only location choice; the form has no date, no sport and no taken/open slots.

**Generation is asynchronous (owner decision, 2026-11-19, SESSION-GROUP-5 hardening).** The save answers as soon as the change is committed; the slot a change causes (today's, or the nearest day) is queued at once and generated by a background worker moments later (a second or so, longer if the queue is crowded), so the response never contains the new session and a refetch right after the save may not show it yet. The client says the change is saved and the sessions will appear shortly, in en and vi, and refetches the group's sessions after a short delay (or on the next visit to the Sessions tab). No new field or error code: the worker's failures are retried and never reach the caller.

## Scope change (owner, 2026-11-20, at pickup)

Answers to the Phase 1 questions and three small changes to the existing settings tab, all in this ticket:

- **Add and Edit are disabled** until CLIENT-GROUP-SESSION-5 builds the form (the list, ON/OFF, the mode switch and Delete work in full). The "saved" dialog text the owner gave (two texts by the switch, No / Create more) is the form's, so it was written into CLIENT-GROUP-SESSION-5.
- **The "sessions will appear shortly" line** (generation is asynchronous, a save is confirmed and the new session is not waited for) **belongs to adding/updating a configuration, not to the ON/OFF switch**: it is the saved dialog of CLIENT-GROUP-SESSION-5 (see there). Nothing of it is built in this ticket. (Revised 2026-11-20, see the second scope change.)
- **Every section of the settings tab is collapsed by default** (General, Permission and the new Sessions section; today the first two open expanded).
- **The Save button moves into the Permission section.** It used to be one shared button for Permission *and* the General section's Rules and Schedule text, so, decided with the owner: **Rules and Schedule save on blur** (like Privacy saves on click), and the Save button is Permission's only (the three toggles are owner-only, so an admin sees no Save). `useSettingsUnsavedGuard` then guards the Permission draft only; Rules/Schedule failures show inline on their field.
- **Leave group asks for confirmation first** (a confirm dialog, en and vi; "Leave" / "Stay"), then calls the existing leave; the owner's disabled state and the leave error line stay.

## Second scope change (owner, 2026-11-20, at the Phase 3 design)

**The ON/OFF switch asks for confirmation (owner's wording, typos corrected; en and vi):**
- **To ON:** "By switching this feature ON, your regular sessions will be generated automatically from the group's recurrence configurations. Are you ready?" with **Let me check again** / **Got it, turn on**.
- **To OFF:** "By switching this feature OFF, your regular sessions will stop being generated. The sessions already scheduled will stay here. Is that OK?" with three choices: **Hold on, don't turn off** (closes, nothing changes) / **No, cancel the remaining sessions and turn off** (`PUT .../settings` `{ enabled: false, cancelScheduled: true }`) / **Yes, keep them and turn off** (`{ enabled: false, cancelScheduled: false }`, same as omitting it). The dialog is always shown (no count lookup); a cancel refreshes the group's sessions (they leave the Scheduled section).
- **Effect on CLIENT-GROUP-SESSION-6:** its OFF prompt is built here, in this ticket, so CLIENT-GROUP-SESSION-6 keeps the **delete-a-configuration** and **mode-switch** prompts only (it also still owns the count lookup for them). *(Pending the owner's confirmation of this split; CLIENT-GROUP-SESSION-6's ticket is edited once confirmed.)*
- The mode-switch confirm and the delete confirm of this ticket are unchanged (no cancel option until CLIENT-GROUP-SESSION-6).

**Location names in the list: a small server part, folded into this ticket (owner, 2026-11-20), its own commit, built first.** The configuration list shows each slot's location, but `GroupSessionRecurrenceResponse` carries only `locationId`; a session response already embeds a resolved `location` (`LocationResponse`: name, address, coordinates, sport) through the batch `LocationService.getLocationsByIds`. So the recurrence response gets the same `location` field:
- **Server (session-impl, `GroupSessionConfigServiceImpl`):** `GroupSessionRecurrenceResponse.location` (`LocationResponse`, null when the configuration has no location or the location is no longer available); the list resolves the distinct location ids of all configurations in **one** `getLocationsByIds` call (no per-item lookup), `POST`/`PUT` resolve the single location of the saved row. `locationId` stays (additive change). Consumer census: `GroupSessionConfigController`, `GroupSessionConfigServiceImpl` (the only producers), `GroupSessionConfigServiceImplSpec`, `GroupSessionConfigIntegrationTest`, the generator (reads the entity, not the response), the client (no code yet) and its MSW mocks (new in this ticket): all **compatible as-is** or **updated here**. No migration, no new error code, no client-mirrored enum.
- **Tests:** Spock (one batch for many configurations, no lookup when no configuration has a location, create/update carry the location, an unresolved location is null) and the real-wiring `GroupSessionConfigIntegrationTest` asserting `location` in the list and create responses.
- **Docs:** `GROUP_SESSION_DESIGN.md` § 4 (the response field), `documentation/release-notes/SERVER.md` under `## Unreleased` (Changes: the field; no manual actions; rollback: none needed, additive), and the client reads `recurrence.location` (no `useLocationsById` hook, no per-location requests).
- The client part of this ticket **depends on** this server part (same branch, two commits: server first).

Checks re-run: *account lifecycle* the ON/OFF and cancel calls are owner/admin on the server (`cancelScheduled` is ignored unless the call turns generation off or switches the mode); a deactivated caller is refused by the per-request gate; *client-visible enum or event type* none new (the cancelled sessions' notifications use existing types); *i18n* five new dialog strings sets in en and vi (ON, OFF with three buttons); *duplicates checked* against CLIENT-GROUP-SESSION-6 (the OFF prompt overlaps it, hence the split above) and against the session backlog (SESSION-GROUP-1 to 12: no ticket adds the location to the recurrence response, so it is folded here, not filed).
