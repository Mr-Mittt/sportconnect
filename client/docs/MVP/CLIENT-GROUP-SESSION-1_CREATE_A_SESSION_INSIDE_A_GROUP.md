# CLIENT-GROUP-SESSION-1 · Create a session inside a group (group mode of the create form)

**Status:** `DONE` (2026-11-19)
**Type:** New Feature · **Depends on:** SESSION-GROUP-1 and SESSION-GROUP-2 (`modules/session/docs/MVP/`; both merged)
**Filed:** 2026-11-19, from the owner's group-session specification ("Custom session ... Creation: share the creation form with standalone session").

The client cannot create a group session today: `CreateSessionModal` never sends `groupId` and has no sport lock. New **group mode** (a `group` prop with the group's id, sport id and name; entry point is the group's Sessions tab, CLIENT-GROUP-SESSION-2), same sections as the standalone form with these differences:
- **Overview:** the sport select is hidden (the `sportField` slot is simply omitted) and the sport is the group's; the form must not re-seed on a sport change (`seededForSport` logic keys off the locked sport).
- **Who:** the visibility switch and its warning are absent (a group session is never public); taken/open slots and the gender split are absent (a group session shows no slot information); in their place **two radios, "All members" (default) and "Specific"**. Specific opens a **member picker**: server search through `useGroupMemberSearch` (`GET /groups/{id}/members/search`, B23), removable badges as the friend picker has, no limit on the number picked. The picker is a small shared component with a `{id, name, avatarUrl}` adapter, so CLIENT-GROUP-SESSION-5 and -3 reuse it (extract `isGroupManager(role)` while there: the role strings are repeated in four files).
- **Auto approve:** on by default; the confirm dialog for turning it on does not show for a group session.
- **Payload:** `CreateSessionPayload` sends `groupId`, `audience` (`ALL_MEMBERS`|`SPECIFIC`) and `audienceUserIds`; `isPublic` is not sent.
- **Errors:** the new SESSION-GROUP-1 codes get en/vi entries in `errors.json` and a row in the I18N-4 census; an `SPECIFIC` audience with nobody picked is a client validation message.
- All new strings en and vi; stories (group mode, Specific with picks); tests; MSW: the create handler accepts `groupId`/`audience`, refuses a non-member.

**Consumer census:** `CreateSessionModal` and its four page instances (`MatchesPage`, `GroupsPage`, `HomeFeedPage`, `FriendsPage`), `useCreateSessionModalData`, `useSessionWhoFields`, `SessionSectionFields`, `CreateSessionPayload`, e2e mocks.

**Out of scope:** editing the audience after creation, the Sessions tab (CLIENT-GROUP-SESSION-2), sharing (-3).

---

**Server contract (built 2026-11-19; the whole contract is `modules/session/docs/GROUP_SESSION_DESIGN.md` § 4.1).** `POST /api/sessions` with `groupId` is open to any member (`403 SESSION_GROUP_MEMBER_REQUIRED` otherwise); the group's sport is used and `sportId` is ignored (the client hides the sport and sends none); `audience` is `ALL_MEMBERS` (default) or `SPECIFIC` with `audienceUserIds` (at least one other member, no upper limit; `400 SESSION_AUDIENCE_REQUIRED`, `400 SESSION_AUDIENCE_NOT_MEMBER {count}`); `autoApprove` defaults to `true` for a group session when omitted; `isPublic` is ignored (a group session is never public); the creator is `JOINED`. The answer is the usual `SessionResponse` and does **not** carry the audience. Add en and vi copy for the three error codes.

---

**Scope change (2026-11-19, owner, at pickup): a "Session" shortcut on the group's Posts tab.** Added because the Sessions tab (CLIENT-GROUP-SESSION-2) is not built yet and a member should see and start group sessions from where the group's activity is.

- **Where:** the group's **Posts** tab, directly under the post composer, above the feed. A collapsible section titled "Session", **expanded by default** (the collapse state is page-local, not persisted). Shown to **members only** (the list endpoint answers `403 SESSION_GROUP_MEMBER_REQUIRED` to anyone else, so the section is not rendered for a non-member).
- **Content:** a horizontal **slider** (scroll-snap row of short session cards; no new dependency, keyboard reachable) holding **today's sessions that are `ONGOING` or `SCHEDULED`** (ongoing first, then by start time), then a **placeholder card with "+"** that opens the group-mode create form of this ticket. Owner's decision: **no completed session is shown** (the first wording also listed the last completed one and today's completed ones; dropped because that needs the `HISTORY` bucket, which mixes completed and cancelled and has no date filter). A session leaves the slider when it completes.
- **The "+" placeholder is the entry point** of the create form (so no separate header button).
- **Not in the slider:** `PREPARING` drafts, `COMPLETED` and `CANCELLED` sessions. A card opens the session detail (`SessionDetailModal`), like every other session card.
- **Empty:** with nothing ongoing or scheduled today, the slider is just the "+" placeholder.
- **Data:** the existing `GET /api/sessions/group/{groupId}?bucket=ONGOING` and `?bucket=SCHEDULED` (SESSION-GROUP-2; soonest first, small page), merged and filtered to "today" on the client by one `useGroupSessionShortcutData` hook. No server change. Limit to document: more sessions on the page size than fit are cut off (rare: a group has at most 5 configurations a day plus custom sessions).
- **"Today":** the session's own timezone, `session.location.timezone` (a nullable field of the location in the session response), compared with today's date in that same zone; when it is null (no location, no coordinates, or outside every timezone area) the **viewer's** zone is used. `scheduledStart` itself is a raw UTC instant with no zone (SESSION-33).
- **Card:** the standalone session card, with **the joined count only** (`participantCount`) for a group session: no capacity, no taken or open slots, no gender split. This rule moves here from CLIENT-GROUP-SESSION-2, which reuses it.
- **Strings and checks:** section title, placeholder label and the load error in en and vi; stories (expanded with cards, only the placeholder, collapsed, loading); tests (today in another timezone, null timezone fallback, ongoing before scheduled, a draft never listed); MSW handler for the two bucket calls; a Playwright flow (open the Posts tab, see the shortcut, "+" opens the group-mode form, create, the new session appears).

**Scope change 2 (2026-11-19, owner, at pickup): the host and the group's owner/admin can manage and cancel a group session.** Found while planning: once any member can create a group session, the client still lets only the group's owner/admin manage one, and the cancel button was removed from the session detail after CLIENT-SESSION-10 (user decision), so there is no way to cancel a session in the UI at all.

- **`isGroupManager(role)`** is extracted (reverses the first recommendation to skip it): one helper in `shared/lib/groupRole.ts` for "owner or admin" (`'group_owner'` or `'group_admin'`), used by `useSessionDetailModalData` (`CAN_MANAGE_ROLES`), `useGroupMembersTabData`, `useGroupsPageData` (`canBroadcast`) and `GroupSettingsTab`; no behaviour change there. Its own commit.
- **`canManage` for a group session** in `useSessionDetailModalData` becomes: the host (`session.createdBy` is the caller) **or** a group owner/admin, the same rule as the server (`GROUP_SESSION_DESIGN.md` § 4.3: the creator while still a member, or the owner/admin). Today it is the owner/admin only, so a host who is a plain member could not edit their own `PREPARING` session, schedule it or see its approval queue. A standalone session is unchanged (the creator).
- **Cancel a group session:** a cancel action in the session detail for anyone who `canManage` a group session whose status is `PREPARING`, `SCHEDULED` or `ONGOING` (the server answers `409 SESSION_NOT_CANCELLABLE {status}` for `COMPLETED` or `CANCELLED`), through the existing `useCancelSession` hook, with a confirm dialog and an optional reason. The server tells the audience and the joined players (`session.group.cancelled`; its notification text is CLIENT-GROUP-SESSION-3). The cancelled session leaves the shortcut slider.
- **Decided (owner):** the cancel action is in the **session detail only**, for a **group session only** (a standalone session keeps having no cancel button); the confirm dialog asks for an **optional reason**. Not on the shortcut card.

## Implementation summary (2026-11-19)

**Design as approved** (owner, after the UI draft `client/design-reference/design-reference-group-session-shortcut.html` and two scope changes, above): the create form gains a **group mode** (a `group` prop); the group's **Posts** tab gains a collapsible **"Session" shortcut** (today's ongoing and scheduled sessions, then a "+" card); a group session is managed by its **host or a group owner/admin** and can be **cancelled** from the detail. Client only; no server change.

**What was built**
- **Shortcut:** `GroupSessionShortcut` (`features/groups/components/`), under the post composer in `GroupsPage`: a collapsible section (expanded by default, state local), a scroll-snap row (focusable region, every card reachable by Tab), today's `ONGOING` sessions first, then `SCHEDULED`, then the dashed "+" card (a wide "+" row when nothing is on today); loading placeholders; a retry line on a failed load that keeps the "+" usable. Data: `useGroupSessionShortcutData` over `useGroupSessionBucket` (`GET /sessions/group/{id}?bucket=ONGOING|SCHEDULED&size=20`, SESSION-GROUP-2), merged on the client; a status guard on top of the bucket; `sessionKeys.groupSessions` sits under `sessionKeys.all`, so every session write refreshes it. "Today" is `isSessionToday` (`shared/lib/sessionToday.ts`): the **location's** timezone when the session has one, otherwise the viewer's (`Location.timezone` is now typed, optional).
- **Card:** `SessionCard` shows `formatJoinedCount` ("9 joined") for any session with a `groupId`, and no gender split. It is shared, so the right-rail and the Matches lists show the same for a group session.
- **Create form, group mode:** `CreateSessionModal` `group` + `audienceSearch` props. The sport select is gone (round 2: an intro line and a title pre-filled "{group name}'s session" instead), the "add a sport first" gate is skipped, auto approve is on by default with no confirm popup, there is no visibility switch, no taken/open slot, no gender split and no friend invite (`WhoFields` got `hideSlots` and `audienceField`). `GroupAudienceField`: **All members** (default) or **Specific members** with the shared `MemberPicker` (removable badges, no limit, the group member search B23 through `useCreateSessionModalData.audienceSearch`, the caller never offered: `toAudienceResults`). Payload: `groupId`, `audience`, `audienceUserIds`, `capacity: 9999` (`UNCAPPED_CAPACITY`, the server still requires one); no `sportId`, `isPublic`, `initialSlot`, `inviteeIds`. "Specific" with nobody picked is a client message. `openCreateGroupSessionModal(group)` is a separate function from `openCreateModal()` because pages hand the latter to `onClick`.
- **Host and manager:** `isGroupManager(role)` (`shared/lib/groupRole.ts`) replaces the four hand-written owner/admin checks (members tab, broadcast, settings, session detail). `canManage` in `useSessionDetailModalData` is now **the host, or a group owner/admin** (the server's rule), so a host who is a plain member can edit and schedule their own draft and see its join-request queue.
- **Cancel:** a "Cancel session" button in the session detail for `canManage` on a **group** session in `PREPARING`, `SCHEDULED` or `ONGOING`, and `ConfirmCancelSessionDialog` (optional reason up to 500 characters, trimmed, "Keep session" the primary choice), through the existing `useCancelSession`. A standalone session still has no cancel button (decided).
- **i18n (en and vi):** `groups.sessionShortcut.*`, `session.create.audience.*`, `session.create.groupLocked`, `session.create.validation.audience`, `session.detail.summary.audience*`, `session.detail.cancelSession*`, `session.capacity.joined`, `sharedComponents.memberPicker.*`, `errors.codes.SESSION_AUDIENCE_REQUIRED` and `SESSION_AUDIENCE_NOT_MEMBER {count}`. I18N-4 census row added. `SESSION_GROUP_MEMBER_REQUIRED` and `SESSION_NOT_CANCELLABLE` already had copy and are already shown by the app-wide session error dialog.
- **MSW:** `POST /sessions` honours `groupId` (403 for a group the caller is not in), `audience` (the two 400 codes), joins the creator and defaults `autoApprove` for a group session; `GET /sessions/group/:id` filters by `bucket` and `size` and re-times the owned group's fixture session to noon today for the shortcut.

**Divergences from the plan:** none of substance. Two things came out of building: (1) `openCreateModal` could not take the group as an argument (event argument from `onClick`), hence the separate opener; (2) the card rule moved from CLIENT-GROUP-SESSION-2 into this ticket (scope change 1), so the rail and Matches lists changed too.

**Known limits (documented, not bugs):** one page (20) of each bucket is read, so more than 20 sessions in one status are cut off; a session with no location timezone is "today" on the viewer's clock; the shortcut does not poll, it refreshes on a session write, on mount and on window refocus (TanStack Query defaults).

**Delta for later tickets:** CLIENT-GROUP-SESSION-2 reuses the card and keeps only the `SessionDetailModal` slot rows; CLIENT-GROUP-SESSION-3 owns the `session.group.cancelled` notification text; CLIENT-GROUP-SESSION-5 can reuse `MemberPicker`.

- **Found in use (owner, 2026-11-20), two bugs after leaving a group:**
  1. **The Upcoming rail keeps the group sessions of a group the user has left.** Root cause on the server: `GET /sessions/upcoming` (and requested and history) select a session through the caller's participant row only, and leaving a group never touches it, while the detail gate asks for group membership (403). **Filed as server ticket SESSION-GROUP-12** (session backlog; the lists will list a group session only while the caller is a member of the active group). Client part, done here: `useLeaveGroup` drops the cached session queries nothing shows (`removeQueries`, `type: 'inactive'`) and invalidates the session lists, so the rail refreshes at once.
  2. **A session opened from a notification after leaving showed the access message and the session's information.** Root cause: the detail query is TanStack Query, which keeps the last good `data` when a refetch fails; the modal rendered the session whenever `data` existed, whatever the error. Fixed in `useSessionDetailModalData`: when the load failed with a 403 or 404 (`getApiError(error).category`) the session, its players and `canManage` are not returned, so only the no-access / not-found message shows; any other failure (network, 500) keeps the cached session. Tests: `useSessionDetailModalData.lostAccess.test.tsx` (403, 404 hide; 500 keeps), `useLeaveGroup.test.tsx`; mutation check 6/6 killed.
- **Question answered:** a group member who has not joined may log results on the **server** (SESSION-50: `SessionRecordGate`, group session = any group member, standalone = `JOINED`; the named players must be `JOINED`), but the **client** (CLIENT-GL-38, `getResultAccess`) lets only a `JOINED` participant edit and shows a non-joined member the Result section read-only.
