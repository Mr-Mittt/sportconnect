# CLIENT-SESSION-49 · "Share" a session with friends from the Players section header

**Status:** `DONE` (2026-11-18)
**Type:** New Feature · **Depends on:** SESSION-66
**Filed:** 2026-11-17 as "Invite friends from the Players section header", owner decision (the standalone-session list: finish the standalone session first, then group and group sessions), checked against the existing backlogs and filed in the same planning pass. **Renamed 2026-11-18 (owner): the feature says "share" everywhere, never "invite"** (see Scope changes).

In the session modal's Players section header a **Share** button (an icon button, a share icon, `aria-label` "Share this session") opens a **Share with friends** dialog. **Scope change (owner, 2026-11-18):** shown to **every viewer** of a **standalone** session, **whatever the session's status and whatever the viewer's own participation** (joined, requested, invited, left, or not in it at all); hidden only for group sessions (those come after the standalone chain). It was first filed as "a `JOINED` caller only, `PREPARING` or `SCHEDULED` only".

**Dialog.** All of the caller's friends, one row each: avatar and name on the left (the same friends hook and row look as the create form's friend field; the name filter is the shared name rule from CLIENT-GL-50). **Not joined** friends (including `REQUESTED` and `INVITED`) are listed first, each with a checkbox. **Joined** friends are listed below, the text "Joined" right-aligned, no checkbox. "Joined" comes from the players list the session modal already loaded (**scope change, owner, 2026-11-18**: no extra query). Known limit: that list is the first page of the participants endpoint (20); a joined friend beyond it shows with a checkbox, and ticking them is harmless because the server skips them. The footer button reads **Share (x)** with x the number of **newly** ticked friends and is disabled at 0. Sending calls `POST /api/sessions/{id}/shares`.

**After a send (scope change, owner, 2026-11-18).** The dialog stays open. A short **generic** line confirms it inline ("Session shared." in en/vi; it does not say how many, because `sent` can be lower than the ticks). The friends just sent to **stay ticked but become disabled** (they count as already shared with), and **x resets to 0** and counts only the new ticks made after that. The line clears on the next tick.

**The limit of one turn (scope change, owner, 2026-11-18).** The server takes 1 to 50 friends per call. Once **50 are newly ticked** the dialog shows a generic **warning in the footer** ("You reached the limit of one sharing turn." in en/vi, amber warning style, text carries the meaning) and **disables every unticked checkbox**; the ticked ones can still be unticked, which lifts the warning and the disabling. Friends already sent to (ticked and disabled) do not count toward the 50.

**Errors (scope change, owner, 2026-11-18).** A 404 `SESSION_NOT_FOUND` or a 403 `SESSION_SHARE_NOT_ALLOWED` shows an **information dialog** with its en/vi text and a **"Got it"** button, which also closes the sharing dialog. `VALIDATION_FAILED` cannot be sent by the UI (the button is disabled at 0 and capped at 50). Any other failure shows the generic inline error and keeps the ticks.

**Server change, folded into this ticket (owner, 2026-11-18), first and separate commit.** SESSION-66 is corrected so the feature is one idea, "share", from the endpoint to the notification text:
- the **status rule goes**: no `SESSION_NOT_SHAREABLE` (409), a share works whatever the session's status (ONGOING, COMPLETED and CANCELLED included);
- the **participant rule goes**: `SessionShareGate` lets any caller share a standalone session; only a **group session** is still refused (403 `SESSION_SHARE_NOT_ALLOWED`, which now means exactly "this is a group session", for everyone);
- **its own event and notification, no longer the invitation one** (reverses the 2026-11-18 SESSION-66 decision "reuse the invitation type"): the outbox row is `session.share.created` (`SessionShareCreatedEvent`: `sessionId`, `actorId`, `recipientUserId`), one per recipient, consumed by `notification-impl`'s `SessionEventsConsumer` as a single-recipient notification that opens the session. The key has three words on purpose: the notification queue is bound with `session.*.*`, so `session.shared` would never reach the consumer. `session.invitation.created` is back to meaning only a creation-time invitation (its Javadoc loses "also used by shares").
Unchanged: the 404 for an unavailable session, the friends-only recipients, the silent skips (non-friends, deactivated, the caller's own id, already `JOINED`/`REQUESTED`/`INVITED`), `{ sent, skipped }`, the 1 to 50 limit, no participant row, no system comment. Touches `SessionServiceImpl`, `SessionShareGate`, the new event, `SessionEventsConsumer`, their Spock specs, `SessionShareIntegrationTest`, `SessionEventsConsumerIntegrationTest` (the real path of the new key), the `SessionService` and `SessionInvitationCreatedEvent` Javadoc, `ERROR_CODES.md` (drop the 409 row, reword the 403), `session-impl/CLAUDE.md`, `NOTIFICATION_USE_CASES.md` NOTIF-13, the SESSION-66 ticket (Deltas), `SERVER.md` release notes and `PROGRESS.md`. Nothing is released yet, so no stored `session.invitation.created` notification needs converting. Consequence recorded, not a decision to revisit here: any user can now notify up to 50 of their friends per call about any standalone session, with no rate limit.

**The notification on the client (CLIENT-NOTIF-4, in this ticket).** `session.share.created` is added to the `NotificationType` union, with its `getNotificationText` case: "{name} shared "{session}" with you" / "{name} đã chia sẻ "{session}" với bạn" (`enums:notifications.sessionShareCreated*`), a row in `notificationText.test.ts`, the MSW notification fixture, and the click opens the session like the other session notifications.

**en/vi** for every new string (the button's label, the dialog title, filter placeholder and label, "Joined", "Share (x)", the inline "Session shared." line, the limit warning, "Got it" (the existing app-wide dialog's), empty list "You have no friends to share with yet.", no filter match, the generic inline error, the error code `SESSION_SHARE_NOT_ALLOWED`; `SESSION_NOT_SHAREABLE` is no longer a code), the notification text above, the I18N-4 census row for this dialog, `EmptyHint` for the empty states, a new Radix checkbox primitive (`@radix-ui/react-checkbox`, owner-approved 2026-11-18) restyled with tokens, MSW handler and fixtures for the endpoint, the dialog title centered as every dialog.

**Server contract (SESSION-66, 2026-11-18, corrected by this ticket's server commit).** `POST /api/sessions/{id}/shares` with `{ "userIds": [...] }` (1 to 50) answers `{ sent, skipped }` (`data`). `sent` can be lower than the number ticked: anyone who is no longer a friend (silently, no error), friends who joined, requested or were invited in the meantime, and friends deactivated since the list loaded are skipped. A friend who left the session earlier is notified again. Errors: 403 `SESSION_SHARE_NOT_ALLOWED` (a group session), 404 `SESSION_NOT_FOUND`, and the generic `VALIDATION_FAILED`.

**Out of scope:** Group sessions, sharing with people who are not friends, seeing who was already notified, host approval of a share, a rate limit on shares, fetching every joined participant for the grouping, splitting more than 50 friends into several calls.

**Tests:** Vitest for the dialog (grouping, order, selection count, disabled at 0, filter, sent friends stay ticked and disabled, x resets, the 50 cap and its warning, un-ticking lifts it, errors) and for the notification text, a scoped e2e (open, tick two, send, request body, the 404 dialog), Storybook states; the server commit has its own Spock and IT changes; the changed client surface goes into `BASELINE-UPDATE-1`, no baseline is regenerated.

## Implementation summary (2026-11-18)

**Design as approved** ("nothing", 2026-11-18, after two owner corrections of the first plan: the feature says "share" and never "invite", including a notification of its own; at 50 ticks a footer warning shows and the unticked boxes are disabled). Built as designed, with the divergences listed below. Two commits on this branch: the server correction first, then the client.

**Server (first commit, SESSION-66 corrected).** `SessionShareGate` lets any identified caller share a standalone session (no participant read any more; a group session is still 403 `SESSION_SHARE_NOT_ALLOWED`); the status rule and `SESSION_NOT_SHAREABLE` are gone; the outbox row is the new `session.share.created` (`SessionShareCreatedEvent`) and `SessionEventsConsumer` turns it into a single-recipient notification. The key has three words because the notification queue is bound with `session.*.*` (found in the census; `session.shared` would have been dropped). Details, consumers and verification are in SESSION-66's Correction section.

**Client (second commit).**
- `shared/ui/checkbox.tsx`: a Radix checkbox (`@radix-ui/react-checkbox` 1.3.3, owner-approved), controlled, tokens only, the ticked one stays visible when disabled.
- `hooks/useShareSession.ts`: `POST /sessions/{id}/shares`, `SHARE_LIMIT = 50` (the one place the limit is set; the server's `ShareSessionRequest.MAX_RECIPIENTS` is the other end of the contract), a coded 404 / 403 goes to the app-wide session error dialog, anything else stays on the mutation. No query is invalidated (a share changes nothing in the session).
- `components/ShareSessionDialog.tsx` (presentational; its filter, ticks and sent set are local and start fresh each open): not-joined friends first with a checkbox, joined ones below with "Joined", the shared name filter, "Share (x)" counting only the ticks made since the last send, a generic "Session shared." line, sent friends ticked and disabled, the footer warning and the disabled unticked boxes at `SHARE_LIMIT` (ticked ones can still be unticked; friends already sent to do not count).
- `components/ShareSessionButton.tsx` (icon-only, `aria-label` and tooltip "Share this session") placed in `SessionFormSection`'s `actions` (read-only layout) and, in the host's editable layout, in a rebuilt header row: the toggle (its `::after` stretches over the row so the chevron still toggles), the button above it, the chevron as an `aria-hidden` icon. Shown for `session.groupId === null` only, in every status and for every viewer. `SessionDetailModal` takes an optional `share` slice; the six pages that host it pass `share={...share}`.
- `useSessionDetailModalData` owns the slice: friends fetched only while the dialog is open (`useFriends(open)`), `onShare(ids, onDone)`, reset with the session. `sessionErrors.ts`: `SESSION_SHARE_NOT_ALLOWED` joins the stay-open dialog codes and `useCloseOnSessionErrorDismissal` closes the Share dialog when the error dialog its own failure opened is dismissed.
- Notification (CLIENT-NOTIF-4): `session.share.created` in the `NotificationType` union, its `getNotificationText` case ("{name} shared "{session}" with you"), en/vi.
- en/vi: `session:detail.share.*`, `errors:codes.SESSION_SHARE_NOT_ALLOWED`, `enums:notifications.sessionShareCreated{Prefix,Suffix}`; I18N-4 census row added.
- MSW: `POST /api/sessions/:id/shares` (404, 403 group, 400 empty or over 50, already-in friends skipped).

**Divergences and non-obvious points.**
- The "Joined" label comes from the players the modal already loaded: the first page of the participants endpoint (20). A joined friend beyond it shows with a checkbox; ticking them is harmless because the server skips them. Owner's choice (option 1), unchanged.
- No MSW notification fixture was added for the bell: a new default fixture would move the notification-bell baselines and counts in other specs; the text is covered by `notificationText.test.ts`.
- The unit tests of the limit mock `SHARE_LIMIT` to 3: the first version ticked 50 boxes, took about 13 s per case under load and timed out in the wide run (the only failures of that run). The real 50 is asserted in `useShareSession.test.tsx`, enforced by the server IT (51 ids is `VALIDATION_FAILED`) and driven in a browser by the e2e spec.
- A Share dialog rendered in the same first render as the session modal is `aria-hidden` (Radix hides the portals that exist when a modal mounts); in the app it opens later, so the tests open it with a rerender.
- `initialsFor` is now in three components; left as is (extracting it touches unrelated files).
