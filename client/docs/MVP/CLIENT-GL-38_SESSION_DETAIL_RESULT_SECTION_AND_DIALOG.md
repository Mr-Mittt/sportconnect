# CLIENT-GL-38 · Session detail: collapsible Result section and nested edit dialog

**Status:** `DONE`
**Type:** Feature · **Depends on:** SESSION-50 (session backlog) ·
**Filed:** 2026-11-12, Filed 2026-11-12 by the `/feature` session "game logging" (BA document `D:\Planning\business-analyst\Requirements - Games, Statistics and Leaderboards.md`; design: `modules/session/docs/SESSION_RECORDS_DESIGN.md`).

In the session detail modal, under Players, a collapsible "Result / Kết quả" section, collapsed by default, shown for ONGOING/COMPLETED sessions whose sport has a result schema. It shows a client-computed scoreboard (games, wins, losses, net points from the schema's points rule) and the record list; the header "Update" button opens a nested dialog to add, edit and delete records.

The UI is built from the sport's result schema and the client validates the list (side sizes, no player on both sides, winner set, `maxRecords`, size). The dialog is a draft: it keeps each existing row's database `id` hidden (the #1, #2, #3 shown are display positions by creation order only), gives new rows a client UUID (`clientRef`), and on Save sends only the diff against its snapshot as one change set to `POST /api/sessions/{id}/records/changes`, then replaces its state with the response's fresh list. Disabled after the 24-hour window. Mobile first, one-handed, at most three taps once the players are chosen. En/vi copy including the `SESSION_RECORD_*` error codes (`errors:codes`), the sport's labels, MSW handlers, hand-mirrored types. **Contract (2026-11-13):** each add and update sends `playerIds` (every user named in `data`) beside `data` so the server can check they are `JOINED`; the server stores only `data`, so the list response has no `players` field and the client reads players, sides, winner and scores from `data`. On load the client validates each record's `data` against the sport's result schema and skips (does not show) one that fails. There is no audit endpoint.

**Out of scope:** Chat commands (SESSION-GL-51 / CLIENT-GL-39), guests, shortcuts, offline queue, duplicate warning, sharing, statistics views.

**Tests:** Vitest for the section, the dialog, the diff logic, the schema-driven validation and the scoreboard math; a scoped Playwright flow with MSW; requirement-by-requirement mutation check. Release-note lines in `documentation/release-notes/CLIENT.md`.

**Contract note (2026-11-13, SESSION-50):** `POST .../records/changes` answers 200 with one result per operation even when some are bad: a refused one has `status: "REJECTED"`, `errorCode` (`SESSION_RECORD_INVALID`, `_TOO_LARGE` with `errorParams.maxBytes`, `_PLAYER_NOT_JOINED`, `_LIMIT_REACHED` with `errorParams.maxRecords`) and its `clientRef` (add) or `requestedId` (update). The valid ones are already saved and `records` is the fresh list. After Save, keep only the rejected rows in the dialog, mark each with the en/vi copy of its code, and let the player fix or remove them; only a 400 `SESSION_RECORD_INVALID` without `results` means the whole request was malformed. Add the `REJECTED` status to the mirrored status type.

**Scope decisions (2026-11-13, `/workon client`, owner's answers):**
- **Who edits:** any `JOINED` participant of the session. A group member who is not `JOINED` sees the section read-only (scoreboard and list, no Update button).
- **24-hour window:** the client disables Update from its own clock (`scheduledEndAt + 24h`) and also shows the server's `SESSION_RECORD_WINDOW_CLOSED` if it still arrives; the server stays the source of truth.
- **No result schema for the sport:** the section is hidden.
- **Which kinds:** not limited to `MATCH` / `WINNER_ONLY`. The sport's result schema decides what the section and dialog show (the UI is built from the schema).
- **Row action slot (replaces a plain per-row remove):** in the record dialog every record has one action slot on its right side.
  - Initial state: a red X (delete). Pressing it marks the row deleted: its text is struck through and the slot turns into a blue circular-arrow undo.
  - If the user edits anything in a row, the slot turns into the blue undo. Undo restores the row to its initial state (the snapshot values), whether it was edited or deleted.
  - Deletes and edits take effect only on Save (the diff against the snapshot); no extra confirm.
- **New rows (owner, 2026-11-13):** the dialog always ends with one empty placeholder row for a new record. When the user fills it (it is "taken"), a fresh placeholder is added automatically below it. Saved records show #1, #2, #3 ...; new rows continue the numbering (#4, #5, #6 ...). The red X on a new row removes it completely (no strike-through, no undo); the numbers of the rows below it shift up. An untouched placeholder is never sent.
- **Rejected rows after Save:** all rejected rows are shown together at the bottom of the list, each with its en/vi error message. Their action slot works as for any row (X deletes it from the draft; undo restores the saved values). Undo also clears the row's rejection message.
- **List order and numbers (owner, 2026-11-13):** saved rows (#1, #2, ...), then new rows, then rejected rows, with the empty placeholder always the last row. A rejected new row keeps the number it had before Save; a rejected edited row keeps its saved number.
- **At `maxRecords`:** when saved plus new rows reach the limit, no further placeholder is added and the dialog shows a hint (en/vi) that the limit is reached, so the user is not confused. Deleting a row frees a slot and the placeholder comes back.

**Scope change (2026-11-13, owner): no scoreboard here.** This ticket logs records only: the collapsible Result section shows the record list (no scoreboard) and the dialog adds, edits and deletes. The client-computed scoreboard (games, wins, losses, points) moves to **CLIENT-GL-49**. Everything above that says "scoreboard" now means CLIENT-GL-49.

**Record schema contract (2026-11-13, owner's drafts `modules/common/src/test/resources/record/badminton-record-schema-v1.json` and `record-ui-v1.json`):** the sport's result schema is `{ maxRecords, record: { data: { type: "COMPETITIVE", playersPerSide: {min, max}, score: { slot: [{ title: {vi, en}, rule }] } }, UI: { id: "horizontal" | "vertical", config: { winnerAlign, winnerTone, loserTone } } } }`. The first team of a record is the winner. Scores are optional but, when given, need both sides. On Save, an invalid field gets a red border: a side below `playersPerSide.min`, or a score missing or failing its `rule` on one side. Supersedes the earlier `kind` / `recordMode` / `winningSide` sketch in this ticket and in `SESSION_RECORDS_DESIGN.md`.

**Record UI decisions (2026-11-13, owner, final contract `documentation/md/RECORD_SCHEMA_CONTRACT.md`):**
- Red border **while typing and on Save**. Marked: a team below `playersPerSide.min`; the same player on both teams; a score present on one team only; a score failing its slot `rule`; a team with any score filled but a `required` slot empty.
- No manual "add player" slot: the dialog draws `playersPerSide.max` player slots per team up front. More than 2 slots per team stack vertically. Score slots are always vertical when there is more than one.
- The winner is the first team, by position; scores are accepted as typed, but on Save the higher first-slot score goes first (see the 2026-11-14 addendum). On load the list draws the first team on the schema's `winnerAlign` side. Tones (`winnerTone`, `loserTone`) are semantic names mapped to design tokens, never hex.
- A stored record that fails the schema is skipped on load. The schema files live in `client/src/features/session/recordSchema/` (moved from `modules/common/src/test/resources/record/`), covered by a contract test.

### Addendum: the winner goes first on Save; the dialog stays open after saving (owner, 2026-11-14)

- **Winner first (supersedes "scores are not compared"):** the user may type the higher score on either side. On Save, `winnerFirst(schema, data)` (`recordData.ts`) puts the team with the higher score in the first score slot first, with its players and all its scores; a tie or a missing first score keeps the typed order. It is applied to every add and update just before sending, so the server stores the winner first, and the dialog (reloaded from the response) shows the swapped row, the winner on the `winnerAlign` side. Only the first slot decides (a second slot such as penalties does not). Contract: `RECORD_SCHEMA_CONTRACT.md`.
- **Also on load (same day):** `showableRecords` applies `winnerFirst` to every record it returns, and the dialog applies it to the save response, so a record already stored with the higher score on the second team (an older save, another client) is shown winner first in the section and the dialog and is not counted as a change. Storage is not rewritten until that record is edited and saved.
- **No close after saving:** a successful save keeps the dialog open (the rows reload from the response, Save disables, the footer button reads Close); a rejected row stays as before. Close or Discard leave it.
- **Tests:** `recordData.test.ts` (+4 for `winnerFirst`), `SessionResultDialog.test.tsx` (stays open; the wrong-side record is sent swapped and shown swapped); e2e `session-results.spec.ts` closes the dialog by hand after each save.
