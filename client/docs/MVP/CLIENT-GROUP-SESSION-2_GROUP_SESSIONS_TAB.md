# CLIENT-GROUP-SESSION-2 · The group's Sessions tab, and no slot information for a group session

**Status:** `DONE` (2026-11-20)
**Type:** New Feature · **Depends on:** SESSION-GROUP-2 (done), **SESSION-GROUP-12 parts B and C** (session backlog: the group `/today`, `/later`, `/history/dates`, `/history` endpoints and the end time of a cancelled session)
**Filed:** 2026-11-19, from the owner's group-session specification ("How it shows": a Sessions tab between Posts and Chat, grouped into collapsible Ongoing, Scheduled and History; the modal hides taken and open slots). The owner decided a PREPARING session is not mixed into Scheduled.

- **Tab:** `'sessions'` added to `GroupTabKey`/`TABS` in `GroupTabs.tsx` between Posts and Chat, rendered by `GroupsPage` (`{activeGroupTab === 'sessions' && ...}`), label in `groups.json` en/vi; existing `GroupTabs`, `GroupsPage` tests and `group-settings.spec.ts` updated.
- **Content:** collapsible groups built on `Collapsible`: **Ongoing**, **Scheduled**, **Preparing** (own group, only shown when it has sessions), **History** (loads on first expand). One hook per bucket on `GET /sessions/group/{groupId}?bucket=` with a `sessionKeys` group key invalidated by create, join and cancel; `SessionCard` rows; `EmptyHint` for empty groups; a "Create session" button opens the group-mode form (CLIENT-GROUP-SESSION-1). Opening a card opens `SessionDetailModal`.
- **No slot information:** for a group session the taken and open slot rows are hidden in the three places of `SessionDetailModal` (`WhoSection` summary and view rows, `InformationSection`, the Players header count and `PlayersMeter`) and in `SessionCard`'s participant count. **Scope change (2026-11-19, owner, at the pickup of CLIENT-GROUP-SESSION-1):** the `SessionCard` part is built in CLIENT-GROUP-SESSION-1 (its Posts-tab shortcut shows group session cards with the joined count only: no capacity, open slots or gender split); this ticket reuses it and, since round 4 (2026-11-20), the `SessionDetailModal` part too (Joined instead of Taken and Open): both are done in CLIENT-GROUP-SESSION-1; this ticket keeps only the Sessions tab.
- All strings en and vi; stories for the tab states; MSW handler for the bucket query; Playwright flow (open the tab, expand History, create from the tab).

**Consumer census:** `GroupTabs`, `GroupsPage`, `groups.json`, `SessionDetailModal`, `SessionDetailSections`, `SessionCard`, `useSessionDetailModalData`, `sessionKeys`, e2e mocks, `BASELINE-UPDATE-1` rows for the new visual surfaces.

**Scope change (owner, 2026-11-20, at the pickup): the Sessions tab has three collapsible sections with their own status filter, not four status buckets.** The four-bucket content bullet above is replaced by this (everything else in the ticket stands):

Each section has a **multi-select status filter dropdown, right-aligned in its header**.

| Section | Which sessions | Status filter (options, default) | Order |
|---|---|---|---|
| **Today's** | playing time overlaps today | all five statuses; default ONGOING, SCHEDULED, PREPARING | ONGOING, then SCHEDULED (the rest after, to confirm), each by start |
| **Others** | from tomorrow to the future | PREPARING, SCHEDULED, CANCELLED; default PREPARING + SCHEDULED | start time |
| **History** | grouped by the date of the **end time**, from yesterday back, like the history of My sessions on the Matches page; yesterday is open, every other date collapsed | COMPLETED, CANCELLED; default COMPLETED | end time |

History is limited to **30 days before yesterday**; "Load more" loads the next 30 days. **History lists a row for every day of the window, whether or not the day has a finished session (owner, 2026-11-20, after the first build listed only the days that have sessions): each row reads `<date> (<count>)`, `(0)` for an empty day.**

**Server need (owner's finding):** the existing `GET /sessions/group/{groupId}?bucket=` cannot serve this (one status per call, no overlap rule, no date grouping, no window). **SESSION-GROUP-12 is expanded** (owner, 2026-11-20) with dedicated group endpoints, status-filtered in one call each, in the **viewer's zone**: `/today`, `/later`, `/history/dates` (30-day windows by end date, `hasMore`) and `/history?date=`; the `bucket` parameter is **replaced**, so this ticket also moves the Posts-tab shortcut to one `GET /today?status=ONGOING,SCHEDULED,PREPARING` call (its client-side "is today" filter and three bucket calls go away).

**Other decisions (owner, 2026-11-20):** Today's order is ONGOING, SCHEDULED, PREPARING, COMPLETED, CANCELLED, then start; a session that overlaps today is in Today's whatever its status, History starts at "ended yesterday or earlier"; "today" and the end dates are read in the viewer's zone; each section's status filter **stays for the browser session** (reset on a new one).

**Server finding that goes with it:** a `PREPARING` session has no end (`scheduled_end_at` is set only with a duration), and all three cancel paths (`cancelSession`, `cancelUnpreparedSessions`, `RegularSessionCanceller`) set `cancelled_at` only, so a cancelled draft has **no end time**: History cannot order or group it by end. Owner's decision: a cancel sets the end to the start when the session has none (and the existing cancelled rows are backfilled); part of the same server ticket.

---

**Server contract (built 2026-11-19; the whole contract is `modules/session/docs/GROUP_SESSION_DESIGN.md` § 4.2).** `GET /api/sessions/group/{groupId}?bucket=ONGOING|SCHEDULED|PREPARING|HISTORY&page=&size=`, member only (`403 SESSION_GROUP_MEMBER_REQUIRED`). `SCHEDULED` is only `SCHEDULED`; `PREPARING` is its own bucket; `HISTORY` is `COMPLETED` plus `CANCELLED`, newest first; the other buckets are soonest first; the caller's `sort` is ignored; an unknown `bucket` is an un-coded 400. A page of `SessionResponse`, which has **no** field telling a regular session from a custom one. A regular session appears moments after the rule change that caused it, so a refetch right after a save in the settings may not show it yet.

## Implementation summary (DONE 2026-11-20)

**Scope changes after filing, all by the owner on 2026-11-20 (see the scope-change paragraph above for the first two):** (1) the tab is three status-filtered sections, not four buckets; (2) History is grouped by end date with 30-day windows; (3) **a right-aligned "See all" link in the header of the Posts tab's "Today's session" shortcut opens the Sessions tab** (added mid-implementation); (4) the end of a session cancelled without a duration (set to its start by the server) is not shown, in the card, the detail header and the detail "Ends" rows, for standalone sessions too; (5) the Posts-tab shortcut moves to one `/today` call; (6) **History shows a row for every one of the 30 days (zero days included), also for a group with no finished session at all** (the first build listed only the days that had sessions, and showed "No finished session yet." for a group with none; that hint is removed); (7) **the group page remembers the tab across a reload** (`activeGroupTab` moved from `GroupsPage`'s local state into the persisted `groupsPageStore`, reset to Posts whenever the selected group changes). Decisions answered at the gates: Others starts collapsed, Today's and History open; unticking every status shows "Select at least one status." and sends no request; the filters stay for the browser session; yesterday opens by default even when it has no session (it then reads "No session on this day."); opening a day with no session makes no request; "Load more" adds the next 30 days.

**Design as approved, restated.** Server contract: SESSION-GROUP-12 (`/today`, `/later`, `/history/dates`, `/history`, a required `viewerZoneId`, a repeatable `status`; `bucket` removed). Client: types and `sessionKeys` for the four calls; one hook each (`useGroupSessionsToday`, `useGroupSessionsLater`, `useGroupHistoryDates`, `useGroupHistoryDateSessions`) and `useGroupSessionsTabData` composing them with the filters (`groupSessionsTabStore`, a Zustand store persisted in `sessionStorage`, one selection per section shared by every group) and the expanded dates; components `GroupSessionsTab` (connected, mounted per group like the chat tab) over `GroupSessionsTabView`, `GroupSessionsSection` (collapsible, filter left of the chevron), `SessionStatusFilter` (checkbox dropdown, new `DropdownMenuCheckboxItem` in `shared/ui`) and `GroupHistoryDateSessions` (lazy per date); a `sessions` tab between Posts and Chat; the shortcut's data hook reduced to one `/today` call.

**What was built (beyond the list above).** The status list is sent comma-joined (`status=A,B`: axios would send `status[]=`). "Today" and every date are the viewer's (`getViewerZoneId`), as the server reads them; the shortcut therefore moved from the session's own zone to the viewer's. The history rows are built on the client from the window each page covers (the dates call only returns the days that have sessions): from the day before the previous page's `nextBefore` (or today for the first page) back to this page's `nextBefore`, with the count from the answer and 0 for the rest; the server needed no change. The first build followed empty windows by itself and showed "No finished session yet." for a group with none: both are removed. `distinctEnd(start, end)` (`startTime.ts`) returns the end only when it is after the start; `formatSessionTimeRange`, `formatSessionHeaderDateTime` and the detail's four "Ends" rows use it. Removed: `useGroupSessionBucket`, `sessionToday.ts` and its test. MSW: the `bucket` handler is replaced by the four endpoints (member gate, `viewerZoneId` and `status` validation, overlap, windows, end dates), the owned group has a spread of sessions laid out around the real today (`groupSessionsFor`), and a `groupSessionsEmpty` override (with `seedEmptyGroupSessionsOnNextLoad`) lets a frozen-clock visual spec keep the Posts shortcut empty.

**Divergences from the approved design.** None in behaviour. One test-only finding: opening the History filter while the date rows were still loading moved the page under its menu (an e2e flake in the new spec), so the spec waits for the rows first.

**Consumer census (final).** `GET /sessions/group/:id?bucket=`: the shortcut hooks, `queryKeys.groupSessions`, the MSW handler and `group-session-shortcut.spec.ts` are **updated here**. `GroupTabKey`/`GroupTabs` (test and stories updated; `group-invitations.spec` only clicks the Members tab by name, unchanged), `GroupsPage` (the tab and `onSeeAll`), `groups.json` en/vi. `startTime.ts` consumers (`SessionCard`, `SessionDetailModal`, `SessionDetailSections`): updated for the end rule; the record window (`resultAccess`) and `sessionReadiness` read `scheduledEndAt` only for `ONGOING`/`COMPLETED` and `PREPARING` sessions, compatible. `sessionKeys` writes: every session write invalidates `[...all]`, which covers the four new keys.
