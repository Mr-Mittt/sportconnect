# AUTH-13 · Visual regression coverage for the auth screens (`/login`, `/register`, `/forgot-password`, `/reset-password`)

**Status:** `DONE` (2026-10-13)
**Type:** Infrastructure (Testing)
**Depends on:** none — AUTH-1, AUTH-2 and AUTH-9 (`DONE`) shipped every surface below.
**Filed:** 2026-10-13, found at **AUTH-9** pickup. `client/CLAUDE.md` says a screen ships with a `visual-regression` check against a frozen `design-reference-*.html`. No auth screen has one: `e2e/visual/` holds only `app-*` specs, and `design-reference/design-reference-login.html` exists but nothing diffs the built page against it. AUTH-9 adds two more screens in the same state, so the gap is filed once for all four instead of inheriting it silently.

## What

- A `visual-regression` spec (`e2e/visual/auth-screens.spec.ts`) screenshotting at 375 / 768 / 1280 px:
  - `/login` (default, and with the AUTH-9 "Password updated" notice),
  - `/register` (default),
  - `/forgot-password` (form and sent state),
  - `/reset-password?token=…` (form, and the link-problem state for an expired token).
- Frozen reference HTML for the three screens that lack one (`design-reference-register.html`, `design-reference-forgot-password.html`, `design-reference-reset-password.html`), same approach as `design-reference-login.html`.
- **Scope change (2026-10-13, user decision at pickup):** also cover the Account Settings surfaces, which are the other auth-adjacent screens with no visual coverage today (`e2e/flows/` has `account-settings-unsaved.spec.ts` and `user-errors.spec.ts`, but nothing in `e2e/visual/`). A second spec, `e2e/visual/account-settings.spec.ts`, screenshotting at 375 / 768 / 1280 px:
  - `AccountSettingsModal` (default open state),
  - the ACCOUNT-3 `ChangePasswordDialog` stacked on it (empty form),
  - the ACCOUNT-4 `DeactivateAccountDialog` stacked on it (password-confirm).
  Frozen references for these (`design-reference-account-settings.html`, covering the modal and both stacked dialogs) follow the same approach as the auth screens. Title/filename of the ticket stay as-is to keep links valid.
- Baselines are generated by the `update-baselines` GitHub dispatch, not on a Windows host.

## Out of scope

Changing any auth screen's visuals; the Windows font-rendering noise floor.

## Summary (2026-10-13)

**Design as approved:** two new `visual-regression` specs, no `src/` change — `auth-screens.spec.ts` (7 states × 3 widths) and, from the pickup scope change, `account-settings.spec.ts` (3 states × 3 widths); four frozen reference HTML files; baselines from the `update-baselines` dispatch. Triggers copied from the passing functional specs (`password-reset.spec.ts`, `account-settings-unsaved.spec.ts`).

**Built:**
- `e2e/visual/auth-screens.spec.ts` — 21 instances: login (default; "Password updated" notice, reached by completing a real reset), register, forgot-password (form, sent), reset-password (form, link problem via `mockExpiredResetToken`).
- `e2e/visual/account-settings.spec.ts` — 9 instances: the modal, the stacked change-password dialog, the stacked deactivate dialog (initial state only).
- `design-reference/design-reference-{register,forgot-password,reset-password,account-settings}.html` — static, dependency-free, same two-column shell and tokens as `design-reference-login.html` (the illustration is reduced to its globe disc). The forgot/reset files show both of their states; the account-settings file shows the Password and Deactivate sections plus both dialogs, and omits the modal's profile/contact/personal form fields. **Like the existing reference files, nothing diffs against them** — no spec reads any `design-reference-*.html`; the baselines come from the built page. Written because the ticket and `client/CLAUDE.md` ask for them (user decision).

**Key decisions / deviations:**
- `animations: 'disabled'` on every shot (the community illustration floats continuously) plus a blur of the active element.
- **Found by a stability re-run, not by the first pass:** the account-settings modal shot flaked by 10 px because the Language select is pre-filled by async detection. The spec now waits for `Language` to have a value and for network idle; 3 consecutive generate-then-compare cycles then passed.
- The "token used" and "unknown token" reset states are not shot: they render the same layout as the expired one (only one sentence differs) and the mock validate endpoint gives them all the same 404.
- No i18n keys, hooks, stories, or backend change (no `src/` file touched).

**Verification:** `tsc -b` and eslint clean. Both new specs were run with `--update-snapshots` and then compared against themselves — 30/30 pass, repeatably. The generated PNGs were **deleted**: they are Windows-rendered and baselines must come from the `update-baselines` dispatch.

**E2E:** scoped `e2e` subset (`password-reset`, `auth-errors`, `auth-reactivate`, `account-settings-unsaved`, `account-deactivate`, `account-change-password`, `user-errors`) — 38 passed. The full `e2e` project was not run: no `src/` or flow spec changed, and the scoped subset covers every surface the new specs touch.

**Visual-regression expectation:** (b) 30 *new* baselines — `auth-{login-default,login-password-updated,register-default,forgot-password-form,forgot-password-sent,reset-password-form,reset-password-link-problem}-{375,768,1280}.png` and `account-settings-{default,change-password,deactivate}-{375,768,1280}.png`; every existing baseline untouched.

**Executed (2026-10-13):** `update-baselines` dispatch run, artifact `visual-baselines` applied in commit `13d61fe`. SHA-256 against the committed set: exactly the predicted 30 files are NEW, 0 CHANGED, 0 MISSING, and the other 150 baselines came back byte-identical. Eyeballed one image per surface (10 surfaces, mixed widths): each shows its intended state — the "Password updated" notice above the login form, the neutral "Check your email" confirmation, the link-problem state with "Request a new link", the Account Settings modal with its Language field filled, and both stacked dialogs empty. Rendered on Linux (DejaVu), so unlike the local Windows shots.
